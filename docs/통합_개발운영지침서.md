## 1. 프로젝트 목표와 범위

실물 미니 주차장 A·B 2곳(각각 카메라 1대, 카메라 총 2대)과 가상 주차장 C(필수)·D(여유 시)를 하나의 운영 시스템으로 연결한다. 미니카 총 24대는 실물 두 주차장에 나누어 사용한다. 카메라 설치 위치는 미정이다. 후보는 ① 주차장 중앙 상단에서 전체를 내려다보는 방식, ② 주차장 모서리 상단에서 전체를 대각선으로 촬영하는 방식이다. A·B 주차장 각각 전체 주차칸 가시성, 차량 가림, 번호 스티커 인식률, LED 인식률을 비교해 확정한다. 실물 판 크기·각 주차면 수는 차량 실측 후 결정한다.


| 구분 | 핵심 기능 | 범위 |

## 4. 공유 시스템 흐름

Camera A/B → Frame Hub → Vehicle / ID OCR / LED Detection → ROI Mapping → Evidence Events  
                    → FastAPI state engine + DB → Public API → User Web / Admin Web / LLM Tools

C·D 가상 주차장은 카메라가 아닌 시뮬레이터가 이벤트를 생성하되, 실제 주차장과 동일한 주차 상태/요금/결제 스키마를 사용한다. 영상 분석에서 확정 판정까지는 명확히 분리한다.

## 5.1. 핵심 객체 예시

{  
  "lot_id":"A", "camera_id":"camera_a", "space_id":"A-03",  
  "status":"occupied", "car_id":"12", "confidence":0.94,  
  "observed_at":"2026-11-02T10:00:00+09:00", "source":"vision"  
}

status: empty / occupied / uncertain / unavailable 제안. 불확실한 인식은 차량 ID를 null로 저장하고, 최종 주차 상태·입출차 확정은 서버의 시간적 안정성 확인 후 결정한다.

{  
  "event_id":"evt_0001", "lot_id":"A", "camera_id":"camera_a",  
  "event_type":"vehicle_observed", "space_id":"A-03",  
  "car_id":"12", "bbox_xyxy":[100,140,180,260],  
  "confidence":0.92, "observed_at":"2026-11-02T10:00:00+09:00"  
}

모델별 원시 출력은 별도 어댑터에서 위 공통 이벤트로 변환한다. fire 이벤트는 event_type=mock_fire_led_observed로 구분하고 위치·신뢰도·증거 프레임 ID를 저장한다.

## 5.2. 식별자·상태 일관성

- lot_id: A/B/C/D, camera_id: camera_a/camera_b; 가상 주차장 camera_id=null.
- space_id는 lot 내부에서 고유(A-01 등); DB에서는 (lot_id, space_id) 조합으로 고유하게 관리.
- car_id는 실물 미니카 스티커 두 자리 숫자 문자열 `10`~`99` (`00`~`09` 미사용, 2026-11-03 PM 결정). OCR 실패 시 null. 같은 차량이 여러 칸에서 검출되면 중복 이벤트로 표시하고 관리자 확인.
- session_id는 입차~출차 단위. 주차칸 사이 이동은 세션 종료가 아님.
- 실제 입차/출차 이벤트는 전체 주차장 관찰과 안정성 기준으로 확정. 단일 프레임 미검출 시 즉시 출차 처리하지 않음.
- 요금정책은 lot_id와 유효시작일로 관리; 실제 요금 수준은 미확정.
- 결제는 모의 결제만. idempotency_key로 중복 결제 방지. 결제 완료 금액에서 취소/환불 반영 후 매출 집계.

## 7. GitHub 협업·코드 소유 규칙

- 기준 브랜치 main은 항상 실행 가능 상태 유지. feature/<jira-key>-<short-name> 규칙(예: feature/KAN-4-vehicle-detector).
- 한 사람이 담당하지 않는 폴더를 수정해야 하면 Jira 댓글/Discord에 먼저 범위와 인터페이스를 공유.
- 두 AI 공동 담당자는 같은 모델 개발 이슈와 PR에서 함께 검토. 테스트/학습 코드 실험은 별도 폴더나 브랜치에서 진행.
- PR 기본 항목: Jira 작업 링크, 변경 이유, 수정 파일, API 변경 여부, 실행 방법, 테스트 결과/증거 화면, 롤백 방법.
- 최소 1명 타인 리뷰, 공통 API/DB/설정 변경은 김한별(PM)+해당 소유자 승인 후 병합.
- 직접 main push 및 force push 지양, PR 기반 병합. 충돌 시 해당 코드 소유자가 우선 해결.
- 대형 학습 데이터·모델 가중치·카메라 원본 영상은 Git 직접 업로드 지양. 저장 위치/버전/해시를 문서화.
- requirements.txt·lock 파일과 README의 실행 명령 동기화; 임의 라이브러리 교체 시 사전 공유.
## 8. AI 코딩 도구 사용 규칙

- GPT·Gemini·Claude 사용은 자유이나 동일한 프로젝트 명세와 API 계약을 프롬프트에 첨부한다.
- AI 생성 코드도 작성자가 직접 실행·테스트하고 책임진다. 실행 확인 없는 완료 처리 금지.
- AI에 요청할 때 담당 폴더·수정 가능한 파일·금지 영역·입출력 타입·기존 함수 시그니처를 명시한다.
- 다른 팀 코드 전체 교체 금지. 공통 코드 수정은 변경 사항과 영향을 PR에 기록한다.
- 실제 API 키/비밀번호/개인정보를 AI 프롬프트나 저장소에 넣지 않는다.
- 최신 라이브러리 설치 방법은 팀 공통 버전에 맞춰 검증하고, 해결 실패 시 로그를 공유한다.
## 9. Jira 관리 규칙

EPIC 01 차량 탐지(김한별·박해준), EPIC 02 번호 인식(우지원·김채린), EPIC 03 LED 인식(윤명수·서정범); EPIC 04 백엔드, 05 요금/결제, 06 챗봇, 07 사용자 웹, 08 관리자 관제, 09 실물 제작/통합. PM 관리 작업은 별도 EPIC 또는 Task로 둔다.


| 항목 | 필수 기입 |
| --- | --- |
| Epic | 개발 목표, 공동 담당자 2명, 완료 조건 |
| Task | 한 명의 대표 Assignee, 공동 참여자, 기한, 우선순위, 완료 기준 |
| 상태 | To Do → In Progress → Review/Test → Done |
| 버그 | 재현 단계·예상/실제·영상/로그·심각도 |
| 완료 조건 | 기능 동작 + 테스트 증거 + API 호환 + PR 병합 + 담당자 확인 |

Jira 사용자 선택 필드가 2명을 지원하면 공동 담당자로 등록하되, Jira의 기본 Assignee는 대표 1명으로 유지한다. 팀원 이름이 목록에 표시되는 것과 작업 자동 알림/권한은 별도이다.
