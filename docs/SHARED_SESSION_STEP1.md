# KAN-17 공용 주차 세션 Step 1

## 세션 저장과 billing 연동

최신 팀 main `504b5e2` 기준으로 billing의 `parking_sessions`를 재사용한다. 기존 열인 `session_id`(TEXT PK), `lot_id`, `space_id`, `car_id`, `entry_at`, `exit_at`의 표현과 이름을 유지한다. `space_id`와 `car_id`는 NULL을 허용한다. 새 `status`는 입차 시 `active`, 출차 시 `closed`다. 기존 `ses_` 및 UUID 문자열은 그대로 저장하며 접두어에 따라 분기하지 않는다. 시간은 시간대를 포함한 ISO 8601 문자열로 저장한다.

서비스는 호출자가 제공한 전용 SQLite 연결과 확정된 입차·출차 명령을 받는다. 호출자가 입차 재시도에 같은 세션 ID와 입력을 사용해야 한다. 동일 출차 시각 재요청은 저장된 결과를 돌려주며, 다른 시각의 재종료는 충돌로 처리한다. `BEGIN IMMEDIATE`로 조회와 쓰기를 직렬화한다. 식별 차량은 주차장에 관계없이 활성 세션 하나로 제한하는 보수적인 초기 정책을 사용한다. 미인식 차량은 차량 번호로 묶을 수 없으므로 동일 세션 ID로만 중복을 막는다. 이 동시성 보장은 해당 서비스를 통한 쓰기에 적용된다.

기존 billing은 요청마다 sqlite3 연결을 열고 `SMART_PARKING_DB_PATH` 또는 기본 `data/smart_parking.db`를 사용한다. 이 서비스는 DB 경로를 고르거나 연결을 생성하지 않는다. 기존 SQLAlchemy의 `ParkingLot`·`ParkingSpace`는 유지한다. SQLAlchemy 주차장 테이블과 billing의 주차장 테이블은 컬럼이 다르므로 스키마 소유권과 초기화 순서를 정하기 전 같은 파일에 두 초기화 절차를 적용하면 안 된다.

## 운영 적용 전 확인

운영 연결과 마이그레이션은 보류한다. DB 경로·DDL 담당자와 배포 순서, 식별자 유일 범위 및 미인식 차량의 재시도 ID 발급 방식을 먼저 확정한다. 기존 DB 이전은 승인 후 백업·복원 검증부터 진행한다. 격리 사본에서 쓰기를 차단한 뒤 기존 `exit_at`의 NULL 여부로 `active/closed`를 채우는 방안을 검토한다. 활성 중복과 잘못된 시각을 먼저 보고하고, 정상 데이터의 행 수·세션 ID·요금과 결제 참조를 대조한다. 검증 후 상태 제약과 활성 세션 고유 인덱스 도입 여부를 결정한다. 운영 라우터, 주차칸 배정, 가상 번호판의 식별 정책은 후속 범위다.

## 검증

Python 3.11 격리 환경에서 `pytest`로 신규 세션, billing 단위·API 통합, V3, health, 모델 테스트를 실행했다. 84개 통과, 실패·건너뜀 0개, 기존 Starlette/httpx 경고 1개. SQLite 접속은 실행마다 새 임시 디렉터리로 제한했고, 실제 billing 테이블 정의에 대한 `status` 추가는 신규 시험 DB에서만 실행했다. 동시 입차와 출차 각각 8개 요청에서 재전송은 같은 결과를 반환했고 충돌 입력은 한 요청만 반영됐다. 기존 요금 API는 같은 세션 행을 읽어 `ses_`·UUID, 식별·미인식 차량 모두 45분 요금을 계산했다. 운영 DB 이전 및 실제 트래픽 부하는 미검증이다.
