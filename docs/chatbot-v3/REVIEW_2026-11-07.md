## 통합 전에 해결해야 할 항목

1. **HTTP/UI 호환**: 현재는 `cards` 목록이며 기존 계약은 `card`, `messages`, `chips`,
   `flow`, `vehicle_context` 등이다. `session_id`, `chip_id`, confirmation 및
   runtime/state/alert version, `/updates` 처리도 어댑터 설계가 필요하다.
   기존 API 계약의 text 200자와 내부 서비스 2000자 제한도 HTTP 경계에서 맞춰야 한다.
2. **20초 화면 제한**: 모델 호출 2회와 도구 여러 번의 개별 timeout만 있다.
   전체 턴 deadline은 없고 글로벌 lock이 여러 대화를 직렬화한다.
   httpx timeout도 전체 요청 벽시계 제한을 보장하지 않는다. HTTP 연결 전 개선 필요.
3. **운영 캐시**: 요청 1000개 도달 후 계속 거절하는 구조이며 자동 회수 정책이 없다.
   재시작/다중 워커에서도 견적 중복 방지를 유지할 영속 저장·보존 정책이 필요하다.
   성급한 캐시 삭제로 같은 요청을 다시 실행하지 않도록 설계해야 한다.
4. **다국어·인증**: 기존 language/translation_status 계약 미구현. CLI에는 인증된
   백엔드용 토큰 설정이 없고 사용자별 차량 조회 권한은 연결 전 별도 결정해야 한다.
5. **실제 모델 의미 평가**: '23 말고 45', '부산역 말고 공항', 오타, 복합 질문,
   잘못된 장소 선택은 프롬프트만으로 보장되지 않는다. clarify의 question도 LLM 생성문이다.
   16개 설정 사례에 이런 반례를 더해 실제 모델로 평가해야 한다.
6. **기능 범위**: Q&A 40개는 요구/자료 목록이다. 별도 rate-policy/safety/space-context
   도구가 있어도 현재 Coordinator는 일부를 직접 선택할 수 없다.
   따라서 모든 FAQ를 구현한 완성 챗봇으로 표시하지 않는다.
7. **모델 설정**: API 문서에는 기존 모델 예시가 있으나 v3는 환경 설정으로 선택한다.
   가격·가용성·실제 품질은 확인하지 않았다. 유료 API 호출 없이 이번 검토를 진행했다.

## 검증

- 추가 반례 8개 포함, 외부 호출 없는 선택 시험: 29 passed / runtime 2개 제외.
- 수정 후 전체 회귀 시험: **387 passed, 1 failed, 7 warnings / 173.15초**. 새 챗봇 시험 31개는 모두 통과.
- frontend는 이번 검토에서 변경하지 않았으며 직전 복구 검증의 빌드 성공을 유지.
- Windows 실기·실제 LLM·배포 환경·브라우저 통합은 이번 검토 대상 시험에 포함되지 않음.

## 기존 시뮬레이터 시험의 간헐 실패

`tests/test_simulator_vehicle_types.py::test_old_database_general_vehicle_in_new_dedicated_bay_can_exit`
에서 `/simulation/C/clear`가 기대한 200 대신 503을 반환했다. 해당 시험만 독립 실행한 결과는
**1 passed / 7.86초**다. 기존 서버·시험 파일은 HEAD와 동일하며 새 chatbot_v3는 기존 서버에
등록되지 않았다. `runtime.py`의 clear 처리에는 전체 출차 확정을 기다리는 15초 deadline과
503 경로가 있지만, 이번 응답은 일반화된 에러 본문이라 정확한 내부 발생 지점까지 확정할 수 없다.
부하·스케줄링 또는 상태 안정화 타이밍에 따른 간헐 실패 가능성이 있으며 원인은 추가 확인 대상이다.
전체 실행을 모두 통과했다고 기록하지 않는다. 공통 서버 로직은 이번 챗봇 검토에서 변경하지 않았다.
