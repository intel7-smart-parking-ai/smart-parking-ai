# v2.15 설정·평가·검증 경계 검수

작성일: 2026-11-04(KST). 기준: `chatbot-v2.15.zip`, 로컬 커밋 `f4a6bb0`.

## 결론

평가 스크립트의 `.env` 키 확인을 고친 뒤에도 **키를 SDK에 전달하는 단계에 같은 원인의 누락**이 남아 있었다. OpenAI·Anthropic을 각각 직접 제공자로 선택하고 키를 `.env`에만 두는 경우다. OpenRouter 생성 경로에는 명시적인 키 전달이 있어 이 문제가 재현되지 않았다.

추가로 모델 미준비/호출 실패를 점수와 함께 보고하는 평가 경로, 측정 종료 후에야 발견되는 저장 경로 오류를 재현했다. `.env` 문법, 외부 평가 CSV, 선택 검사의 종료 코드는 입력 제약 또는 자동화의 해석 위험으로 구분했다. 모델 준비 중 설정 전환은 조건부 경쟁 위험이다.

이번 작업은 분석과 재현이다. 실행 코드·설정·기존 테스트·CSV를 수정하지 않았다. 기존 납품 zip 225개 파일이 현재 소스와 바이트 단위로 같은 것을 확인했다. 현재 결과는 발견 사항과 수정 순서를 제공하며, 수정 완료를 의미하지 않는다.

## 방법과 범위

- 설정 읽기 → 사전 조건 확인 → SDK 생성 → 분류 → 결과 집계 → 저장/종료까지 경계를 추적했다.
- 실제 선택 패키지의 생성자와 가짜 모델을 사용했다. `socket.connect/connect_ex`를 차단했으며 외부 통신 시도 0건, 실제 LLM API 호출 0회였다.
- 키는 합성 문자열만 사용했다. 실제 키·사용자 `.env` 내용은 보고서에 기록하지 않았다.
- 기존 35문항·회귀 248문항·고정 holdout 내용은 재현 입력으로 사용하지 않았다. 합성 문장/임시 CSV만 사용했다.
- 전체 회귀/브라우저 검사는 반복하지 않았다. 이번에는 실행 코드 변경이 없어, 의심 경로에 한정한 재현과 정상 대조군을 검사했다.
- 재현 스크립트/원자료는 작업 폴더의 `.validation/audit_v215/reproduce.py`, `evidence.json`이다. 배포 zip에는 넣지 않았다.

P1은 다음 모델 실측 전에 우선 보완할 항목이며, 모든 사용자 기능이 중단됐다는 뜻은 아니다. P2는 입력/자동화 보완이다. 조건부 항목은 발생 조건을 함께 적었다.

| 항목 | 종류 | 우선순위 | 발생 조건과 결과 |
| --- | --- | --- | --- |
| A1. 설정 키와 SDK 키 불일치 | 실행 경로 결함 | P1 | OpenAI/Anthropic 키를 `.env`에만 둠 → 설정은 통과, SDK 키는 없음 |
| A2. 준비 실패에도 hybrid 점수 생성 | 평가 유효성 결함 | P1 | 구 평가 스크립트에서 패키지 준비 실패 → 정상적인 숫자 결과와 정상 종료 |
| A3. 호출 오류 원인 누락 | 평가 결과 정보 누락 | P1 | 새 비교 도구에서 호출이 실패해 unknown이 됨 → CSV에 `api_error` 없음 |
| A4. 저장 경로 확인이 측정 뒤에 있음 | 평가 운영 결함 | P1 | 출력 상위 폴더 없음 → 모든 측정 후 FileNotFoundError, 결과 파일 없음 |
| A5. `.env` 문법 제약 | 조건부 설정 함정 | P2 | 첫 키 앞 BOM, 따옴표, 값 뒤 주석 → 키/모드가 의도와 다르게 읽힘 |
| A6. 평가 정답/인자 검증 부족 | 외부 입력 검증 결함 | P2 | 이름이 틀린 intent·빈 필드·불가능한 인자를 가진 CSV도 읽기 통과 |
| A7. 검사 미실행도 종료 코드 0 | 자동화 해석 위험 | P2 | 리허설 의존성/팀 파일 없음 → 미실행 안내와 코드 0, PASS는 없음 |
| A8. 다른 모델의 준비 상태를 인정 | 조건부 경쟁 위험 | 낮음 | 모델 A 준비 중 B로 전환 → B 준비 확인이 A의 ready를 수락 |

### A1. `.env`는 읽었지만 SDK에는 전달하지 않음

근거: `chatbot/config.py:14–31,57–58`, `chatbot/llm_router.py:92–102`.

설정 모듈은 `.env`를 자체 사전에 읽는다. 프로세스 환경변수에 값을 주입하지 않는다. 그런데 모델 생성 시 OpenAI·Anthropic에는 `api_key`를 전달하지 않고 SDK의 환경변수 읽기에 의존한다. OpenRouter에는 `api_key=config.api_key("openrouter")`를 전달한다.

실제 설치 패키지 생성자 결과:

| 키 위치 | 제공자 | 프로젝트 설정 키 확인 | 생성 결과/SDK 키 |
| --- | --- | --- | --- |
| `.env`만 | OpenAI | 있음 | 생성 시 `OpenAIError` |
| `.env`만 | Anthropic | 있음 | 객체는 생성되지만 SDK 키가 비어 있음 |
| `.env`만 | OpenRouter | 있음 | SDK 키 일치 |
| 환경변수 | OpenAI | 있음 | SDK 키 일치 |
| 환경변수 | Anthropic | 있음 | SDK 키 일치 |
| 환경변수 | OpenRouter | 있음 | SDK 키 일치 |

Anthropic의 실제 유료 호출 실패까지 실행한 것은 아니다. SDK 객체에 인증 키가 전달되지 않았다는 사실을 확인했다. 이 상태에서는 정상 인증 분류를 기대할 수 없다. 런타임은 실패 시 규칙/미인식 안내로 넘어가므로 사용자는 LLM 연동 실패를 단순 미인식으로 경험할 수 있다.

기존 `tests/test_llm_router.py`의 실제 생성자 검사는 환경변수에 두 제공자의 가짜 키를 넣었다. v2.15의 `.env` 전용 키 검사는 모델 준비/분류를 mock 처리했다. 두 검사가 각각 통과해도 **dotenv 읽기와 실제 생성자의 연결**은 검증되지 않았던 것이다.

최소 수정안: OpenAI와 Anthropic 생성자에도 해당 제공자의 `config.api_key(provider)`를 명시적으로 전달한다. `os.environ` 전체에 키를 주입하는 방식은 피하고 기존 환경변수 우선순위는 유지한다. SDK 생성 후 키 일치 여부를 비밀값 출력 없이 검사하는 대조 테스트를 추가한다. 관리자/결제 흐름이나 동시성 구조 변경은 필요 없다.

### A2. 모델 준비 실패인데도 비교 점수가 나옴

근거: `tests/run_llm_compare.py:40–50`.

`--compare`와 설정을 확인한 뒤 warmup을 기다리지만, 대기 종료 후 `ready`를 확인하지 않는다. 패키지 준비가 `ModuleNotFoundError`로 실패하도록 주입하자 다음 결과가 나왔다.

- 준비 상태: false.
- 합성 문장 2개 모두 실제 모델 분류 없이 unknown.
- 정답이 각각 get_fee/unknown인 합성 세트의 hybrid 정답률: 50%.
- `router_counts.not_installed=2`, `ok=0`인데 정상 종료했다.
- hybrid에 `skipped` 또는 측정 무효 상태는 없었다.

오류 원인 카운터는 출력되므로 완전히 숨겨진 것은 아니다. 다만 점수 또는 종료 코드만 읽는 자동화가 이를 정상 모델 비교로 오해할 수 있다. 기존 규칙-only dry run은 의도된 기능이므로 그대로 구분해 두어야 한다.

최소 수정안: 비교 요청이 있는 경우 준비 실패/준비 대기 종료를 명시적인 측정 무효 상태로 반환하고 원인을 기록한다. 모델 준비 확인과 유료 요청이 실제 성공했다는 확인은 별개다. 기존 규칙 fallback은 서비스에서 유지하고, 평가 도구 쪽에서 유효성을 판단한다.

### A3. API 오류가 unknown으로만 합산됨

근거: `tools/compare_models.py:42–61,94–103`, `chatbot/llm_router.py`의 invoke 예외 처리.

가짜 모델이 호출마다 `PermissionError`를 내도록 했다. 합성 2문장에 대해 런타임 진단은 `api_error=2`를 기록했지만, 비교 결과는 `unknown=2`, 정답률 50%, `wrong_tool=0`이었다. 새 비교 CSV에 `api_error` 필드는 없었다.

현재 `timeout/invalid_intent/invalid_params`만 추가 수집한다. 잘못된 키, 공급자 장애, 모델 접근 거절 등도 호출 오류로 처리되면 모델이 판단을 유보한 경우와 같은 unknown 합계 안에 들어간다. 가짜 모델로는 SDK의 특정 HTTP 오류 종류까지 검증하지 않았으며, 예외 후 집계 경로를 확인했다.

최소 수정안: 카운터의 모든 실패 원인과 실제 유효 분류 수를 측정 결과에 남긴다. `api_error/not_installed/missing_key/preparing/busy` 등으로 수행되지 못한 행이 있으면 해당 실행을 품질 채택용 정상 측정과 구분한다. `no_tool_call`은 모델의 미선택일 수 있어 인프라 오류와 같은 종류로 단정하지 않는다.

### A4. 모든 측정 뒤에 저장 오류가 발생함

근거: `tools/compare_models.py:87–97`.

출력 경로를 존재하지 않는 상위 폴더의 CSV로 지정했다. 모델/모드/파일/반복에 대응하는 합성 `measure()` 24회를 마친 뒤에야 `FileNotFoundError`가 발생했다. 결과 파일은 없었다. **실제 API 24회를 호출한 것은 아니다.** 가짜 측정 함수의 실행 횟수다.

실제 실측에서도 유효하지 않은 저장 경로를 같은 시점에 발견할 수 있다. 현재는 모든 그룹을 메모리에 모아 마지막에 쓰므로, 중간 예외/프로세스 중단에 앞선 결과도 파일에 남지 않는 구조다.

최소 수정안: 첫 측정 전에 출력 위치를 확인하고, 기존 파일 덮어쓰기 정책도 명시한다. 각 반복/그룹 종료 때 원자료를 임시 파일에 저장하고 완료 시 원자적으로 최종 파일로 교체하는 작은 보완이 적절하다. 측정 완료 전 최종 파일을 빈 파일로 덮어쓰는 방식은 피한다.

### A5. Windows 편집과 일반 `.env` 표기

근거: `chatbot/config.py:14–31,89–91,146–149,187–188`.

| 합성 파일 내용 | 관찰 결과 |
| --- | --- |
| `LLM_PROVIDER=openrouter` / `LLM_FEWSHOT=1` | 정상 |
| 첫 실제 키 앞 UTF-8 BOM | 키 이름에 BOM이 남아 provider 기본값 none을 읽음 |
| `LLM_PROVIDER="openrouter"` | 따옴표가 값에 남음; 시작 시 허용 제공자 검사에서 거절되는 값 |
| `LLM_FEWSHOT="1"` | True가 아니라 False |
| `LLM_FEWSHOT=1 # enable` | True가 아니라 False |

실제 Windows 기기를 실행하지 않았다. Windows 편집/저장 시 생길 수 있는 동일한 문자열을 주입해 파싱 결과를 확인했다. `.env.example`을 그대로 복사하면 첫 줄이 주석이므로 BOM이 첫 provider 키를 가리는 조건과는 다르다. BOM이 첫 실제 키에 붙은 최소 파일에서의 재현이다.

이는 모든 `.env`가 깨진다는 뜻이 아니다. 현재 파서는 단순 `KEY=VALUE` 형식만 처리한다. 지원 문법을 명시하거나 BOM·정상 따옴표를 안전하게 처리하는 보완이 필요하다. 주석을 처리한다면 따옴표/키 값 안의 `#`를 무조건 잘라 내지 않아야 한다. boolean 값이 잘못됐을 때 조용히 꺼지는 문제도 별도로 고려한다.

환경변수의 빈 문자열이 `.env`를 덮는 것은 현재 문서의 환경변수 우선 정책과 일치했다. 이를 임의로 파일 값으로 대체하는 수정은 권하지 않는다.

### A6. CSV 열 이름만 맞으면 잘못된 정답도 통과

근거: `tools/compare_models.py:64–72`.

합성 CSV 세 종류가 모두 `read_rows()`를 통과했다.

1. 존재하지 않는 intent 이름.
2. question만 있고 정답/인자 필드 값이 빈 행.
3. 차량 번호 칸에 숫자가 아닌 문자열이 있는 행.

현재는 헤더 순서, 비어 있지 않은 파일, 질문이 규칙 미인식인지만 검사한다. 기존 35/holdout 40에 잘못된 정답이 있다는 증거는 아니다. 사람이 추가 CSV를 만들거나 파일을 잘못 선택했을 때의 문제다.

최소 수정안: 질문·정답 필수값, 도구 이름, 열 개수, 인자 형식을 측정 전 확인한다. 기존 평가 파일과 API/도구 계약의 허용 범위를 먼저 확인하고, 기존 기대값을 바꾸는 방식으로 해결하지 않는다.

### A7. 선택 검사 미실행과 통과의 종료 코드가 같음

근거: `tools/rehearsal_1106.py:139–150`. 비슷한 정책은 `tools/check_alerts_compat.py`에도 있다.

리허설 `available()`을 false로 주입했다. 미실행 안내가 나오고 `main()`은 0을 반환했다. `PASS 11/06 리허설 6/6` 표시는 없었다.

선택 도구가 없는 환경에서 실패로 취급하지 않는 정책 자체를 버그라고 단정하지 않는다. 다만 CI/검수자가 종료 코드 0만 확인하면 리허설을 수행한 것으로 오해할 수 있다. 이번 v2.15 최종 리허설 로그에는 실제 6/6 PASS가 있으므로 그 결과가 미실행이었다는 뜻은 아니다.

최소 수정안: 일반 실행의 선택적 동작은 보존하고, 필수 게이트에는 `--strict` 같은 별도 모드 또는 실행/skip/pass 구조화 결과를 사용한다. 통합 검수는 실행 건수와 PASS 표시까지 확인한다.

### A8. 모델 초기화 중 설정 전환

근거: `chatbot/llm_router.py:105–129`, `tools/compare_models.py:34–39`.

가짜 생성자 A를 준비 중인 상태로 멈춘 뒤 설정을 B로 바꾸고 비교 도구의 `prepare()`를 호출했다. A를 준비 완료시키자 `prepare()`가 true를 반환했지만 `_model_key`의 모델은 A였다. 이어 B 분류를 요청하면 B 초기화가 시작되며 첫 결과가 unknown/preparing으로 돌아왔다.

현재 ready는 어떤 모델 객체가 있는지만 나타낸다. 원하는 설정의 모델 준비가 끝났는지는 포함하지 않는다. 재시작 후 한 모델만 사용하는 일반 시연 경로에서 이 조건이 발생한다고 단정하지 않는다. 다른 초기화가 진행 중인 프로세스에서 설정을 바꾸는 경우의 재현이다.

수정 제안: 준비 확인 시 요청한 설정과 준비된 모델 식별이 일치하는지 기존 모델 잠금 아래에서 확인한다. 기존 잠금/실행 슬롯/세대 구조를 재설계하지 않는다. 변경에 앞서 A 준비 중 B 전환·B 준비 실패·시간 제한 종료 세 경우의 검증을 준비해야 한다. 우선순위는 A1~A4보다 낮다.

## 왜 기존 전체 검사가 통과했나

1. 키 읽기와 SDK 생성자를 각각 검사했지만 키의 저장 위치를 교차하지 않았다.
2. 가짜 모델의 정답·예외 처리는 검사했지만, 평가 도구가 그 실패를 유효한 측정으로 집계하는지는 충분히 검사하지 않았다.
3. 출력 파일 검사는 정상 임시 폴더만 사용했다. 저장 불가능한 경로에서 호출을 시작하기 전에 멈추는지는 검사하지 않았다.
4. `.env`·CSV·선택 도구는 올바른 입력/실행 환경에 대한 검사 비중이 높았다.
