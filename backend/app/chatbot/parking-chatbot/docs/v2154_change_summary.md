# v2.15.4 — D-39 스티커·목업 정합성 변경 결과

작성: 2026-11-05. 기준: v2.15.3 `3e5e55e`. 브랜치: `feature/KAN-9-d39-mock-alignment`.

## 1. 승인 범위와 적용 기준

팀 저장소의 D-39 배정표와 사용자의 변경 승인을 근거로, 목업 차량 번호·차종과 이에 의존하는 검사 입력/기대 데이터를 맞췄다. 새 기능은 추가하지 않았다. 기존 검사 의미를 유지하며 승인된 데이터 의존 부분만 변경했다.

읽은 팀 기준은 main `4e048c8d7cfb7fccb3f13d7b3ccb326884ca1fd1`, progress-status `9fd4f2addacb66f8567f0fc87e270399a2822c79`, 통합 브랜치 `5163d0d2a267683c764ef0435c32d16572d08de0`다. D-39는 확정 배정이며 D-44 모델 결정은 별도다. 팀 코드는 격리 검증 사본에서만 사용했고 임의 병합하지 않았다.

변경 전 대응표와 작업 순서를 `docs/d39_mock_migration.md`에 먼저 고정했다(`f8016a0`). 목업·관련 회귀·문서는 `451eb17`, 선택 실행 검사에 남은 번호 참조는 `c7ebb5a`에 분리했다.

## 3. 보존한 항목과 의도된 차이

- ApiAdapter·engine·parser·templates·팀 서버 코드는 이번에 수정하지 않았다. API 경로·칩 ID·기존 환경변수 이름·응답 형식·설정 키 이름은 유지했다.
- 세션 잠금·요청 재전송·캐시 세대·알림 cursor·결제 직렬화·불확실 결제 기록·Lv2 정책은 변경하지 않았다.
- 주차장 배치·수용량·요금 정책·초기 주차 시간은 원본과 비교해 동일함을 확인했다.
- `assigned_car_ids=null`을 유지했다. 서버가 17·99 등 10~99 범위의 차량을 반환하면 기존대로 처리하며, D-39 24대로 서버/파서 입력을 제한하지 않는다. API 모드 차종은 서버 값을 사용한다.
- 모든 CSV와 LLM 평가/holdout 자료, chips.json·api_paths.json·.env.example·public_contract_v210.json은 그대로다. CSV와 지정 고정 파일 15개의 원본 바이트가 동일하다.
- 공개 계약 JSON은 그대로 두고, 검사에서 사용하는 `demo_cars` 기대 데이터 개수만 19대로 맞췄다. 각 항목의 키·타입 검사와 다른 경로 검사는 유지했다. 신규 회귀에서 명시 차량 19대와 전체 점유 27칸을 별도로 고정한다.
- 기존 Python 검사 26개 파일과 선택 실행 검사 2개의 테스트 메서드 목록·검증문 수가 원본과 동일하다. 검사를 삭제하거나 skip을 추가하지 않았다.
- 주차 차량의 기존 선택 필드 `vehicle_type`에 확정 차종이 전달되므로 전기차/장애인 차량의 기존 표시 문구가 해당 차종에 맞게 나온다. 일반 차량의 표시 이름은 추가하지 않았다.

기본 응답 스냅샷 242개 중 **241개 동일, 1개 변경**이다. 고정 질문의 “18번 차 관리자 불러주세요”는 이제 초기 미주차 차량이므로 관리자 요약이 기존 위치/요금에서 “위치 미확인”으로 달라졌다. 호출 접수·응답 필드·흐름은 같다. 번호 배정 변경에 따른 의도된 데이터 차이이며 차이 0으로 보고하지 않는다. 같은 스냅샷의 파서 분류·번호 추출 결과는 전후 모두 동일하다.

설치 환경 skip 2개는 RUN_SLOW 별도 실행 항목이며, 미설치 환경의 추가 7개는 선택 LangChain/제공자/메시지 패키지 부재다. 전체와 RUN_SLOW 결과는 중복을 포함하므로 합산하지 않는다. 실제 유료 LLM 호출은 하지 않았다. benchmark는 로컬 목업에 통제 지연을 넣은 검사이며 실제 서비스 성능 향상 수치가 아니다.

첫 종합 실행에서는 옛 번호·전각 숫자·목업 결제 도우미 참조와 초기 만차 점유 분리, 공개 목록 기대 대수, 장애인 차종 표시의 누락을 발견했다. 관련 항목을 고친 후 관련 77개 통과를 확인하고 전체 두 환경·질문·브라우저·HTTP 검증을 다시 실행했다. 그 최종 결과가 위 표다. 이후 선택 실행 benchmark/soak의 차량 번호 참조만 정리했으며 해당 두 도구만 실행했다. 제품 코드의 추가 변경은 없었다.

### 남아 있는 별도 검사 실패

1. **DATA-01 (required):** 미래 시각 응답을 거절해도 명부 순서가 바뀌는 기존 문제. v2.15.3 기록과 이번 추가 인수검사 모두 실패다.
2. **DNS-01 (advisory):** DNS 해석 지연이 짧은 요청 예산을 넘기는 기존 문제. 이번 합성 200ms 지연에서도 동일하게 재현됐다.
3. **선택 실행 optimization_soak:** 보고서 요약에 내부 lot ID와 공백(`A `)을 요구하지만 실제 문구는 `개발원주차장`을 사용한다. 수정 전 `3e5e55e` 소스를 격리 추출해 같은 줄의 실패를 재현했다. 번호 변경으로 생긴 실패가 아니며 이번 승인 범위를 넘는 검증 문구 변경은 하지 않았다. 이 실행은 중간 assertion에서 끝나므로 부하 검사 전체 통과로 해석할 수 없다.

따라서 전체 Python 회귀 실패 0과 별개로 **모든 추가 인수·선택 검사까지 합격한 상태는 아니다**. 위 항목은 숨기거나 기대값을 바꿔 통과시키지 않았다.

## 5. 미실행과 후속 작업

- 실제 스티커 부착 상태·카메라 인식·LED·Windows 실행·현장 PC 배치·팀 프런트 화면은 사람이 확인해야 한다. PowerShell/UTF-8 실행 지침은 유지했다.
- 모델 변경·실제 LLM 정확도/비용 평가·의존성 업그레이드·추가 기능 구현은 하지 않았다. D-44 및 원자료 확인은 기존 후속 사항이다.
- D-39 적용 승인은 이번에 해소됐다. 팀 반영 시 실제 부착 번호와 이 보고서의 확정 차종표를 대조한다.
- 팀 저장소 push·PR·병합·메시지 발송·운영 데이터 변경은 하지 않았다. 결과 ZIP의 `chatbot/` 폴더를 팀의 `backend/app/chatbot/` 위치에서 검토하면 된다.
- ZIP에는 chatbot 폴더 전체를 담되 .env·.bundle·.validation·__pycache__·빌드 캐시·DB·로그는 제외한다. 변경 전 보고서는 과거 기록으로 보존한다.
