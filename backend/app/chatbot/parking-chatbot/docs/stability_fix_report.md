## 2. 결제·경보 정책

- Lv1: 상태 안내와 조회·결제 확인 흐름을 유지한다.
- Lv2: 미완료 모의 결제를 취소하고 새 모의 결제를 열지 않는다. 대피·경보 위치·관리자 호출 버튼을 우선한다.
- 경보 주차장의 빈자리 이용 안내를 보류한다. 실제 자리 예약 기능을 만들지 않는다.
- 경보 해제 안내는 운영 재개를 단정하지 않는다. 이용자는 현재 경보·운영 안내를 확인한다.
- ‘결제 완료이므로 차단기가 자동으로 열린다’는 문구를 제거했다. 모의 결제와 현장 개방 확인을 구분한다.
- 결제 금액이 맞지 않거나 후속 요금 상태가 명시적으로 미결제이면 정상 영수증을 표시하지 않는다. 자동 재결제는 금지한다.
- 이미 결제 응답은 받았지만 후속 조회가 실패한 경우에는 그 응답을 버리지 않고 ‘상태 재확인 필요’로 표시한다.

서버와 실제 결제 백엔드 사이에 공통 트랜잭션이 없으므로, 최종 경보 확인 직후 발생하는 모든 변화까지 결제와 원자적으로 묶었다고 주장하지 않는다. 실제 차단기나 실제 결제는 이번 검증 범위 밖이다.

## 3. 검증 결과와 해석

| 검사 | 결과 | 범위 |
|---|---|---|
| 질문 분류 | 195/195 | 기존 175개+이번 재현 20개. 의도·주차장·차량 값 비교 |
| Python 검사 | 150개 통과 | 기존 108개+새 42개. FastAPI 포함 |
| 기존 Chromium 검사 | 15항목 통과 | 기존 화면·중복 방지·재전송 보호 동작 |
| 추가 Chromium 검사 | 12항목 통과 | 분석본의 화면 결함과 회복, 마지막 항목은 브라우저 실행 오류 확인 |
| 지연 주입 | 12세션 동시, 경보 조회 지연 40ms | 하나의 외부 경보 조회로 합쳐지고 전체 지연 통계에 반영 |

이번 20문장은 알려진 실패를 보정·고정한 회귀 사례다. 새 비공개 사용자 표본이나 실사용 정확도 평가가 아니다. 기존 확인용 20문장도 이전부터 존재한 세트다. 최종 판단에는 팀원이 작성한 비공개 질문과 실제 장비 연동 리허설이 여전히 필요하다.

원시 실행 결과는 다음 파일에 있다.

- `validation_results.json`: 검사별 명령·종료 코드·소요 시간
- `validation_python.txt`: 150개 검사명과 결과
- `validation_questions.txt`: 질문 195개 평가
- `validation_browser_existing.txt`: 기존 15항목
- `validation_browser_stability.txt`: 추가 12항목, 메모 30초 유지 포함
- `stability_benchmark.json`: 실제 측정된 개별 대기 시간·서버 통계 및 조회 횟수

모든 실행은 로컬 mock, LLM 비활성, 단일 프로세스 기준이다. FastAPI TestClient 의존성의 httpx 폐기 예정 경고가 있었으며 검사 실패는 아니다.

## 4. 최적화의 범위

동시에 들어온 경보 조회는 한 결과를 공유한다. API 모드는 기본 최대 0.2초 동안 공용 결과를 재사용하며 이 값은 `.env`에서 조정한다. Mock의 연속적인 수동 경보 변경은 즉시 관찰하도록 동시 조회만 합친다. 같은 요청의 위치 카드와 고정 카드 조회 공유도 유지했다.

기존 분석에서 40ms 조회 지연·12명 동시 요청은 마지막 응답이 약 484ms였고 통계에는 약 0.1ms로 기록됐다. 수정 후 1회 측정에서는 외부 경보 조회가 1회였고 최대 응답은 41.24ms였다. 개별 수치는 `stability_benchmark.json`에 있다. 이것은 잠금·중복 조회 개선을 확인한 통제 실험이며 실서버의 지연이나 처리량을 보장하지 않는다.

외부 조회 예산은 요청당 기본 6초, 개별 백엔드 호출 제한은 최대 2초이며 화면 fetch는 8초 제한이다. 남은 예산을 다음 조회와 선택적 LLM 호출에도 적용한다. 네트워크 수신 단계·처리 대기까지 포함하는 엄격한 실시간 보장은 아니므로 실제 팀 PC·백엔드에서 측정해야 한다.

WebSocket, Redis, 브로커, 추가 AI는 도입하지 않았다. 기존 2초 폴링과 수신 확인 커서를 유지한다.

## 5. 의도적으로 바꾼 기존 검사 기대값

검사를 통과시키기 위해 보호 동작을 삭제하지 않았다. 아래 항목은 동작 계약이 바뀌었으므로 기대값을 함께 수정했다.

1. 기존 ‘경보 알림이 결제 확인을 유지한다’ → **Lv2가 결제 확인을 폐기한다**. Lv1 유지도 별도 검사한다.
2. 세션 ID 없는 start 200 → **누락 요청 거부**. 유효한 세션 요청의 정상 응답도 함께 검사한다.
3. 요청 재전송 시 전체 JSON 동일 → **작업 결과 동일·중복 실행 없음**, 화면 상태 버전과 지연은 최신. 영수증 및 실제 pay 호출 1회 검사는 유지한다.

30세션 호출 ID 구분, 12번 결제 중복 요청의 pay 1회, 다른 기능 전환 후 과거 결제 차단, 오래된 요금으로 결제 확인 금지, 대기 순서와 알림 ID 재전송 검사를 유지했다.

## 6. 아직 연결하거나 보장하지 않은 부분

- 실제 팀 API의 경로·필드·주차장 구성은 미확정 상태다. 기존 mock은 A/B/C 각 8칸이다. 최종 모형에 맞춰 `LOT_IDS`, `LOT_CAPACITY`, 칩 및 백엔드 매핑을 함께 맞춰야 한다.
- 실제 DB·visit_id·실제 결제·차단기·비전·카메라·실제 LLM 호출은 검증하지 않았다. LLM 허용 의도 목록은 코드 정의와 맞췄지만 모델 품질을 평가한 것은 아니다.
- 서버가 관찰하지 못한 경보는 복원하지 못한다. 최근 100건 범위를 넘는 과거 이력이나 서버 재시작 후 메모리 상태도 보장하지 않는다.
- 세션·문의·보고서·큐·불확실 결제 상태는 단일 프로세스 메모리다. 장시간 운영 보관 상한·DB 이관은 별도 작업이다.
- 관리자 메모 초안은 같은 탭의 sessionStorage에 저장한다. 다른 기기/브라우저 동기화나 브라우저 저장 차단 상황의 새로고침 보존을 보장하지 않는다.
- 접근 키 검사는 시연 범위의 관리자 경계다. 사용자 로그인·차량 소유자 인증은 구현하지 않았다. 팀 인증을 재사용할 수 있으면 `chatbot/access.py`의 검사를 대체한다.
- 규칙 기반 한국어 인식의 전체 정확도는 확인하지 않았다. 새로운 표현의 실패는 추가 수집해야 한다.
- 영향 차량 목록 재조회는 경보 상태 변경 시 수행한다. 발생 시점에 실패한 목록을 나중에 확보해도 발생 당시의 사실로 소급하지 않는다.

## 7. 다음 작업 순서

1. 이 ZIP으로 사용자 2~3명·관리자 1명이 동시에 리허설한다. 새 기능은 추가하지 않는다.
2. 팀원의 비공개 질문, 호출 직후 경보, 결제 확인 중 경보, 끊김·재시도·새로고침을 확인한다.
3. 실제 API의 차량·입차 ID·결제 결과·경보 버전과 갱신 시각 계약을 맞춘다.
4. 공유망에서는 관리자 접근 키와 demo 비활성 설정을 확인하고, 팀 인증이 있으면 연동한다.
5. 실제 백엔드의 지연·실패를 측정하고 남은 실패 사례만 수정한다.
6. LLM 하나의 실제 연결 평가를 그 다음에 진행한다. 슈퍼바이저 AI 도입은 계속 보류한다.

실행 명령은 루트 README에 정리했다. 이전 문서들은 이력으로 보존했으며 현재 동작은 본 문서와 최신 API 계약을 우선한다.
