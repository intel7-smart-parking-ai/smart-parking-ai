## 3. 재현과 수정

수정 전 신규 6개 중 5개가 실패하고 명시적 false 대조군 1개만 통과했다. 수정 후 동일 6개 모두 통과했다. 기존 테스트 기대값은 바꾸지 않았다.

| 상황 | 수정 전 관찰 | 수정 후 검사 |
| --- | --- | --- |
| fee payment_blocked=true | 필드가 정규화에서 사라져 confirm_action 열림 | 확인 단계 없음·결제 버튼 없음·POST 0 |
| 차단 상태 요금 조회 | pay 칩 노출 | 서버 금액 2,500원 유지, pay/confirm_yes 없음·대피 안내 |
| 확인 이후 fee에서 차단 | 결제 POST 수행 | 확인 소비 후 차단·POST 0 |
| POST 409 EVACUATION_ACTIVE | 미확인 실패로 처리돼 불확실 기록 생성 | 기존 conflict 상태로 매핑하고 error_code로 대피 분기. POST 1회 후 재전송/‘네’에 추가 POST 0, 불확실 기록 0 |
| 명시적 false | 기존 확인→모의 결제 | 동일 정상 경로·결제 POST 1 |
| 잘못된 타입의 차단 값 | 무시됨 | 타입 검증으로 거절·POST 0 |

ApiAdapter.get_fee는 서버가 필드를 보냈을 때만 boolean을 검사·보존한다. 필드가 없는 기존 응답은 바뀌지 않는다. 새 공개 상태값을 만들지 않고 EVACUATION_ACTIVE를 기존 conflict로 정규화해 원래 error_code만 확인한다. 요금 조회·확인 진입·확인 직전 재조회·POST 결과 처리에 차단을 적용했다.

안내는 기존 모의 화재 안전 카드 제목·대피 문구를 재사용했다. 서버 차단 사실로 경보의 칸·시각·신뢰도·정확한 레벨을 만들어 내지 않는다. 경보 API로 Lv2를 확인한 기존 경로는 text와 safety 응답을 그대로 사용한다. 서버가 경보 API보다 먼저 결제를 차단한 경로에서는 대피 문구를 text에 포함한다.
