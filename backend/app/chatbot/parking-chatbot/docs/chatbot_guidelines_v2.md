## 3. 핵심 설계 원칙

### 3.1 규칙 우선 + LangChain 도구 호출 하이브리드
- 처리 순서: **칩 → 규칙 파서 → (규칙이 모를 때만) LangChain 라우터 → 처리 함수 → 템플릿**
- LangChain은 `bind_tools`로 **도구(의도) 하나와 인자(lot_id·zone·car_id)만 고른다.** 실행·답변은 기존 처리 함수와 `templates.py`.
- 답변 문장은 템플릿, 숫자는 백엔드 API 값. LLM이 빈자리 수·요금·경보 상태를 만들면 안 된다.
- LLM 설정: temperature 0, 3초 넘으면 포기하고 칩 안내, 동시 2개 상한, 늦게 온 결과 폐기, **경보 Lv2 중에는 LLM 생략**.
- LangChain은 선택 의존성(`requirements-llm.txt`). 미설치·키 없음·꺼짐(`LLM_PROVIDER=none`, 기본값)이어도 모든 기능 동작. 비상시 `LLM_ENGINE=direct`로 되돌림.
- 같은 패턴의 상용 예: Amazon Lex Assisted NLU Fallback, Rasa CALM, Dialogflow CX Generative fallback.

### 3.2 칩은 LLM을 거치지 않는다
- 칩 = 미리 정한 함수로 바로 연결. 같은 질문은 칩으로 물어도, 문장으로 물어도 같은 답.

### 3.3 응답 형식은 하나로 통일

```json
{ "text": "말풍선 문장 (두 줄 이내)",
  "card": {"type": "카드 종류", "data": {}},
  "chips": [{"id": "칩 ID", "label": "표시 문구"}],
  "banner": null,
  "safety": null,
  "updated_at": "데이터 기준 시각 (ISO 8601)" }
```

카드 종류: `empty_spots`, `car_location`, `fee`, `payment`, `exit_issue`, `journey`(카드 안 진행 표시), `alert`, `admin_call`, `unrecognized_candidates`
`safety`: Lv2일 때 사람 먼저 안내(title·guidance·vehicle_help), 그 외 null. 안정성 필드(`request_id`, `runtime_id`, `confirmation_token`, `cursor`)는 유지.

### 3.4 데이터 연결층 분리
- 챗봇은 `adapters.py` 함수만 부른다. `DATA_SOURCE=mock`이면 가짜 데이터, `api`이면 팀 백엔드.
- API 경로는 `api_paths.json`, 형식 차이는 어댑터에서 변환.
- 백엔드 장애 시 최근 30초 이내 값만 "마지막 정보, 갱신 중" 표시와 함께 사용. 결제 준비에는 오래된 값 금지.
- 경보 조회 실패를 "경보 없음"으로, 차량 목록 실패를 "0대"로 표시하지 않는다.
- 팀 API v1 변환 예정: `car_id`↔`car_id`, `space_id`("A-03")→칸 번호, 요금은 `session_id` 경유, 기결제 409→`already_paid`, 경보 목록→Lv0/1/2, 칸 상태 `uncertain`, 번호 미인식 `car_id: null`.

### 3.5 실행 작업과 조회 작업을 구분한다

| 작업 | 확인 단계 |
|---|---|
| 조회 (빈자리, 위치, 요금, 현황, 경보) | 없음 |
| 결제 | **있음**: 금액을 보여주고 한 번 더 확인 |
| 관리자 호출 (사람이 칩·명확한 문장으로 요청) | **없음**: 바로 등록 |
| 관리자 호출 (LLM이 고른 경우) | **있음 (작업계획서 v3 R1)**: "관리자를 부를까요?" 칩으로 제안 |
| 차량번호 | 세션에서 처음 나올 때·번호를 바꿀 때 확인 ("33번 차 맞으세요?") |
| 번호 미인식 후보 | 위치만 안내. 내 차로 자동 연결 금지, 요금·결제 금지 |

- 다른 기능을 요청하면 이전에 확인을 기다리던 작업은 취소한다.
- 중복 요청 방지, 결제 직렬화, 관리자 호출 중복 통합(10분)은 유지한다.
- 부정 문장("부르지 마", "안 오셔도 돼요", "결제하지 마")은 실행으로 분류하지 않는다.

## 4. UX·화면 원칙

### 4.1 대상과 이용 시점
대상은 **운전자**.

| 시점 | 마음 | 화면 |
|---|---|---|
| 진입 직전 (잠깐 정차) | 자리 있을까 불안 | 큰 숫자 하나, 3초 안에 읽혀야 함 |
| 주차 직후 | 어디 댔는지 잊음 | 위치 자동 기록 |
| 출차 직전 | 요금·출구 걱정 | 예상 요금 + 미리 결제 + "출구에서 자동으로 열려요" |

### 4.2 단순하게 (고령층·디지털 약자 배려)
- 칩은 한 화면에 3~4개 (근거: 힉의 법칙)
  - T = a + b × log₂(n + 1)
  - T: 결정 시간, n: 선택지 개수, a: 기본 반응 시간, b: 선택지가 늘 때 시간이 늘어나는 정도
- 자주 쓰는 버튼은 크게, 엄지가 닿는 화면 아래쪽 (근거: 피츠의 법칙)
  - T = a + b × log₂(D / W + 1)
  - T: 누르기까지 걸리는 시간, D: 버튼까지 거리, W: 버튼 크기, a·b: 기기·사람에 따른 상수
- 한 화면에 한 목적, 답변은 두 줄 이내, 숫자 먼저
- 추천 하나를 크게 ("가장 여유 있는 곳은 C 주차장")
- 하단 고정 메뉴 4개: 빈자리 / 내 차 / 요금 / 도움
- 글자 크게 보기, 고대비, 버튼 높이 최소 약 48px
- 앱 설치·회원가입 없이 QR로 바로 열리는 모바일 웹

### 4.3 대화 흐름
- 첫 메시지: 정체 + 할 수 있는 일 + 시작 칩
- 막다른 길 금지: 모든 답변 끝에 다음 행동 칩
- 이해 못 했을 때: 1차 예시와 함께 다시 묻기 → 2차 칩 + 관리자 호출 버튼
- 범위 밖 질문(날씨, 잡담)은 답하지 않고 할 수 있는 일로 안내
- "자리 나면 알려줘"는 "그 기능은 없어요" + 현재 빈자리·대안으로 정직하게 답한다
- 봇임을 분명히 하고 사람 흉내를 내지 않는다. 과하게 사과하지 않는다
- 답변마다 데이터 기준 시각 표시
- 색만으로 상태를 구분하지 않는다 (색 + 아이콘 + 글자)
  - 초록 = 빈자리/여유, 노랑 = 주의/혼잡, 빨강 = 만차/경보, 파랑 = 장애인구역, ◐ = 카메라 확인 중

### 4.4 상황 레벨 (경보)

| 레벨 | 배너 | 칩 | 챗봇이 먼저 말함 |
|---|---|---|---|
| Lv0 평상시 | 없음 | 기본 칩 | 아니오 |
| Lv1 확인 중 | 노란 배너 | 경보 확인 칩 | 예 |
| Lv2 경보 | 빨간 고정 배너 + 사람 먼저 카드 | 전부 경보용 (대피 안내가 맨 앞). **내 차 위치·요금·결제 칩 금지** | 예 |
| 해제 | 없음 | 원래 칩 | 예 ("경보가 해제됐어요") |

**Lv2 "사람 먼저" 문구 규칙**
1. 주차장 안에 있으면 지정 출구로 이동
2. 주차장 밖에 있으면 들어오지 않기
3. 차를 옮기려 하지 않기
4. 차량 피해 확인은 현장 관리자에게 요청 (관리자 호출로 정보를 남길 수 있음)
5. "영향 낮음", "이동하지 않아도 돼요" 같은 안심시키며 판단을 맡기는 표현 금지
6. 두 줄 이내, 나머지는 사람 먼저 카드

- 경보 단계 기준은 EPIC 03(LED 인식)과 맞춘다. 경보 응답 형식(`fire_router`)이 정해지면 어댑터에서 변환.

### 5.2 모의 화재 표기
- "화재 발생" 금지 → **"모의 화재(LED) 감지"**
- 보고서·브리핑에는 항상 "시연용 모의 상황이며 실제 화재가 아님"
- LED 모델 출력: fire evidence·위치·신뢰도만, `event_type=mock_fire_led_observed`

### 5.3 구현된 범위만 말한다

| 피할 표현 | 쓸 표현 |
|---|---|
| 관리자에게 전달했어요 / 다시 설명 안 해도 돼요 | 관리자에게 확인을 요청했어요. 차량 정보와 최근 문의를 요약해 관리자 화면에 함께 등록했어요 |
| 관리자가 확인해 연락드릴게요 | 차량 피해 확인은 현장 관리자에게 요청해 주세요 (연락 기능 없음) |
| 두 번 실행되지 않아요 | 중복 결제 요청을 구분해요 |
| 알림을 놓치지 않아요 | 일시적인 통신 장애로 받지 못한 알림을 다시 받을 수 있어요 |
| 자리를 잡아 드렸어요 / 자리 나면 알려드릴게요 | (예약·대기 없음) 지금 빈자리는 ○○예요 |
| 질식소화덮개가 필요합니다 | 질식소화덮개·이동식 수조 필요 가능성 (판단은 소방) |

발표 한 줄: **"버튼과 규칙으로 먼저 처리하고, 모르는 문장만 LangChain이 도구를 선택하며, 실행·답변·숫자는 시스템 데이터와 확인 절차로 처리합니다."**

## 6. 상황 보고서·현장 브리핑 원칙

- 사람이 처음부터 쓰지 않고, 시스템이 쓴 초안을 검토만 한다.
- 경보가 뜨는 순간 초안 생성 → 단계 변화, 영향 차량(근접 차량 강조), 챗봇 안내 수, 대피·근접 문의 수, 관리자 호출이 쌓임
- 체크리스트(현장 확인, 근접 차량 차주 안내(현장 접근 금지), 대피 방송, 119 신고 판단, 운영 재개)를 누르면 시각 기록
- 해제 후 관리자 메모를 붙여 확정. 진행 중 확정 불가, 확정 후 수정 불가
- 차량 목록 조회 실패 → "영향 범위 미확인" (0대 아님)

**소방 현장 정보 브리핑**
- 위치·구역, 해당 칸과 양옆 차량, 전기차 여부, 주차장 내 전기차 수, 장비 참고, 출구, 설비
- 장비 참고 판단 범위는 화재 칸과 양옆. 근거(충전 구역·인접 전기차) 있으면 "필요 가능성" 우선, 근거 없고 그 범위가 미확인이면 "대비 필요"
- 충전 구역은 설정값(바닥 색이 다른 칸), 전기차는 번호 목록 설정값. 색 인식은 보조
- 설비 값: null=미확인, true=있음, false=없음, 높이 제한 false=해당 없음 (`docs/settings_guide.md`)

## 8. 팀 공통 개발 규칙

- 카메라는 Frame Hub에서만 연다. 다른 모듈은 VideoCapture를 직접 쓰지 않는다.
- JSON 키는 snake_case, 시간은 ISO 8601 (시간대 포함)
- 브랜치 `feature/KAN-9-<기능명>`, main 직접 수정 금지, PR 리뷰 필수, **Merge는 PM(김한별)**
- 이미 push한 커밋은 `--amend`·강제 push 금지, 수정은 새 커밋으로
- 비밀키(LLM API 키, BACKEND_TOKEN)는 `.env`에만. 레포 루트 파일(requirements 등) 수정 금지
- 결과 zip·커밋에 `.bundle`, `__pycache__`, `.env` 포함 금지
- AI가 만든 코드도 담당자가 직접 실행·검증

## 10. 테스트·검증 원칙

- 작은 수정 중에는 관련 검사, 변경을 모은 뒤 전체·질문 검사(`python -m unittest discover -s tests`, `python tests/run_eval.py <csv>`)를 실행한다. 현재 범위와 반복 기준은 [구현·검증 원칙](validation_policy.md)을 따른다.
- 정답률 = intent·lot_id·car_id가 모두 맞은 질문 수 ÷ 전체 질문 수
- 질문 세트는 직접 만든 것이라 100%여도 실제 성능이 아니다. **팀원 블라인드 리허설 실패 문장을 계속 추가**
  - 규칙 오분류 문장 → `tests/questions_rehearsal.csv` (규칙 수정 대상)
  - 규칙이 모르는 문장 → `tests/llm_eval_questions.csv` (LLM 평가 대상)
- LLM 비교: `tests/run_llm_compare.py`로 규칙만 vs 하이브리드 정답률·평균/최대 응답시간·실패 이유
- 11/11 측정 지표: 정답률, 응답 시간(칩 vs 자유 입력), 실패율, 칩 사용률, 과업 완료 탭 수
- **Windows 호환**: 파일 읽기·쓰기 `encoding="utf-8"`, 테스트에서 subprocess로 Python을 띄우면 `PYTHONIOENCODING=utf-8` + `errors='replace'`
- 보고할 때는 "실제 실행한 검사"와 "코드 검토 수준"을 구분
