# 시스템 안정성 후속 검사 — 멈춤·자원·소켓 장애

2026-11-01. 기준본 v12에서 점검했습니다. 현장 운영에서 확인하는 장애 격리·제한 시간·중복 처리·상태 일관성·자원 상한을 기준으로 로컬 실행했습니다. 실제 운영 환경의 인증이나 부하 인증을 뜻하지 않습니다.

## 재현한 문제와 보정

1. **동일 세션 잠금 대기 상한 없음**: 잠금을 잡은 요청이 지연되면 다음 요청이 요청 예산 밖에서 계속 기다렸습니다. 잠금 대기를 REQUEST_BUDGET_SEC(기본 6초)로 제한하고, 대기 시간도 이후 외부 조회 예산에서 차감합니다. 초과하면 409와 재시도 안내를 반환하며, 처리 중인 기존 요청을 강제 중단하지 않습니다. 잠금 해제 후 다시 정상 처리됨과 다른 세션의 독립 처리를 확인했습니다.
2. **개발 서버의 미완성 HTTP 요청**: 기본 소켓 제한 시간이 없어 헤더·본문 수신에서 스레드가 무기한 묶일 수 있었습니다. 수신 제한 10초를 적용하고 본문 수신 시간 초과는 408로 종료합니다. 테스트는 동일 구현의 제한만 0.15초로 줄여 실제 TCP 연결로 실행했습니다.
3. **개발 서버의 비정상 연결·본문 처리 보강**: 응답 중 연결 종료에 따른 BrokenPipe/ConnectionReset을 처리하고, 선언 길이보다 짧은 본문과 지나치게 깊은 JSON을 거부합니다. 깊은 JSON과 malformed/과대 본문 거부 후 정상 조회 응답을 확인했습니다. 연결 종료 예외 처리는 코드 검토 수준이며 강제 RST의 모든 타이밍을 재현한 것은 아닙니다.

수정 파일: chatbot/engine.py, server_dev.py. 신규 의존성은 없습니다. FastAPI의 HTTP 수신 제한은 ASGI 서버·프록시 설정 대상이며 개발 서버의 10초 제한을 FastAPI에도 적용했다고 주장하지 않습니다.

## 남아 있는 운영 한계 — 코드 검토 수준

- **장기간 운영 데이터 증가**: 관리자 문의·사건 보고서는 메모리 목록에 누적됩니다. 자동 삭제하면 처리 이력을 잃을 수 있어 이번에 임의의 보존·삭제 정책을 넣지 않았습니다. 장기 운영에는 영속 저장과 보존 정책이 필요합니다.
- **연결 수 상한**: 개발용 ThreadingHTTPServer는 연결 수·요청률을 제한하는 운영 서버가 아닙니다. 10초 수신 제한은 유휴 대기 상한이며, 동시 연결 폭주나 매번 조금씩 보내는 연결의 총 수신 시간까지 보장하지 않습니다. 현장 공유망 이상의 배포에서는 ASGI/프록시의 본문 크기·전체 수신 시간·동시성·요청률 제한을 확정해야 합니다.
- **메모리·재시작**: 단일 프로세스 상태입니다. 재시작 복원·다중 프로세스 공유·고가용성·장기 RSS 관찰은 검증 범위 밖입니다.
- **물리 시스템 연동**: 실제 API·DB·카메라·기기·현장 와이파이·LLM API는 아직 검증하지 않았습니다. 해당 환경의 시간 초과·노후 데이터·재접속·서버 재시작 시나리오는 통합 리허설이 필요합니다.
- **전체 실행 시간**: 외부 조회 예산과 잠금 대기 상한을 적용하지만 임의의 Python 코드나 운영체제 정지를 강제 중단하는 watchdog은 아닙니다.

현재 범위에서는 재현된 멈춤 경로를 보정하고 회귀 검사를 통과했습니다. 운영 배포 완료 판정과 모든 장애가 없다는 보장은 별개입니다.
