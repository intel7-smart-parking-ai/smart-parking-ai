# 현재 프로젝트 기준 구현·검증 원칙

갱신: 2026-11-05. 사용자의 “최신 프로젝트 내용을 반영해 검증한다”는 지시를 반영한다. 적용 범위는 `backend/app/chatbot/`다. 과거 작업계획과 보고서는 당시 기록으로 보존한다.

## 1. 기준을 정하는 순서

1. 이번 작업의 사용자 지시와 이미 승인된 범위.
2. 팀 레포의 최신 확정 결정(`docs/DECISIONS.md`)과 해당 기능의 API 계약・`docs/통합_개발운영지침서.md`・`docs/GIT_RULES.md`・구축 절차(`docs/RUNBOOK_DEMO_HOST.md`).
3. 검증할 브랜치/커밋의 구현과 현재 설정·실제 응답.
4. 위 기준을 검증하는 기존 테스트·질문·스냅샷.
5. 과거 작업계획·검토 의견·로그.

현재 코드가 이렇게 동작한다는 사실만으로 기대값을 바꾸지 않는다. 팀 문서와 구현이 충돌하면 승인된 동작을 먼저 확인하고 구현 오류·오래된 검사·아직 적용되지 않은 결정을 구분한다. 미확정 제안은 확정 명세로 취급하지 않는다. main과 미병합 브랜치의 결과도 구분한다.

## 2. 매 작업에서 먼저 확인할 것

- 팀 저장소의 main과 관련 결정/통합 브랜치를 읽기 전용으로 확인하고 커밋을 기록한다. 단일 브랜치 clone에서는 다른 브랜치를 fetch해도 추적 참조가 갱신되지 않을 수 있으므로 실제 원격 HEAD와 대조한다. 이전 커밋을 확인 없이 “최신”이라 부르지 않는다. 연결할 수 없으면 마지막 확인 시점과 미확인 범위를 명시한다.
- 변경할 기능에 관계된 결정·계약·설정·호출 경로와 검사를 대조한다. 저장소 전체를 반복 검사하거나 오래된 계획의 작업을 다시 실행하지 않는다.
- 수정 전 실패가 있으면 관련 사례로 재현한다. 이미 재현된 기록이 충분하면 이를 재사용한다.
- 계획에는 수정 범위, 보존할 조건, 기대값 변경 근거, 최종 검증 범위를 적는다.

이번 확인 기준:

- chore/progress-status: `3cab1b0738a582f2fc7f1273a6fa31ce73a021bd`
- codex/backend-integration-complete: `f30cd77b3d03d42df3752976dfc6afaa7f382c60` (main 미병합)
- D-06: 실물 번호 두 자리 10~99, 00~09 미사용.
- D-39: 확정 24대 배정. 전기차 23·42·57·85, 장애인 차량 14·32·55·75. 상세 대응은 `d39_mock_migration.md`.
- progress-status D-48: 기본 시연 기기는 PC, 휴대폰 음성 퍼포먼스는 필수가 아닌 후속 항목.

- 모델 변경 D-44는 해당 결정 문서에서 PM 확인 대기다. 임의 모델 변경 근거가 아니다.

위 커밋/대수/문항 수는 확인 시점의 기록이며 영구 고정값이 아니다.

## 3. 기대값 변경 판단

| 실패 유형 | 처리 |
| --- | --- |
| 확정 배정표·주차장 표시 이름·실제 API 계약과 옛 fixture가 다름 | 근거를 기록하고 관련 입력·기대 데이터·문서를 함께 갱신 |
| 질문 파일이 승인된 범위에서 추가됨 | 파일 수·문항 수·테스트 이름 갱신. LLM 평가 세트 제외 및 빠진 파일 검사는 유지 |
| 보고서에서 내부 주차장 ID 대신 설정된 표시 이름을 사용 | 해당 위치의 현재 표시 이름을 검사. 보고서 연결·호출 포함 관계는 계속 검사 |
| 중복 결제·확인 없는 실행·경보 무시·거절 응답의 상태 변경·타 세션 혼입 | 구현 결함으로 관리. 기대값을 실패 동작에 맞추지 않음 |
| 최신 합의가 없는 SLA나 로컬 장애 주입 수치 | 별도 제안 기준으로 보고. 합의된 기준과 분리하며 임의로 통과 처리하지 않음 |
| 명세와 근거가 모호함 | 추정임을 밝히고 결정을 요청. 독립적으로 진행 가능한 작업은 계속 수행 |

이미 승인된 명세를 맞추는 fixture·표시 이름·기대 개수·공식 API 연결은 이번 원칙 안에서 진행한다. 같은 명세 변경을 다시 승인받느라 작업을 중단하지 않는다. 팀/사용자 승인 범위를 벗어나는 새 기능·기능 삭제·계약 변경·정책 변경은 먼저 보고하고 허락을 받는다. 첨부 관리 메모의 “처리 없음”도 현재 구현과 대조하며, 이미 구현된 것을 중복 구현하지 않는다.

기대값을 고칠 때는 변경 전후와 출처를 남긴다. 검사를 삭제하거나 assertion을 없애거나 FAIL을 SKIP으로 바꾸어 통과시키지 않는다. 문구 고정이 필요한 UX 검사는 유지하고, 설정 가능한 이름을 검사할 때만 현재 설정을 사용한다. fixture와 구현이 같은 상수를 읽는 검사만으로 배정표 정확성을 입증하지 않으며 D-39 같은 고정 명세의 독립 대조 검사도 유지한다.

## 4. 계속 보존할 조건

- 기존 기능, 챗봇 공개 API·응답 형식·칩 ID·설정 키 이름과 Windows UTF-8 호환. 승인된 팀 API 변경에 맞춘 소비 경로 설정값은 변경 가능하며, 호출부·검사·문서를 함께 반영한다. 챗봇 공개 계약을 바꾸는 경우에는 팀 공통 계약 절차를 따른다.
- 세션 잠금·요청 ID 재전송·캐시 세대·알림 cursor·결제 직렬화·확인 절차·Lv2 정책.
- 불확실한 정보를 확정 사실로 만들지 않기. API 장애 때 목업으로 바꿔 정상처럼 보이지 않기.
- 미인식 차량의 결제 차단, 결제 전 재조회, 오래된 응답의 상태 되돌림 방지.
- 구조 변경이 필요하면 이유와 검증 방법을 먼저 제시한다.
- 새 사용자 기능·의존성·전환 모드를 정리 작업에 끼워 넣지 않는다.

## 5. 검사는 변경 영향에 맞춰 실행

작은 단위 수정 → 관련 검사 → 변경을 모은 뒤 필요한 최종 검증 순서로 진행한다. 매 파일 수정이나 커밋마다 전체 검사를 반복하지 않는다. 추가 실패·코드 변경·미해결 위험이 있을 때만 해당 범위를 다시 확인한다.

| 변경 영향 | 검증 |
| --- | --- |
| 문서만 변경 | 링크·명령·현재 상태와의 일치 확인 |
| 테스트의 낡은 이름·fixture만 갱신, 제품 코드 동일 | 해당 검사와 인접 회귀. 직전 전체 결과는 출처와 시점을 표시해 참고 |
| 엔진·어댑터·상태·계약·공용 설정 등 제품 동작 변경 | 최종 전체 검사: LangChain 설치/미설치, 질문, 영향 있는 브라우저·HTTP 연결·리허설 |
| 동시성·프리징·메모리 관련 변경 | 관련 경합/장애 주입/장기 검사 추가. 다른 전체 검사와 중복 집계하지 않음 |
| 팀 서버·통합 브랜치 변경 | 현재 챗봇을 격리 사본에 연결해 계약·실제 서버 리허설 확인. 제품 범위 밖 파일 수정 금지 |

질문 파일은 현재 `tests/questions*.csv` 전체를 확인하며, `tests/llm_eval_questions.csv`는 별도 평가 대상으로 유지한다. 2026-11-05 현재 규칙 회귀는 **9세트 248문항**이다. rehearsal 포함/제외 범위를 명시한다. LLM 평가 자료나 holdout을 정답률을 올리기 위한 튜닝 대상으로 사용하지 않는다.

파일 읽기·쓰기는 `encoding="utf-8"`, Python subprocess는 `PYTHONIOENCODING=utf-8`를 유지한다. 실제 유료 LLM 호출·키 변경·현장 장비 조작·push/PR/병합·외부 메시지는 해당 작업의 별도 승인 범위에서만 수행한다.

## 6. 결과를 보고하는 방법

- 구현 오류 수정 / 최신 명세 반영 / 검사 오류 수정 / 미해결 / 미실행을 구분한다.
- 실행한 검사의 전체 수·통과·실패·오류·skip을 기록한다. 별도 묶음과 전체의 중복을 합산하지 않는다.
- 실제 새로 실행한 검사와 이전 결과 참고를 구분한다. 새로 전체 검사를 안 돌렸으면 전체 통과를 새 측정처럼 쓰지 않는다.
- 스냅샷 차이가 있으면 개수와 이유를 밝힌다. 승인된 배정 변경을 무조건 회귀로 보거나 차이를 숨기지 않는다.
- 과거 보고서는 고쳐 쓰지 않고 현재 문서에서 해소/잔존을 연결한다.
- 현재 DATA-01은 거절된 응답이 명부를 바꾸는 필수 무결성 검사다. DNS-01은 합의 SLA가 아닌 별도 advisory 검사다. 둘 다 표시 문구 불일치와 구분하며 실제 실패 기록은 유지한다.
