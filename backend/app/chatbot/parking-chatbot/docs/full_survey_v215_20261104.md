# v2.15 챗봇 전수 검토 — 근거·우선순위·수정 경계

작성일: 2026-11-04(KST). 기준: 납품 `chatbot-v2.15.zip`, 소스 커밋 `f4a6bb0`.

## 결론

**일반적인 문의/거절이 관리자 호출로 접수되는 규칙 분류 문제가 가장 먼저 수정할 항목이다.** “직원 계세요?”, “관리자 있나요?”, “관리자 오지 마세요”가 각각 관리자 접수 1건으로 이어졌다. LLM이 꺼져 있어도 발생한다.

이용자 화면의 미확인 값 표시, 거절된 API 응답의 내부 명부 변경, 관리자 편집 중 체크리스트 갱신 누락도 재현했다. 혼잡 응답의 화면 반영, 시간 제한, 정책별 기본 시간 표시는 특정 조건에서의 문제다. 이 보고서는 문제 수를 늘리기 위해 각 문장을 별도 결함으로 세지 않고 원인별로 묶었다.

이전 설정·평가 검수에서 확인한 SDK 키 전달과 평가 도구의 문제는 별도 미해결 항목으로 유지한다. 이번 조사는 수정 전 분석이며 실행 코드·기존 테스트·CSV는 바꾸지 않았다. 새 배포 zip도 만들지 않았다.

## 1. 조사 범위와 방법

- 챗봇 소유 영역 `backend/app/chatbot/`: 실행 Python 38개, HTML 2개, 실행 설정 JSON 3개, 합계 43파일/7,638줄을 정적 검토했다. 직전 조사에서 읽은 LLM·설정 코드는 동일 버전임을 확인해 재사용했다.
- 기존 테스트/실행 보조 Python 68개는 모두 AST 구문 검사를 했다. 의미 검토는 관련 회귀 검사·장애 주입·평가/브라우저 실행 도구에 집중했다. 68개 테스트 파일의 모든 경로를 다시 실행했다는 뜻은 아니다.

- 외부 서버·유료 LLM·실제 키는 사용하지 않았다. Python 재현에서는 외부 연결을 차단했고 시도 0건이었다. 브라우저 검사는 동적 포트의 로컬 모의 서버만 사용했다.

- “미지원 기능”, “의도된 단일 프로세스”, “잘못된 입력을 거절하는 정상 동작”은 새 결함으로 분류하지 않았다.

## 3. 재현과 원인

### F1. 문의·거절을 관리자 호출로 접수

근거: `chatbot/parser.py:163,185–218,266–278`, `engine.py:1067–1095,746–779`.

| 입력 | 결과 intent | 새 관리자 접수 |
| --- | --- | ---: |
| 직원 계세요? | call_admin | 1 |
| 관리자 있나요? | call_admin | 1 |
| 관리자 오지 마세요 | call_admin | 1 |
| 관리자 오지 말아 주세요 | cancel_action | 0 |
| 직원 좀 불러 주세요 | call_admin | 1 |

질문 보호에는 존재/위치 질문 표현이 충분하지 않고, 부정의 `오지 말`과 `오지 마`가 다르게 처리된다. 보호 규칙을 통과하지 못하면 ‘관리자/직원’이라는 단어만으로 넓은 call_admin 규칙이 맞는다. 규칙 경로는 기존 명세대로 즉시 접수하므로 분류 실수가 실제 접수로 이어진다. B 도구 설명을 고쳐도 규칙이 먼저 처리하므로 해결되지 않는다.

같은 분류 경계에서 “결제하는 방법 알려줘”도 payment_help가 아닌 pay_fee/ask_vehicle로 진행했다. 이 경우 결제 실행은 없었다. 관리자 오접수보다 영향이 작은 안내 흐름 오류로 같은 묶음에 기록한다.

최소 수정 방향: 존재/위치·방법 질문은 문의로, 명시적 거절은 취소로 구분하는 보호 표현을 좁게 보완한다. 긍정 호출과 호출 칩의 즉시 접수, LLM 호출 제안의 확인 칩, 결제 확인 단계를 유지한다. 기존 기대값을 바꾸지 않고 이 문장들에 대한 새 회귀 사례를 추가한다.

### F2. 이용자 화면에서 미확인 값을 수치로 바꿈

근거: `static/index.html:238,281–287,303–309`, `adapters.py:606–641`, `contracts.py:61–78,134–147`.

프로젝트 어댑터와 계약 검사에 실제로 통과한 합성 API 응답을 현재 Chromium 화면에 넣었다.

| API 의미/값 | 현재 이용자 화면 | 필요한 의미 |
| --- | --- | --- |
| confidence=null | 신뢰도 0% | 미확인 |
| 위치 응답에 entry_at 없음 → 정규화 후 null | 들어온 시간 09:00 | 시각 미확인/미제공 |

JavaScript의 `(confidence || 0)`이 null을 0으로 바꾸고, `new Date(null)`이 1970-01-01 00:00 UTC로 변환되어 한국 시각 09:00이 된다. 현재 팀 위치 응답 모델에도 entry_at이 없는 경로가 있다. 따라서 반드시 잘못된 서버 응답에서만 생기는 문제가 아니다.

관리자 화면의 nullable confidence는 이미 ‘미확인’ 처리가 있지만 이용자 카드까지 적용되지 않았다. Lv2 데이터와 대피 안내는 유지되므로 null 신뢰도 때문에 경보 단계가 낮아졌다고 주장하지 않는다.

최소 수정 방향: 시간/신뢰도 표시 함수에서 미제공·null·유효하지 않은 값은 수치를 만들지 않는다. 정상 값의 시간대와 표시 형식은 유지한다. API 키/카드 type/응답 필드 변경은 필요 없다.

### F3. 거절된 점유 응답이 명부에는 반영됨

근거: `adapters.py:516–552,554–604,896–925`, `catalog.py:243–249`.

서버 점유 응답의 as_of를 한 시간 미래로, A 주차장 칸 목록을 기존의 역순으로 넣었다. 점유 조회는 DataUnavailable로 올바르게 거절됐다. 그런데 실행 명부 첫 칸은 `A-01,A-02,A-03,A-04`에서 `B-06,B-05,B-04,B-03`으로 이미 바뀌었고 명부 version도 1→2가 됐다.

`_space_snapshot()`의 `adopt_spaces()`가 최종 응답 검증·신선도·캐시 세대 확인보다 먼저 실행된다. 따라서 응답 게시를 막는 검사와 명부 게시 시점이 일치하지 않는다. 캐시에 잘못된 점유 응답이 저장됐다는 뜻은 아니다. 확인한 부작용은 명부 변경이다. 이후 spot_no/space_id 변환과 파생 위치 계산에 영향을 줄 가능성은 있으나, 이번 재현에서 잘못된 근접 차량 안내까지 실행해 확인하지는 않았다.

최소 수정 방향: 읽은 칸 목록을 검증 전 임시 결과로 유지하고, 신뢰할 응답/세대임을 확인한 뒤 명부를 게시한다. 공유 조회·기존 잠금 순서와 세대 구조는 보존한다. API 어댑터의 list_cars 등에서 이 함수를 같이 사용하는 점을 고려해야 하며, 단순히 호출 한 줄을 삭제하는 방식은 피한다.

수정 후 확인: 정상 칸 변경은 반영, 미래/형식 오류 응답은 명부까지 불변, 초기화와 조회가 겹쳐도 이전 명부가 되살아나지 않음.

### F4. 메모 초안 보존 중 체크리스트는 갱신되지 않음

근거: `static/admin.html:141–159`.

브라우저에서 관리자 메모 초안을 입력한 뒤 다른 클라이언트가 첫 체크를 완료했다. 다음 load 결과는 다음과 같았다.

- 서버 체크 완료: true.
- 화면 JavaScript items의 체크 완료: true.
- 실제 체크박스 checked: false.
- 미저장 메모 초안: 보존됨.

초안/포커스를 지키는 조기 반환 분기는 보고서 문장·카운터·차량 등만 갱신하고 체크리스트는 갱신하지 않는다. 메모를 보존하는 설계는 정상이다. 갱신 대상을 빠뜨린 것이 문제다.

최소 수정 방향: textarea 노드는 보존하면서 체크리스트의 상태·완료 시각·수정 가능 여부를 별도로 갱신한다. 기존 revision 충돌 검사와 IME/커서 보존을 유지한다. 이번 재현은 화면 불일치이며 서버 체크 기록이 유실된 것은 아니다.

### F5. 혼잡 응답 뒤 확인 버튼이 복구되지 않음

근거: `engine.py:338–348`, `http_router.py:118–131`, `static/index.html:216–224,369–373`.

현재 결제 확인 응답을 화면에 적용하고, 실제 busy_response() 반환값을 같은 runtime/state 순서로 적용한 뒤 다음 updates 응답을 적용했다.

1. 기존 버튼: confirm_yes / confirm_no.
2. 혼잡 응답: 빈 Session에서 만든 idle/unselected/default chips.
3. 서버에는 기존 결제 확인 pending이 그대로 남음.
4. 다음 poll은 chips=null이어서 확인 버튼을 복원하지 않음.

실제 Chromium에서도 이 순서대로 확인 버튼이 사라졌다. 차량 표시도 혼잡 직후 ‘선택 전’으로 바뀌며 다음 poll의 실제 차량 상태로 돌아왔다. 서버에서 차량 선택이 삭제되거나 미승인 결제가 실행된 것은 아니다. 텍스트로 다시 응답할 수 있어 영구 프리징이라고 부르지 않는다.

조건: 혼잡 응답은 임베디드 입장 제한에서 사용되고, 현재 리치 UI처럼 상태 필드를 반영하는 소비자가 있어야 한다. 현재 팀 ChatPanel의 text-only 사용에서는 같은 상태 표시 문제가 직접 드러나지 않는다. 브라우저 검사는 실제 과부하를 만들지 않고 함수의 실제 응답을 UI에 적용해 이 경계를 확인했다.

최소 수정 방향: 클라이언트가 meta.busy 응답을 안내 메시지로 처리하되 기존 세션 표시/확인 상태는 덮지 않도록 한다. 서버의 입장 제한·결제 직렬화·재전송 구조를 바꾸지 않아도 보완할 수 있다.

### F6. 시간 예산 밖의 DNS와 결제 슬롯 대기

근거: `transport.py:14–45,60–62`, `engine.py:549–560`.

#### DNS

지정 timeout 20ms에서 합성 DNS 해석을 120ms 지연시킨 결과 반환까지 **124.4 ms**가 걸렸다. 최종 예외는 TimeoutError였지만 호출자는 지정 시간에 복귀하지 못했다. 타이머는 연결 후 설치되며 `getaddrinfo()` 대기는 별도 제한하지 않는다. 기존 검사는 DNS의 즉시 실패를 다루고 느린 해석은 다루지 않았다.

기본 BACKEND_BASE_URL의 숫자 루프백 주소에서는 이 DNS 지연 조건의 가능성이 낮다. 호스트명·DNS 장애를 쓰는 배치에서의 위험으로 분류한다. 실제 운영 DNS 장애나 수초 프리징을 측정한 것은 아니다.

#### 결제 예약

다른 결제가 슬롯을 차지한 상태에서 대기 요청의 예산을 30ms로 두었다. **100ms가 지나도 대기가 끝나지 않았고**, 테스트가 슬롯을 해제한 뒤 약 100.9 ms에 반환했다. 조건 변수 wait_for에 timeout/남은 예산 확인이 없다.

슬롯 해제 후에는 만료된 외부 조회 예산이 적용되어 결제를 보내지 않고 요금 미확인 안내로 끝났다. 확인한 것은 대기 시간의 비제한성이다. 실제로 결제가 중복되거나 무한 교착된 것은 아니다. 다만 앞선 처리 자체가 DNS 등으로 묶이면 다른 결제 요청도 예산 내 포기하지 못하는 연쇄가 가능하다.

최소 수정 방향: 결제 예약 대기는 남은 요청 예산 안에서만 기다리고, 시간 초과 시 새 동작 없이 반환한다. DNS 한도는 무제한 스레드 생성으로 우회하지 말고 실행 배치의 주소/해석 정책과 제한된 실행 자원을 포함해 별도 검증한다. 안정성 잠금/직렬화 구조를 바꾸기 전에 이 검증 계획을 적용한다.

### F7. 연결 검사에 옛 규격과 PASS 오판정이 남음

근거: `tests/check_backend.py:17–37`.

- 프로젝트 계약에서 허용되는 경보/요금 unavailable 반환을 주었는데 검사 출력은 PASS 경보·PASS 요금, 종료 코드는 0이었다.
- 현재 유효한 차량 27은 ‘차량 번호는 01~24입니다’와 종료 코드 2로 거절됐다. 런타임 규격은 두 자리 10~99다.

전자는 공개 어댑터 결과 계약에 통과하는 합성 반환값으로 검사했다. 실제 운영 서버가 내려간 채 PASS였다고 주장하지 않는다. 후자는 현재 normalize_car_id('27')의 유효 판정과 도구 판정의 불일치다.

최소 수정 방향: stale 외에 unavailable/error/conflict도 연결 성공과 구분하고, 차량 검증은 공용 normalize_car_id를 사용한다. 이전 보고서의 리허설 미실행 종료 코드 0은 선택 검사 정책일 수 있으나, 이 도구의 unavailable을 PASS로 출력하는 것은 별도 문제다.

### F8. 주차장별 기본 시간이 다른 정책의 요금표

근거: `templates.py:97–105`, `adapters.py:687–699`.

유효한 A 정책은 기본 30분/1,000원, B는 기본 60분/2,000원으로 주었다. 전체 요금표는 다음과 같았다.

> 주차장마다 요금이 달라요. 개발원주차장 기본 1,000원 / 부산역주차장 기본 2,000원 (기본 30분).

첫 정책의 기본 시간을 전체에 한 번 붙여 B의 60분이 드러나지 않는다. 현재 기본 설정이 모두 30분일 때는 이 조건이 생기지 않는다. 서버의 금액 계산이나 실제 결제 금액이 잘못됐다는 뜻도 아니다.

최소 수정 방향: 기본 시간이 같으면 기존 문구를 유지하고, 다른 경우에만 각 정책에 해당 시간을 붙인다. 기존 기대값 변경 없이 조건부 표시를 보완할 수 있다.
