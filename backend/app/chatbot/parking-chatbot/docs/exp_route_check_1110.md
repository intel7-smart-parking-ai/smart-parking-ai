# 가로채기 확인 — 규칙 + 애매하면 AI (11/10 저녁 실험 기록)

> 11/10 로컬 실험 기록(당시 기준 `d47ab2a`). 11/11 검증 뒤 `feature/KAN-9-chatbot-route-check`로 올렸다 → [exp_structure_review_1111.md](exp_structure_review_1111.md) · 기본 꺼짐(`LLM_ROUTE_CHECK=0`)

## 무엇을 하는가

규칙은 자기가 틀린 줄 모른다. 규칙이 "모르겠다"고 한 문장은 지금도 대화 AI로 가지만, 규칙이 **확신하고 잘못 읽은** 문장은 AI를 거치지 않는다.
규칙이 대화 AI를 건너뛰고 직접 맡으려는 순간에만, AI에게 "이 문장이 정말 그 처리인가?"를 짧게 묻는다(`chatbot/route_check.py`, 지시문 `prompts/route_check.md`).

| 대상(규칙이 직접 맡는 처리) | 걸리는 곳 |
|---|---|
| 목적지 설정 | `engine.py` (set_destination) |
| 내 차 찾기(차량 번호가 필요한 단일 조회) | `conversation_turn.reply_to` |
| 혼잡 예측 | `forecast_chat.answer` (되물은 뒤 이어 받은 답은 제외) |
| 충전 현황 카드 | `engine.py` (charging_status) |

- 맞다 → 규칙대로. 아니다 → 가로채지 않고 대화 AI로.
- 꺼짐·키 없음·1.5초 초과·형식 오류 → 규칙대로(지금과 같은 동작).
- 결제 승인·연기 신고·관리자 호출·Lv2 경보 중에는 확인하지 않는다.

## 측정 결과

### 1) 판단 정확도 (`tools/route_check_bench.py`, 지시문 예시와 겹치지 않는 문장)

| | Haiku 5.5 | gemma-4-26b |
|---|---|---|
| 잘못 읽은 문장을 잡음(19개) | 18 | 18 |
| 맞는 문장을 잘못 뒤집음(26개) | 1 | 0 |
| 처음 보는 문장 10개(지시문 다듬은 뒤 추가) | 9 맞음 | 10 맞음 |
| 응답 시간 중앙값 / 90% | 1.19초 / 1.34초 | 0.74초 / 0.95초 |

첫 실행(지시문 다듬기 전)도 두 모델 모두 18/19, 1/26이었다. 다듬은 것: 추론 끔(Haiku가 답 없이 토큰을 다 쓰던 문제), 주차장 기호(A~D) 목록, 혼잡 예측·충전 현황 기준 한 줄씩.

### 2) 기존 질문지 92턴 — 켠 것과 끈 것 (gemma)

| 질문지 | 끔 AI 답 | 켬 AI 답 |
|---|---|---|
| 꼬는 질문 45턴 | 41 | 40 |
| 화면 사례 24턴 | 22 | 22 |
| 오류 화면·봇 질문 23턴 | 12 | 12 |

- 확인이 돈 턴: 7개(전부 규칙이 맡는 턴). 판단은 '맞다' 5개, 1.5초 초과로 건너뜀 2개. **답은 7개 모두 그대로**, 응답만 0.7~1.5초 늦어짐.
- 꼬는 질문 1턴 차이('어디 대면 돼?')는 확인이 돌지 않은 턴으로, 대화 AI의 우연한 시간 초과.
- 기존 질문지의 오분류는 이미 규칙으로 고쳤기 때문에 여기서는 차이가 나지 않는 것이 정상.

### 3) 지금 규칙이 잘못 가로채는 새 문장 12개 (`tests/dialogs/exp_unseen_misroute.json`, gemma)

규칙을 고치는 데 쓰지 않은 문장. 12개 중 11개를 현재 규칙이 잘못 가로챈다(예: '공항 주차장으로 가는 셔틀 있어?' → "목적지로 정했어요").

| | 끔 | 켬 |
|---|---|---|
| AI 답 | 1 | 8 |
| 엉뚱한 규칙 답·이해 못 함 | 11 | 3 |

- 11개 중 10개를 '아니다'로 걸렀다. 8개가 AI 답, 1개는 AI 시간 초과 뒤 규칙이 주차장을 되물음, 1개('차량 번호 스티커는 어디서 받아?')는 여전히 '이해하지 못했어요'.
- 1개('충전 현황판은 어디에 있어?')는 '맞다'로 판단해 충전 카드 그대로(문장 자체가 애매).
- 구해 낸 턴의 응답 시간은 2.5~4.3초(확인 0.6~1.3초 + 대화 AI).

## 구조 비교 — 현업 서비스 챗봇은 어떻게 하는가 (11/10 밤 조사)

| 서비스·자료 | 구조 | 우리와 비교 |
|---|---|---|
| Rasa CALM | AI가 문장을 '명령(흐름 시작·값 채우기)'으로 바꾸고, 업무 흐름은 코드가 정해진 대로 실행 | 업무 흐름을 코드가 쥐는 점은 같다. 다른 점: 저쪽은 매 턴 AI가 먼저 읽는다(우리는 규칙이 먼저) |
| Google Dialogflow CX | 정해진 흐름 + 흐름 밖 문장은 생성형 대체 답(generative fallback), 또는 전부 생성형(playbook) | 우리의 '규칙 + 대화 AI'와 같은 혼합형. 생성형은 안전망으로 아껴 쓰라고 권한다 |
| Intercom Fin | 질문 다듬기 → 자료 찾기 → 순위 → 근거 있는 답 → 검증. 확신이 낮으면 되묻고, 안전 기준에 못 미치면 사람에게 | 우리의 '미리 조회 → 답 → 근거 검사 → 고쳐 쓰기 → 규칙 답'과 같은 뼈대 |
| OpenAI Agents SDK | 입력 가드레일을 에이전트와 **동시에** 실행(기본). 걸리면 에이전트를 중단. 토큰 낭비가 싫으면 차례로 실행 선택 | 가로채기 확인이 바로 이 '입력 가드레일' 자리. 우리는 차례로 돌려 0.7~1.5초를 더 썼다 |
| Anthropic 「Building effective agents」 | 단순한 조합 패턴 권장: 라우팅(쉬운 것은 작은 모델), 병렬 실행 | 확인 전용 모델(LLM_ROUTE_CHECK_MODEL)을 따로 둘 수 있게 해 둔 것과 같은 방향 |
| 임베딩 라우터(semantic router 등) | 확신이 높으면 빠른 길(수 ms), 낮으면 AI에게. 기준 없이 쓰면 애매한 문장을 자신 있게 틀린다 | 우리 규칙이 바로 '기준 없는 빠른 길'이었다 → 확신 기준을 넣음(빠른 길) |

결론: **구조는 유지한다.** 현업 혼합형과 뼈대가 같고, 다른 것은 '확인을 어떻게 싸게 하느냐'뿐이다. 그래서 두 가지만 가져왔다.

1. **빠른 길**(`LLM_ROUTE_CHECK_FAST`, 기본 켬) — 문장이 그 처리의 말(주차장 이름·요청 동사·조사)로만 되어 있으면 확인을 생략한다.
   모르는 낱말이 하나라도 있으면 확인한다. 낱말 목록이 모자라도 틀린 답이 아니라 확인 한 번이 늘 뿐이다(`route_check.sure`).
2. **동시 실행**(`LLM_ROUTE_CHECK_PARALLEL`, 기본 끔) — 확인을 기다리지 않고 대화 AI를 함께 시작한다.
   '아니다'면 이미 달리던 대화 AI 답을 쓰고, '맞다'(또는 실패·시간 초과)면 대화 AI를 취소하고 규칙으로 간다.
   대화 AI는 같은 실행 루프 안에서 취소하므로 조회가 뒤에 남지 않는다. 확인은 제한 시간이 있는 조회 한 번짜리 스레드다.

가져오지 않은 것: AI가 매 턴 먼저 읽는 구조(CALM식) — 규칙이 바로 답하던 턴(결제·신고·목적지)까지 모델을 기다리게 되고, 모델이 죽으면 규칙 길을 따로 또 유지해야 한다. 동결(11/12) 전에 바꿀 구조가 아니다. 임베딩 라우터 — 예문 수집·기준값 조정·모델 파일 배포가 필요하다.

| 문장 묶음 | 맞는 문장 중 확인 생략 | 잘못 읽은 문장 중 확인 생략(0이어야 함) |
|---|---|---|

| 낱말 목록을 쓴 뒤 처음 만든 문장 30개 | 10 / 10 | 0 / 20 |

### 5) 차례로 vs 동시에 — 새 문장 12개 (gemma, 같은 시각에 연달아 실행)

| | 차례로(빠른 길 끔) | 동시에(빠른 길 켬) |
|---|---|---|
| AI 답 | 6 | 8 |
| 평균 / 최대 응답 시간 | 2.8초 / 6.9초 | 2.3초 / 5.3초 |
| 구해 낸 턴에서 확인 때문에 늘어난 시간(응답 시간 − 대화 AI 시간, 6턴 평균) | 약 1.0초 | 약 0.0초 |
| 규칙이 맞다고 나온 턴(U07) | 0.7초 | 0.8초 |

- 이날 밤 gemma 확인 호출이 느렸다(0.7~1.5초, 제한 1.5초를 넘긴 것이 차례로 4턴·동시에 1턴). 제한을 넘기면 두 방식 모두 규칙대로 간다(U11은 두 번 다 충전 카드).
- AI 답 수 차이(6 → 8)는 구조가 아니라 그 시간 초과 횟수 차이다. 구조가 바꾼 것은 **구해 낸 턴의 대기 시간**이다.
- U05·U10은 확인이 '아니다'로 걸러 대화 AI까지 갔지만 답이 되묻기·'이해하지 못했어요'였다(자료에 없는 내용). 구조가 아니라 대화 AI·자료 쪽 과제.

### 6) 기존 질문지 86턴 — 빠른 길 + 동시 실행 켬 (gemma)

| 질문지 | AI 답 | 평균 / 최대 |
|---|---|---|
| 꼬는 질문 45턴 | 41 (끔과 같음) | 2.0초 / 4.6초 |
| 화면 사례 18턴 | 17 | 2.0초 / 5.1초 |
| 오류 화면·봇 질문 23턴 | 12 (끔과 같음) | 1.1초 / 4.8초 |

- 확인 대상 5턴 중 3턴은 빠른 길로 **확인 없이 0.0초**('전기차 충전 현황', '개발원 주차장으로 안내해줘', '내일 아침에 가면 신세계 자리 있어?').
- 나머지 2턴은 확인 1.3초(맞다)·1.5초(제한 초과) 뒤 규칙 답. 답은 5턴 모두 규칙 그대로.
- 전체 테스트 924개 통과(실험 테스트 43개 포함, 2개 건너뜀).

남은 것: 동시 사용 중 측정 없음. 동시 실행은 '규칙이 맞다'로 끝난 턴마다 대화 AI 호출 1번(턴 한도 1회 포함)을 버린다 — 빠른 길이 그런 턴을 대부분 먼저 걸러 주지만, 한도(세션당 분 12회)에 주는 영향은 재지 않았다. 확인 제한 시간(1.5초)은 차례 방식 기준 그대로 뒀다.

## 판단

- **얻는 것**: 아직 발견하지 못한 오분류를 대부분 걸러 낸다. 규칙을 문장마다 고치지 않아도 된다.
- **잃는 것**: 규칙이 맡는 턴(전체의 약 8%)이 0.7~1.5초 느려진다. 맞는 요청을 잘못 뒤집을 가능성이 낮지만 있다(26개 중 0~1개).
- **안전**: 실패·시간 초과는 규칙대로. 결제·안전 흐름은 대상이 아님. 꺼 두면 코드 경로가 지금과 같다(테스트 881개 그대로 통과).
- **남은 확인**: 실제 시연 서버 구성, 동시 사용 시 확인 호출이 모델 자리·시간 예산에 주는 영향, 사람이 본 답 품질.
- 시연에 켤지는 11/11 점검 뒤 PM 결정 사항.
