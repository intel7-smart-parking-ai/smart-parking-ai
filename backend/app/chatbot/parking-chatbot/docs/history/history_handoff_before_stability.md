# 주차장 챗봇 수정 인계서 — 최초 원본 대비 최종 수정본

작성일: 2026-11-01  
대상: `parking-chatbot.zip` 최초 제공본 → 이번 대화에서 전달한 최종 수정본  
용도: Claude가 변경 배경·코드 구조·프로토콜 변경·남은 연동 작업을 파악하고 개발을 이어가기 위한 문서

## 1. 사용자 요청과 수정 방향

처음 요청은 기존 주차장 프로젝트의 방향을 이해하고 **필요한 코드 검토와 최적화만 수행**하는 것이었다. 이후 사용자가 로직 충돌과 오작동을 유발하는 구조까지 개선하고, 기능 추가에 대응할 수 있는 방향으로 확장해 달라고 요청하여 구조 개선을 진행했다.

수정 원칙은 다음과 같다.

1. 문장 분류의 정답률과 실제 업무 흐름의 안정성을 구분한다.
2. 조회와 상태를 변경하는 작업을 분리한다. 결제·관리자 호출은 실행 내용을 확인한 뒤 처리한다.
3. 네트워크 실패를 작업 실패로 단정하지 않는다. 중복 실행과 응답 유실을 별도로 처리한다.
4. 최신 상태·캐시·조회 불가를 구분한다. 오래된 정보로 결제를 진행하지 않는다.
5. 기능을 추가할 때 대화 상태·알림·대기열·외부 데이터 검증을 각각 확장할 수 있도록 나눈다.
6. 실제 프로젝트에 없는 데이터나 장치 동작을 구현 완료로 간주하지 않는다.

기존 Python 엔진, 규칙 우선 파서, 선택적 LLM 분류, 템플릿 답변, mock/API 연결층, 두 종류의 서버와 사용자·관리자 HTML이라는 기본 구성을 유지했다. 외부 프레임워크를 새로 도입하거나 전체 프로젝트를 교체하지 않았다.

## 3. 대화 상태와 실행 작업 구조

새 `chatbot/state.py`의 Session/Pending/Flow로 상태를 표현한다.

| 상태 | 의미 |
|---|---|
| `idle` | 보류 작업 없음 |
| `ask_vehicle` | 차량번호 입력 대기 |
| `confirm_vehicle` | 후보 차량 확인 대기 |
| `confirm_action` | 결제·관리자 호출 내용 확인 대기 |

Pending에는 작업 의도, 매개변수, 차량번호, 확인 토큰, 만료 시각을 함께 저장한다.

결제 흐름 예시:

```text
7번 결제 요청
→ 07번 차량 확인
→ 현재 요금 조회
→ 1,500원 모의 결제 여부 확인
→ 확인 토큰·유효기간·차량·현재 금액·입차 기록 재검사
→ 모의 결제 요청
→ 결과 전달
```

금액이나 입차 기록이 달라지면 새로운 내용을 보여주고 다시 확인한다. 취소·만료·다른 기능 요청으로 이전 작업을 정리한다. 미확인 발화가 결제·호출 확인 사이에 끼는 경우에도 실행 확인을 계속 유지하지 않도록 했다.

관리자 호출도 확인 후 관리자 화면에 문의를 등록한다. 등록 자체를 담당자가 실제로 읽거나 응답했다는 의미로 사용하면 안 된다.

## 4. 중복 요청과 결제 불확실성

### 챗봇 요청 재전송

- 클라이언트는 새 요청마다 request_id를 생성한다.
- 응답을 받지 못한 요청을 다시 확인할 때는 같은 ID와 같은 내용을 보낸다.
- 서버는 세션에 저장한 기존 응답을 반환한다.
- 같은 ID에 다른 내용을 보내면 충돌로 거부한다.
- 기록 범위는 10분 이내, 세션당 최근 100건이다.
- 화면에 **같은 요청 다시 확인** 버튼을 추가했다.

### 결제 작업

- 현재 차량·입차 기록·금액에 기반한 작업 키를 하위 API에 Idempotency-Key로 전달한다.
- expected_amount와 entered_at도 전달한다.
- 프로세스 내 결제 실행을 직렬화한다.
- 요청 결과가 불확실한 입차 건은 다른 세션에서도 추가 실행을 중지한다.
- 결제를 자동 재시도하지 않는다.

**보장 범위:** 현재 앱의 메모리 및 단일 프로세스 안에서의 처리다. 실제 결제 서버는 금액/입차 검사와 중복 키 기록을 DB 트랜잭션으로 구현해야 한다. 프로세스 재시작을 넘는 중복 방지를 이 코드만으로 완성했다고 해석하면 안 된다.

## 5. 알림과 대기열

### 수신 확인 큐

새 `notifications.py`에서 세션별 event_id 순번을 관리한다.

1. 서버가 알림을 큐에 넣는다.
2. 클라이언트가 messages를 받아 화면에 표시한다.
3. 화면 반영 후 cursor를 갱신한다.
4. 다음 조회의 cursor가 이전 메시지 수신 확인 역할을 한다.
5. 수신 확인 전에는 같은 event_id로 재전송하고, 화면은 ID로 중복 표시를 막는다.

큐는 세션당 최대 100건이며 일반 알림 기본 유효기간은 30분이다. 누락·만료를 감지하면 resync_required를 반환한다. 경보 안내 집계는 알림 생성 수가 아니라 수신 확인한 세션 수로 변경했다.

이는 메모리 큐다. 영속 DB와 같은 트랜잭션에 묶인 transactional outbox를 구현한 것은 아니다.

### 대기 정책

새 `waitlist.py`에서 waiting/offered/notified/cancelled/expired 상태를 관리한다.

- 대기 등록: 30분 유효.
- 알림 배정: 60초 유효.
- 이미 배정한 빈자리는 같은 배정 유효기간 동안 중복 배정하지 않는다.
- 배정 유효기간이 끝나고 빈자리가 계속 남아 있으면 다음 대기자에게 안내할 수 있다.
- 대기 상태 조회와 알림 취소를 지원한다.
- 대기 주차장을 변경하면 새 등록으로 순번을 받는다.

**대기 알림은 실제 자리 예약이 아니다.** 폴링 사이에 입차·출차가 상쇄되는 상황까지 정확히 추적하려면 실제 입출차 이벤트 연동이 필요하다.

## 6. 보고서와 관리자 동시 수정

- 보고서에 revision을 추가했다.
- 변경 요청은 화면이 읽었던 expected_revision을 함께 보낸다.
- 다른 변경이 있으면 409로 거부하고 최신 보고서를 다시 확인하도록 한다.
- 체크는 toggle 대신 `{index, checked}`를 보낸다. 같은 최종 상태의 재전송은 표시를 되돌리지 않는다.
- 확정 요청에 notes를 함께 전달하여 메모 저장과 확정을 하나의 변경으로 처리한다.
- 확정된 보고서는 수정하지 않는다.
- 저장 실패·충돌 시 미저장 메모를 화면에 유지한다.
- **최신 보고서 확인** 버튼을 추가했다.
- runtime_id를 검사하여 초기화 전 보고서 ID와 초기화 후 재사용된 ID를 혼동하지 않도록 했다.

경보 위치 변경으로 기존 보고서를 종료하는 것은 이전 위치에서 실제 경보가 해제됐다는 뜻이 아니다. 관련 경과 문구에 이를 명시했다.

## 7. 데이터 연결과 검증

새 `contracts.py`에서 엔진에 들어올 데이터의 최소 계약을 검사한다.

- 빈자리는 0~total 범위의 정수.
- 요금 값은 0 이상 정수, paid는 boolean.
- 차량 위치·경보 필수 필드 검사.
- 시각은 시간대가 있는 ISO 형식.
- 등록된 주차장인지 검사.
- 모르는 결제 status를 차량 없음이나 성공으로 추정하지 않음.

기본 데이터 갱신 허용시간과 장애 시 캐시 허용시간은 각각 30초다. 결제 준비·실행에는 오래된 정보를 사용하지 않는다. 차량 정보의 None 결과, 결제 후 요금 정보, 전체 초기화 시 캐시를 적절히 폐기한다.

팀 API 연결 설정:

| 위치 | 역할 |
|---|---|
| `chatbot/api_paths.json` | 각 기능의 API 경로 |
| `.env`의 DATA_SOURCE | mock/api 선택 |
| BACKEND_BASE_URL | 팀 백엔드 주소 |
| BACKEND_TOKEN | 선택 Bearer 인증 |
| `ApiAdapter` | 실제 응답 필드 → 내부 데이터 형식 변환 |
| LLM_PROVIDER / LLM_MODEL / 해당 API 키 | 선택적 문장 분류기 설정 |

LLM 키와 주차장 데이터 인증은 별개다. 실제 API 명세·응답 예시·최종 모형 구성이 제공되면 연결 코드를 맞추는 작업을 이어갈 수 있다.

LLM은 기존처럼 규칙이 모르는 문장의 의도 분류에만 사용한다. 숫자나 답변을 생성하지 않는다. 반환 형식과 의도·params를 검사하고 문장에서 직접 추출한 값을 우선한다. LLM이 확인 동의를 대신 생성하도록 허용하지 않는다.

## 8. 프런트엔드/API 호환성 변경 — 필수 인계 사항

기존 팀 화면을 따로 연결한다면 아래 변경을 반영해야 한다. 수정본의 두 HTML에는 이미 반영했다.

## 12. 현재 남아 있는 범위와 다음 개발 시 확인점

- 상태는 단일 프로세스 메모리 저장이다. 재시작 후 기록·알림·중복 방지를 유지하려면 팀 DB 저장 및 트랜잭션을 연결해야 한다.
- 활성 경보 위치는 한 곳이다. 여러 위치 동시 경보는 아직 구현하지 않았다.
- 기본 모형은 A/B/C 각 8칸, 차량 01~24다. 최종 주차장 수·배치에 맞춰 설정과 시연 데이터를 맞춘다.
- 근접 차량은 칸 번호 차이로 계산한다. 실제 지도상의 거리 계산이 아니다.
- 실제 환불·차단기 제어·외부 메시지 발송은 구현하지 않았다. 기존 템플릿/카드의 자동 출차 관련 문구를 실제 장치 제어 완료로 해석하지 말아야 한다.
- 관리자·시연 API 인증은 아직 별도 구현하지 않았다. BACKEND_TOKEN은 앱이 팀 백엔드에 접속할 때의 인증이다.
- 입차 식별자는 현재 entered_at 기반이다. 팀 DB에 고유 visit_id가 있다면 연결 시 그것을 사용하는 편이 적절하다.
- 결과 불확실 결제는 보수적으로 추가 실행을 막는다. 상태 조회·관리자 확인으로 해소하는 실제 업무 경로를 팀 API에 맞춰 완성해야 한다.
- 마지막 값이 오래되었다는 판정은 수신 갱신 시각과 로컬 캐시 시간을 사용한다. 필드 형식이 맞다는 검사만으로 데이터의 현실 정확성이 보장되는 것은 아니다.

새 조회 기능은 파서/칩과 조회 처리 함수에, 새 실행 기능은 confirm_action과 실행 전 재검사에 연결한다. 외부 데이터 검사는 contracts, 알림 전달은 notifications, 대기 정책은 waitlist에 두어 대화 분기 안에 모두 섞지 않는 방향으로 이어간다.
