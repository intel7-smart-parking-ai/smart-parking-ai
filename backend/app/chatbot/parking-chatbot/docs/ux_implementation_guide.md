# EPIC 06 사용자 경험 개선 구현·시연 가이드

작성일: 2026-11-01

## 1. 이번 적용 범위

사용자가 승인한 우선 묶음 1~3번을 구현했다.

1. 차량 확인 후 항상 보이는 내 차량 카드와 차량 변경.
2. 관리자 즉시 호출과 접수 → 확인 중 → 처리 완료 → 사용자 해결 확인/미해결 재개.
3. 상태 알림에서 현재 상태 확인·해결 여부 응답 등 바로 행동하기.

주차 정보 오류 신고는 후순위 후보이며 이번 버전에 포함하지 않았다. 기존 결제 확인·요청 중복 방지·알림 수신 확인·보고서 충돌 처리는 유지한다.

## 2. 구현 방식 비교와 선택 이유

아래는 공식 문서로 확인한 기능과 현재 프로젝트에 대한 설계 판단을 구분한 비교다.

| 고려 요소 | 대안 | 이번 선택 및 이유 |
|---|---|---|
| 화면 구성 | 별도 챗봇 재작성 / 기존 HTML 링크 / 같은 출처 iframe | 기존 HTML 확장. 현재 통신·재시도 처리를 재사용하며 EPIC07에서 링크/iframe으로 연결 가능 |
| 상태 전달 | 2초 폴링 / SSE / WebSocket | 기존 폴링+cursor 유지. 연결 종류를 늘리지 않고 장애 복구 경로를 검증 |
| 내 차량 카드 | 매번 위치·요금 동시 조회 / 위치만 갱신 / 브라우저 저장값만 표시 | 서버 세션의 차량과 위치만 표시. 요금은 버튼으로 조회하여 추가 호출 억제 |
| 문의 처리 | 자동 시간 경과로 진행 / 관리자 실제 조작 / 외부 상담 도구 | 관리자 실제 조작. 시간만으로 담당자가 읽었다고 표시하지 않음 |
| 문의 분류·요약 | LLM 매번 호출 / 구조화 데이터·템플릿 | 기존 구조화 요약 사용. 추가 비용·모델 응답 대기 없음 |
| 중복 호출 | 요청 ID만 비교 / 미처리 문의도 통합 | 둘 다 사용. 다른 request_id로 반복 클릭해도 같은 세션·차량의 열린 문의 재사용 |
| 미해결 피드백 | 새 문의 생성 / 같은 문의 재개 | 기존 문의를 확인 중으로 되돌림. 이력과 담당자 맥락 유지 |
| 상태 저장 | 메모리 / 별도 SQLite / 팀 DB | 현재 단일 프로세스 메모리 모델 유지. 팀 DB 계약 전 별도 DB를 중복 구축하지 않음 |

SSE는 서버에서 클라이언트로 전달하는 단방향 연결이고, FastAPI는 WebSocket을 지원한다. 이는 대안의 존재를 확인한 것이며, 이번 작은 모형 시연에서 이들로 바꿔야 한다는 근거는 아니다.

## 3. 내 차량 카드

- 서버가 chat/updates 응답의 vehicle_context에 상태를 포함한다.
- unselected: 차량 미선택.
- parked: 확인된 위치 표시.
- stale: 마지막 위치임을 명시.
- not_found: 입차 기록 없음. 출차 후 예전 위치를 정상 위치로 계속 표시하지 않음.
- unavailable: 위치 갱신 지연. 조회 실패를 출차 완료로 추정하지 않음.
- 위치 보기 / 요금 보기 / 차량 변경 버튼 제공.
- 차량 변경 시 기존 결제 확인을 취소하고 차량 선택 상태로 돌아감.
- 같은 탭의 새로고침은 sessionStorage 세션 ID로 현재 서버 세션을 다시 조회함.

위치 조회 결과와 고정 카드의 위치는 요청 범위 스냅숏을 공유하여 중복 조회를 줄였다. 세션이 없는 사용자의 폴링은 차량 위치를 조회하지 않는다. 선택한 사용자는 폴링 때 차량 위치 조회가 추가된다. 따라서 최초 원본 대비 조회 감소 수치만으로 모든 상황에서 호출이 줄었다고 주장하지 않는다.

## 4. 관리자 요청 상태와 알림

| 상태 | 의미 | 가능한 변경 |
|---|---|---|
| 접수 | 관리자 화면에 기록됨 | 관리자: 확인 중 또는 처리 완료 |
| 확인 중 | 관리자가 확인을 시작했거나 사용자가 미해결을 보고함 | 관리자: 처리 완료 |
| 처리 완료 | 관리자가 조치 완료로 표시 | 사용자: 해결됐어요 / 아직 안 돼요 |
| 해결 확인 | 사용자가 해결을 확인함 | 같은 문의의 상태 추가 변경 제한 |

관리자 호출은 Lv0/Lv1/Lv2 모두 확인 단계 없이 바로 등록한다. 호출 전 최신 정보 요약을 시도하며, 백엔드 실패가 있어도 미확인 항목을 표시하고 등록한다. 실제 외부 메시지 발송이나 담당자 열람을 보장하는 문구는 사용하지 않는다.

POST `/api/v1/chat/admin/calls/{id}/status`

```json
{"status":"확인 중","expected_revision":1,"runtime_id":"현재 서버 ID"}
```

- 오래된 revision이나 서버 runtime_id면 409.
- 같은 최종 상태의 재시도는 상태를 되돌리거나 새 알림을 생성하지 않음.
- 상태 변경과 알림 큐 삽입은 같은 프로세스 잠금 안에서 처리.
- 사용자에게는 본인 세션의 문의 알림만 전송.
- 피드백 버튼은 문의 ID·revision·행동을 포함하고 소유 세션/현재 상태를 재검사.
- 처리 완료 당시의 버튼을 나중에 다시 눌러도 현재 상태를 잘못 변경하지 않음.

서버와 사용자 탭은 기존 event_id/cursor 큐로 상태를 전달한다. 네트워크가 끊겨도 보관 기간 내 같은 이벤트를 재수신하고, 화면은 중복 표시를 제거한다. 앱을 닫은 동안의 OS 푸시는 구현 범위가 아니다.

## 5. 바로 행동할 수 있는 알림

- 빈자리 알림: 해당 주차장 현재 상태 보기. 자리를 예약했다고 표시하지 않음.
- 문의 처리 완료: 해결됐어요 / 아직 안 돼요.
- 모의 경보: 대피 안내 / 관리자 호출 등 기존 경보 행동 유지.
- 진행 중 결제 확인은 하단에서 유지하고, 알림 고유 행동은 메시지 안에도 표시.

알림의 당시 정보와 버튼 실행 시 현재 정보를 구별한다. 결제·피드백 등 상태 변경은 현재 차량/토큰/revision을 다시 확인한다.

## 6. 재현 시나리오와 수용 기준

| 시나리오 | 통과 기준 |
|---|---|
| 7번 차량 확인 후 새로고침 | 같은 세션의 07번 위치가 고정 카드에 복원 |
| 07번 출차 | 다음 정상 조회에서 입차 기록 없음 |
| 위치 조회 장애 | 기존 위치를 최신 위치라고 표시하지 않고 갱신 지연/마지막 정보 표시 |
| 결제 확인 중 차량 변경 | 이전 확인 버튼으로 결제 불가 |
| 모의 Lv2 경보 중 관리자 호출 | 추가 확인 없이 문의 1건 등록 |
| 다른 request_id로 20회 동시 호출 | 같은 세션·차량의 미처리 문의 1건 |
| 관리자 확인 시작/완료 | 사용자 폴링에 상태 알림 포함 |
| 알림 응답 유실 | 같은 이벤트 재전송, 화면 중복 없음 |
| 사용자가 아직 안 돼요 선택 | 같은 문의가 확인 중, 새 문의 생성 없음 |
| 다른 세션이 피드백 ID 추측 | 문의 상태 변경 없음 |
| 관리자 오래된 상태 버튼 | 충돌 또는 동일 상태 응답, 과거 상태로 잘못 변경하지 않음 |
| 이전 runtime의 관리자 요청 | 새 서버의 재사용 ID에 적용 불가 |

### 실행 결과

- 기존 질문: 36/36 통과.
- Python 자동 검사: 86/86 통과. FastAPI 검사 포함.
- Chromium 화면 검사: 15항목 통과. 기존 장애·충돌 12항목에 차량 고정/즉시 호출, 관리자 진행/미해결 재개, 새로고침/출차/차량 변경 시나리오 추가.
- 브라우저 검사 중 경보 해제 알림이 문의 알림 뒤에 표시되는 정상 순서를 확인했다. 테스트가 '마지막 말풍선만 문의여야 함'이라고 가정하던 것을 수정하고, 실제 문의 알림 도착 여부를 검사하도록 바로잡았다.

검증 범위는 모의 데이터와 로컬 서버다. 실서버 응답 속도, 여러 기종의 모바일 앱 내 브라우저, 실제 카메라·차단기·LLM 호출까지 검증했다는 의미는 아니다.

## 7. 시연 운영 절차

### 준비

1. 시연 PC에서 압축을 풀고 Python 3.10 이상으로 실행한다.
2. 기본 mock 시연은 API 키 없이 `python server_dev.py`로 실행한다.
3. 사용자와 관리자 탭을 같은 서버에서 연다. 기본 포트 8080.
4. 시연 전 전체 초기화 후 07번 차량과 B 대기 등록을 연습한다.
5. 시연 PC의 절전·네트워크 변경 없이 같은 탭을 사용한다.

### 권장 3분 시연

1. 7번 차량 위치 조회 → 차량 확인 → 고정 카드와 위치 보기.
2. 관리자 호출 → 관리자 탭에서 확인 시작 → 사용자 상태 알림.
3. 관리자 처리 완료 → 사용자 아직 안 돼요 → 같은 문의 재개 → 다시 완료 → 해결됐어요.
4. B 대기 등록 → 테스트 도구에서 12번 출차 → 빈자리 알림 → B 현재 상태 보기.
5. 마지막에 모의 Lv2 경보 → 관리자 즉시 호출. 실제 화재가 아닌 LED 모의 상황임을 설명.

### 실패 시 복구

- 응답이 없으면 '같은 요청 다시 확인'을 사용. 결제 버튼을 새 요청으로 반복하지 않음.
- 관리자 충돌이면 최신 목록을 불러와 현재 상태 확인 후 변경.
- 서버를 재시작하면 메모리 상태가 사라짐. 사용자/관리자 화면을 갱신하고 초기 데이터로 다시 시작.
- 실서버 장애 때 mock 데이터로 자동 대체하지 않음. 시연 전에 mock/실연동 모드를 명시적으로 선택.
- 실연동은 먼저 `python tests/check_backend.py 07`로 조회 계약을 확인.

## 8. 다음 연결 작업

팀 DB 연결 시 문의 상태·revision·사용자 세션 관계와 알림 이벤트를 함께 저장해야 재시작 후에도 이어갈 수 있다. 현재 메모리 잠금의 원자성을 DB 트랜잭션으로 옮기는 작업이 필요하다.

사용자 웹은 같은 출처 링크/iframe으로 기존 화면을 재사용하는 방안을 우선 검토한다. 다른 출처 iframe은 인증·세션·프레이밍 정책을 실제 배포 환경에서 확인해야 한다. 서버 주소와 주차장 배치를 제공받으면 연결층과 데이터 설정을 맞출 수 있다.

현재 관리자 API는 신뢰된 시연 네트워크 전제다. 외부 공개 운영 전에는 팀의 관리자 인증과 접근 제어를 연결해야 한다. 차량번호는 신원 인증 수단이 아니다.
