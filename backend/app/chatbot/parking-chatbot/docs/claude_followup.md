# Claude 재검토 요청 — 이전 검토 이후 변경 사항

작성일: 2026-11-01  
기준점: Claude가 GPT 작업본을 검토하여 '기준 코드로 채택하되 관리자 호출 확인 제거·기존 화면 재사용'을 추천한 시점  
대상: 함께 제공하는 최신 `parking-chatbot.zip`

## 1. 현재 결정과 수정 방향

기존 구조를 기준으로 유지하면서, 사용자가 다시 입력하거나 상태를 다시 물어야 하는 불편을 줄이는 방향으로 수정했다.

- 규칙 우선 처리, LLM은 미인식 문장의 분류 보조, 답변은 템플릿이라는 원칙 유지.
- 결제 확인·중복 요청 방지·알림 재전송·관리자 동시 수정 충돌 처리는 유지.
- 2주 모형 프로젝트의 시연·안정화 범위에서 기존 데이터와 UI를 재사용.
- 슈퍼바이저/워커 또는 검토 AI를 추가하는 것은 **추후 검토**로 결정. 이번 코드에는 추가하지 않음.
- 현재 LLM은 여전히 기본 비활성(`LLM_PROVIDER=none`). OpenAI/Anthropic 단일 분류기 연결 코드는 있으며, 실제 모델·키는 연결하지 않은 상태.

## 2. Claude 추천에 대한 반영

### 관리자 호출 확인 제거 — 적용 완료

`h_call_admin`이 작업 확인 상태에 들어가지 않고 바로 등록하도록 변경했다. Lv0/Lv1/Lv2 모두 즉시 등록한다. 진행 중 결제 확인 등 다른 보류 작업은 기존 분기에서 정리한다.

단순 요청 재전송뿐 아니라 **다른 request_id로 반복 클릭해도 같은 세션·차량의 접수/확인 중 문의를 재사용**하도록 했다. 서로 다른 사용자의 정상 호출은 별도 등록되며 ID 잠금은 유지한다.

응답 문구는 다음과 같다.

> 관리자에게 확인을 요청했어요. 차량 정보와 최근 문의를 요약해 관리자 화면에 함께 등록했어요.

Claude가 제안한 장점 표현은 살렸지만, 담당자가 실제로 읽거나 외부 알림을 받았다는 확인은 없으므로 '다시 설명하지 않아도 된다'고 단정하지 않았다.

### 기존 HTML 재사용 — 준비 방향 유지, 팀 합의는 미완료

사용자·관리자 HTML을 직접 개선했다. EPIC07/08에서 같은 출처 링크 또는 iframe으로 재사용하는 방안을 가이드에 정리했다. 팀 웹에 실제로 연결하거나 11/02 회의에서 합의한 상태는 아니다.

## 3. 새로 구현한 사용자 경험 개선

### A. 내 차량 고정 카드

- 차량 확인 후 상단에 차량번호·주차장·칸을 지속 표시.
- 위치 보기 / 요금 보기 / 차량 변경 버튼 제공.
- 차량 변경 시 이전 결제 확인을 폐기하고 새 차량 선택으로 이동.
- 출차 후에는 예전 위치 대신 입차 기록 없음 표시.
- 조회 실패는 위치 갱신 지연, 허용된 캐시는 마지막 정보로 구분.
- 같은 탭 새로고침 시 기존 세션 ID로 서버 상태 조회.
- chat/updates 응답에 `vehicle_context` 추가.

추가 요금 조회를 매 폴링마다 수행하지 않는다. 차량 위치 조회와 고정 카드가 같은 요청에서 중복 조회하지 않도록 요청 범위 스냅숏을 공유한다. 차량 선택 후에는 고정 카드 갱신을 위한 위치 조회가 폴링에 추가된다.

### B. 관리자 요청 상태 추적

상태 흐름:

```text
접수 → 확인 중 → 처리 완료 → 해결 확인
                    └─ 아직 안 돼요 → 확인 중
```

- 관리자가 실제 버튼을 누른 경우에만 상태 변경.
- 사용자에게 기존 이벤트 큐로 상태 변경 알림 전송.
- '내 문의 상태' 버튼/질문으로 현재 상태 조회.
- 사용자가 미해결을 선택하면 같은 문의를 재개하며 새 문의를 만들지 않음.
- 문의 revision·runtime_id로 오래된 관리자 요청 검사.
- 사용자 피드백은 문의 ID·revision·소유 세션을 검사.
- 같은 상태 변경을 재전송해도 알림을 중복 생성하지 않음.

새 API:

```http
POST /api/v1/chat/admin/calls/{id}/status
```

```json
{"status":"확인 중","expected_revision":1,"runtime_id":"현재 서버 ID"}
```

관리자는 확인 중/처리 완료를 지정할 수 있다. 사용자 해결 확인/미해결 응답은 챗봇의 상태 검사를 거친 버튼으로 처리한다.

### C. 알림에서 바로 행동하기

- 빈자리 알림에서 해당 주차장 현재 상태 조회.
- 관리자 완료 알림에서 해결됐어요 / 아직 안 돼요.
- 기존 모의 경보 행동 버튼 유지.
- 알림 고유 버튼을 메시지 내부에도 표시.
- `actions`는 알림 고유 행동, `chips`는 현재 대화 흐름의 버튼으로 구분.
- 결제 확인 중 알림이 오더라도 대화 확인 버튼과 알림 행동이 섞이지 않도록 처리.
- 버튼 실행 시 현재 상태를 재검사하며, 과거 상태의 버튼을 다시 눌러도 잘못 변경하지 않음.

사용자가 잘못된 점유/위치를 신고하는 기능은 후순위 후보로만 남겨 두었으며 이번에는 구현하지 않았다.

## 4. 구현 방식 선택과 안정화 방향

대안으로 기존 폴링, SSE, WebSocket을 비교했다. 현재는 **2초 폴링 + 기존 event_id/cursor 수신 확인 큐**를 유지했다. 새 연결 계층을 추가하는 대신 이미 검증한 복구 흐름을 재사용했다.

- 서버의 관리자 상태와 사용자 수신 큐를 같은 프로세스 잠금 안에서 갱신.
- 중복 클릭은 request_id 및 미처리 문의 재사용으로 방어.
- 응답 유실은 동일 요청 재확인과 알림 재전송으로 처리.
- 관리자 수정 충돌은 revision 검사로 거부.
- 실제 데이터 조회 실패 시 mock 데이터로 자동 대체하지 않음.
- 상태·배너·고정 카드는 서버 결과를 근거로 표시하고, 담당자의 확인이나 도착 시간을 임의로 추정하지 않음.

이는 단일 프로세스 메모리 모델에서의 처리다. 영속 DB 트랜잭션이나 외부 서비스까지 아우르는 exactly-once 보장을 구현했다는 의미는 아니다.

## 8. 다음 진행 순서

1. **Claude가 최신 코드의 구조·규칙 우선순위·상태 전이를 재검토.** 특히 규칙을 늘리면서 다른 문장이 잘못 매칭되는 부분을 확인한다.
2. 팀원들이 문장 목록을 보지 않고 직접 질문하는 리허설 실시. 실패 로그를 수집하고 보정용/최종 확인용으로 구분한다.

4. 팀 DB에 세션·문의·보고서·대기열·중복 요청 기록·알림을 연결한다. 상태 변경과 이벤트 저장의 원자성도 DB 트랜잭션으로 옮긴다.
5. LLM은 우선 하나를 연결해 낯선 표현의 분류 정확도·지연·실패율을 측정한다. 기존 테스트 175개는 LLM 성능 검증 결과가 아니다.
6. 슈퍼바이저 AI는 이후 필요성이 확인되면 검토한다. 지금 추가하지 않고, 향후 단일 모델의 실패 사례를 실제로 얼마나 개선하는지 비교한다.
7. 시연 직전에는 기능 추가를 멈추고 전체 회귀 검사와 사용자/관리자 탭 동시 시연을 반복한다.

## 9. 남아 있는 한계

- 단일 프로세스 메모리 저장. 서버 재시작 시 상태가 사라짐.
- 현재 활성 경보 위치는 한 곳. 여러 위치 동시 경보 미지원.
- 대기 알림은 예약이 아니며, 앱을 닫은 동안의 OS 푸시는 미구현.
- 실제 환불·차단기 제어·외부 메시지 발송 미구현.
- 관리자 인증/접근 제어는 신뢰된 시연 환경 전제. BACKEND_TOKEN이 관리자 화면 인증을 대신하지 않음.
- 입차 식별자는 현재 entered_at 기반. 실제 DB의 고유 visit_id 적용 검토 필요.
- 심한 오타·모호한 지시어·여러 차량/여러 작업이 섞인 문장의 일반 처리는 미완성.
- 부정 명령과 '안 해도 되나요?' 같은 규정 질문의 세밀한 의미 차이는 추가 검증 필요.
- 실서버·실제 LLM·카메라·차단기 장치 연동은 별도 통합 검증 필요.

## 10. Claude에게 확인받고 싶은 사항

- 관리자 즉시 호출이 비상 상황 및 기존 결제 확인 취소 흐름과 충돌하지 않는가?
- 반복 호출 통합 조건이 정상적인 새 문의까지 막는 경우는 없는가?
- 문의 상태 전이·revision·사용자 피드백의 검사가 충분한가?
- 고정 카드 갱신이 폴링 부하나 조회 장애를 과도하게 늘리는 부분은 없는가?
- 알림의 actions와 대화 chips가 오래된 버튼 실행을 유발하지 않는가?
