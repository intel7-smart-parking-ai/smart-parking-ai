# V23 종합 코드·데이터 흐름 심층 검수



## 1. 이번 작업의 결론과 범위



V22 → V23은 실제 수정 작업 한 묶음입니다. A주차장 12칸 표시 문제, 과거 자료 재사용, 제공한 두 사진의 회전된 이름/열린 주차선, 사진 1회 자동 수집을 함께 해결했습니다. 사용자가 요구한 ㄷ자 형태를 인식에 반영했고, 카메라 한 대·두 주차장·스티커색이라는 기존 방향을 유지했습니다. B카메라 담당자의 구현에는 관여하지 않습니다.



작동 확인의 범위는 소프트웨어 회귀와 **빈 실물 보드 사진 2장**입니다. 현행 차량의 스티커 번호/색·모든 칸 점유·차량 외곽 위반을 완벽히 판정한다는 결론은 아닙니다. 사진에는 차량이 없고 검증된 점유·차량 분할 모델이 포함되지 않았습니다.



## 2. A12가 안 보이던 원인

## 3. 열린 주차선의 계산 모델



주차면 자체를 ㄷ자 선으로만 저장하면 면적·크롭·스티커 귀속 계산이 정의되지 않습니다. 그래서 **관측된 선과 계산 영역을 별도로 표현**합니다. 관측은 painted_edges 3개, 영역은 polygon 4점, 입구는 entrance_edge 1개입니다. 화면/표시사진에서는 3개 실선+입구 점선으로 구분합니다. 열린 입구를 실제 흰 선으로 판정한 것이 아닙니다.



open_boundaries.py는 낮은 채도·높은 명도·주변 대비로 흰 페인트 마스크를 만들고 Hough 선분을 검출합니다. 평행한 측면 후보와 교차하는 뒤쪽 선, 끝점, 세 면의 픽셀 지지도를 검사합니다. 노란 스토퍼·전용칸 색·접합선·바깥 테두리를 줄이기 위해 길이비·칸 이름 간격·단일 이름 포함을 사용합니다.



시험 중 줄 사이의 작은 틈을 가로질러 측면을 길게 연결하는 문제가 드러났습니다. 짧은 연결 허용(6/8px)과 긴 연결 허용(15/24px) 후보를 모두 유지하고 실제 이름과 최소 면적으로 선택하도록 수정했습니다. 실제 닫힌 4면이 검증되는 옛 형식은 닫힌 윤곽을 우선하며, 색 바닥만 닫혀 보이는 경우는 ㄷ자 후보를 사용합니다.



공유 흰 선의 정수 반올림으로 이웃 면적이 겹치는 경우를 줄이기 위해 검출선에서 원본 2px 안쪽 영역을 사용합니다. JSON의 실제 세 면 좌표는 이 계산 ROI 경계 좌표이며 선 페인트의 모든 픽셀을 저장한 마스크는 아닙니다. boundary_inset_px로 이 오프셋을 남깁니다. 임계값은 현재 사진/합성 시험에서 확인했으며 모든 도면의 범용 학습 모델은 아닙니다.



## 4. 칸 이름과 회전 좌표



automatic_setup.py는 0→270→90→180도 영상을 독립적으로 검사합니다. 긴 변 최대2400의 첫 크기와 최대3200의 두 번째 크기를 사용하며, 원본이 작으면 최대1.5배로 읽습니다. 판독 박스를 원본 좌표로 역변환한 뒤 이름을 A-01 형식으로 정규화합니다. 서로 다른 위치의 같은 이름과 같은 위치의 다른 이름은 충돌로 보류합니다.



제공 사진의 이름은 회전돼 있어 기존 정방향 OCR만으로 부족했습니다. 실제 CPU OCR로 A12/B16 이름을 모두 얻었습니다. B의 작은 글자는 두 번째 크기에서 기준 점수를 만족했습니다. 고정 사진의 수동 좌표 목록을 프로그램에 넣지 않았습니다.



각 이름은 하나의 칸에만 포함되어야 하며 12/16 전체, 카탈로그의 칸종류, 정수 좌표 범위, 볼록성, 칸 간 겹침, 면적 차이를 검증합니다. 일부만 찾았을 때 완성 장면으로 저장하지 않습니다.



## 5. 바닥 문자와 차량 스티커 혼동 수정



빈 실물 사진 첫 검증에서 각 주차장 5칸의 바닥 글자 일부가 흰 스티커 후보가 되어 점유로 표시됐습니다. 번호만 지우는 임시처리로 해결하지 않고, 등록 때 읽은 칸 이름 영상의 32×16 명도 패치와 SHA256을 근거로 추가했습니다.



static_markings.py는 현재 패치와 정규화 상관계수 0.92 이상일 때만 바닥 문자로 봅니다. 후보 면적 절반 이상이 그 문자와 겹치면 스티커 탐색에서 제외합니다. 차량이 이름 위에 들어와 패치가 바뀌면 제외하지 않습니다. 실제 스티커가 기존 이름 위치를 덮는 합성 시험도 통과했습니다. 단, 온갖 조명 변화·부분 가림을 검증한 것은 아닙니다.



vision19.run과 enrich가 같은 제외 근거를 사용합니다. 실제 두 빈 사진에서 색·점유의 거짓 차량 후보가 없어졌고, 전체 칸 실제 OCR까지 실행해도 차량번호를 만들지 않았습니다. 번호 없음은 빈칸 확정이 아니므로 모든 칸은 관측 보류입니다.



## 6. 사진 입력·카메라 입력·작업 분리



사진 자동 등록 버튼은 import→calibrate→analyze→identify→save→scan으로 이어집니다. 사진 취소는 등록 작업을 만들지 않고, 등록 실패는 5초 카메라 재시도 루프에 들어가지 않습니다. 카메라가 연결돼 있더라도 사진 등록 결과를 카메라 프레임과 비교하지 않습니다. IMPORT 출처·원본 파일명/해시·가져온 시각을 기록하고 운영 서버로 보내지 않습니다.



점유/색 빠른 분석과 느린 번호 분석은 분리 작업자에서 수행합니다. 같은 프레임·ROI 문맥에 속한 결과만 조합합니다. 주차장·촬영 묶음·저장 루트 변경 시 기존 결과를 새 상태에 덮어쓰지 않도록 세대 토큰을 검사합니다. 카메라 자동 모드의 기준 재사용·매 장면 구도 검사도 유지했습니다.



자동 수집이 사람 정답 승인을 대신하지는 않습니다. 원본과 미확인 이유를 보존하고, 학습용 확정 정답은 별도 검수 데이터로 관리합니다. 실패를 숨겨 수량·정확도를 높이지 않습니다.



## 7. 저장 구조·완료 상태·복구 검수



records/dataset19는 원본 해시, 사진ID, 출처, 시각, 프레임, 연결 epoch, ROI 문맥을 검사합니다. 동일 ID의 다른 프레임/다른 픽셀/다른 epoch 덮어쓰기를 거부합니다. predictions는 원본/ROI와 별도 파일이고 reviews는 사람 정답입니다. 둘을 합쳐 원래 예측을 지우지 않습니다.



collection_output은 칸명 표시사진·한글 수치 JSON과 전체 장면 표시사진/JSON을 만듭니다. 원본에는 글자를 그리지 않습니다. 한글 라벨에 번호 정수/표기, 스티커색, 칸명·종류, 픽셀 좌표, 품질 지표, 근거, 사람 승인 여부와 파일 해시를 기록합니다. ㄷ자에는 실제 세 면/입구 가상 경계/선 지지비율을 추가했습니다.



V22의 pending-before-write, 마지막 완료 기록, 최신 예측/검수 SHA256 지문을 유지합니다. 저장 도중 중단되거나 파일이 유실/변조되면 완성 묶음의 내보내기를 차단합니다. 복구는 검증된 기존 원본/예측/정답으로 같은 ID의 파생 자료만 다시 만듭니다. 다중 파일 전체가 단일 OS 트랜잭션인 것은 아니므로 pending과 재검증이 필요합니다.



칸별 PNG/JSON은 collected/주차장/칸명 아래 동일 이름이며, 전체는 scenes/주차장 아래입니다. 가져온 원본은 raw/IMPORT, 카메라 원본은 해당 카메라 폴더입니다. 기계용 manifests/predictions/assets/bundles와 사용자용 한글 JSON을 병행합니다.



export_collection은 현재 집계 범위의 정상 묶음을 복사하고 해시를 검사합니다. A12+B16 두 장은 칸28쌍, 전체표시2, 원본2로 이미지32·데이터JSON30입니다. 결과 영수증 JSON1은 별도입니다. UI의 파일 수량과 인식 정확도는 다른 값입니다.



## 8. 호환성·원본 보존·배포



V23는 V22를 별도 폴더로 복사한 수정본입니다. 기존 V22 코드130개 파일 및 ZIP 해시를 대조해 보존을 확인합니다. 사용자 촬영 자료, .venv, 모델, 로그, 캐시, 테스트 임시 파일은 새 배포 ZIP에 넣지 않습니다.



기존 ROI v2는 읽고 새 ㄷ자 자동 등록은 roi-registration-v3를 사용합니다. 새 규격은 세 면/가상 입구와 이름 외관의 의미 차이 때문입니다. D39 계약·예측 규격·collection-v2·설치pose·A/B 카탈로그는 유지했습니다. V23의 새 자료를 V22에서 수정하지 않습니다. 이전 데이터를 자동 이동하지 않으며 UI에서 이전 저장 루트를 선택합니다.



제품 이름, 실행 창, README, VALIDATION, 폴더와 ZIP은 V23으로 맞춥니다. 남아 있는 V19/V21 모듈명과 schema 이름은 구성/계약 이력이며 제품 버전이 아닙니다. 이전 보고서는 history에 보존하고 현재 결과와 구분합니다.



## 9. 검증 근거와 미검증 범위



회귀시험 **215개 통과**(실패0·오류0·건너뜀0). 기존182개에 A/B 표시·과거자료20개, ㄷ자/회전/바닥문자/사진 자동수집13개를 더했습니다. 전체 소프트웨어 경로를 확인했으나 단위시험의 OCR/HTTP는 모의입니다. 별도로 실제 CPU OCR을 제공된 원본 두 장에 적용했습니다.



실제 이름 OCR7회, 전체 칸 번호 파이프라인 OCR28회 관측을 얻었고 동일 영상·인자는 캐시로 재검증했습니다. 최종 등록 A12/B16, 점유/색/번호 오인 차량0, 추론오류0, 저장28쌍, 내보내기 이미지32·데이터JSON30·원본2입니다. 원본 JPEG 해시는 변하지 않았습니다. PHYSICAL_BOARD_VALIDATION_V23.json에 경계 좌표와 실제 경로를 남겼습니다.



V22 별도28곳 쓰기 중단 행렬은 과거 보고서로 보존하며 이번에 재실행했다고 주장하지 않습니다. V23 회귀시험 안의 중단/복구 사례는 다시 실행했습니다. 실제 정전, 다중 프로세스 쓰기, OneDrive 동기화 경쟁은 시험하지 않았습니다.



실제 창은 A 합성/기존 A 장면까지 확인하고 사용자 Esc 입력으로 조작을 중단했습니다. 이후 화면 조작은 재개하지 않았습니다. 최종 A→B 실제 클릭 및 모든 DPI 배치 확인은 미완료이고, 숨긴 Tk 전환 시험과 A/B 파일 오버레이 검수는 완료했습니다.



현행 실차+D39 사진이 없으므로 차량 번호/스티커색 정확도, 차량 경계 위반 정답률을 측정하지 않았습니다. RealSense, GPU, 학습된 모델, Geti, 실서버, 장시간 처리율은 미검증입니다. 첫 등록에 차량이 이름을 가리거나 반사·해상도 부족이면 보류할 수 있습니다. 정확한 빈칸/점유에는 검증된 점유 모델 또는 사람이 확인한 빈 기준이 필요하고, 위치 위반 확정에는 차량 외곽 검출/분할과 정답 데이터가 필요합니다.



## 10. 팀원·교수님께 설명할 작업 순서



“카메라 한 대로 두 주차장을 촬영합니다. A는 직각12칸, B는 사선16칸입니다. 처음에는 보이는 주차선 세 면과 칸 이름을 연결해 자동 등록하고, 열린 입구는 계산용 점선으로 둡니다. 이후 같은 구도인지 확인하면서 칸마다 점유 근거·차량 스티커 번호·배경색을 분석합니다. 결과는 한 UI와 칸별 표시사진/한글 JSON에 함께 남기고 원본도 보존합니다. 저장과 내보내기가 실제로 몇 개 완료됐는지 확인합니다. 현재는 두 빈 보드의 칸 등록과 저장 흐름을 검증했고, 차량이 있는 실물 자료로 번호·색·점유·위치 오류를 측정하는 단계가 남았습니다.”
