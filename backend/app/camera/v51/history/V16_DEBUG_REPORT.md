# V15 → V16 심층 디버깅 결과

V15의 카메라 작업 스레드, 설정 화면, ROI 확인, 분석 결과 검증, 검수 저장, 데이터셋 내보내기를 점검했습니다. 오류를 일으키는 입력·연결 상태·디스크 실패를 만들어 재현한 뒤 수정했습니다. V15 원본은 보존했습니다.

## 발견한 문제와 수정

| 구분 | V15에서 확인한 문제 | V16 수정 | 관련 파일 |
|---|---|---|---|
| 촬영 상태 | 장치 설정이 실행 중인데 이전 프레임을 가져올 수 있었음. 설정 창을 닫고 확인하는 경로에서 특히 문제가 됨 | 설정 변경 시 이전 프레임을 무효화하고 변경 후 영상 읽기가 끝나야 다시 제공. 종료 요청 후에도 마지막 프레임을 반환하지 않음 | camera_hub.py |
| 재연결·ROI | UI의 100ms 점검 사이에 연결이 복구되면 연결 끊김을 놓치고 기존 위치 확인을 유지할 수 있었음 | 연결·설정 변경마다 stream_epoch 증가. 확인한 epoch와 촬영 프레임의 epoch가 다르면 연속 수집 정지 및 위치 재확인. 설정 일부 실패에도 적용 | camera_hub.py, main.py |
| 설정 요청 경합 | 프레임 확인과 요청 등록이 분리되어 연결 종료와 요청 등록이 엇갈릴 수 있었음 | 요청 접수와 연결 종료 시 대기열 정리를 같은 잠금으로 보호. 이전 연결/설정 상태의 요청은 실행 전에 거부 | camera_hub.py |
| 설정값 보존 | 저장 시 카메라 항목 전체를 교체하여 기존 contrast·saturation 등이 삭제됨 | UI가 다루지 않는 값은 유지하고 조회한 값만 병합. 자동/수동 상태 또는 필요한 수동 값이 미확인이면 저장 차단 | camera_tools.py |
| 설정 적용 판정 | set_option이 오류를 내지 않고 실제 값이 달라도 성공으로 보고할 수 있었음 | 요청값과 조회값 비교 후 불일치 시 오류 표시. 부분 적용 가능성을 알리고 재조회 안내 | quality.py |
| 촬영 기록 독립성 | 프레임 이미지는 복사하지만 중첩 camera_options는 공유하여 다른 프레임의 설정 기록도 바뀔 수 있었음 | 작업 스레드와 프레임 제공 경계에서 설정 기록을 깊은 복사. 촬영 기록에도 epoch 저장 | camera_hub.py, pipeline.py |
| OCR 결과 검증 | 상태가 없거나 범위 밖 번호가 있는 JSON도 정상 분석 완료로 인정할 수 있었음 | 상태·번호 범위·신뢰도·원문/번호 일치·중복 번호·전체 요약 검사. 손상된 결과 재분석. 새 분석도 저장 전 검사 | records.py, pipeline.py |
| 검수와 원본 연결 | 수동 편집/가져온 검수 행에 image_id·raw_path 등이 있으면 원본 식별 정보를 덮어쓸 수 있었음 | 정해진 라벨 필드만 받고 파생값은 다시 계산. 원본 ID·경로·배치 정보는 manifest에서 고정 | review.py |
| 불완전한 내보내기 | JSONL을 먼저 완성본 이름으로 쓰고 후속 작업에 실패하면 일부 산출물이 남음. 쓰기 오류가 입력 자료 문제로 처리될 여지도 있었음 | 임시 파일 작성 후 그룹별 자료·보고서를 만들고 주 JSONL을 마지막에 게시. 출력 실패는 전체 실패로 전달하고 해당 실행의 불완전 파일 정리 | review.py |
| 사전 점검 | --check가 camera_quality.json을 읽지 않아 잘못된 화질 설정에도 OK 표시 | JSON 구조·허용 항목·숫자 형식·NaN/Infinity·플리커 모드 검사. 장치별 실제 범위는 연결 후 검사 | quality.py, main.py |

ROI 편집도 화면에 남아 있는 미리보기 대신 카메라 허브의 최신 프레임에서 시작합니다. 명령행 일괄 분석에도 GUI와 같은 manifest 검증을 적용했습니다. 설정 파일 저장 성공과 보조 로그 저장 실패를 구분해 안내합니다.

## 재현과 검증 증거

- 수정 전 V15에서 회귀 사례 11개 실행: 실패 10개, 오류 1개. 오류는 사라진 contrast 설정에 접근할 때 발생한 KeyError입니다. 결과는 `V15_REPRODUCTION.json`에 있습니다. 사례 수가 독립 버그 수와 같다는 뜻은 아닙니다.
- V16 전체 테스트 **112개 통과**: 기존 96개 + 신규 16개, 실패 0·오류 0·건너뜀 0. 결과는 `TEST_RESULTS_V16.json`, 신규 사례는 `tests/test_v16.py`에 있습니다.
- 실제 Tk 창을 생성해 연결 변경 시 재확인, 설정 저장 값 보존, 자동/수동 상태 미확인 시 저장 차단을 검사했습니다.
- 가짜 카메라 소스와 동기화 이벤트로 설정 중 프레임 차단, 연결 복구 후 epoch 변경, 부분 설정 실패, 종료 후 프레임 차단을 검사했습니다. 실제 USB 장애 시험은 아닙니다.
- 디스크 쓰기 도중 오류와 후속 자료 생성 오류를 주입해 성공으로 보고하지 않는지 검사했습니다.
- Python 파일 27개 구문 검사 및 `main.py --check` 통과.
- V15 소스 51개를 작업 전 SHA-256과 비교하여 변경되지 않았음을 확인했습니다. 기준값은 `V15_BASELINE_HASHES.json`에 있습니다.
- ZIP CRC 및 배포 소스와 포함 파일의 바이트 일치를 확인했습니다. 가상환경·모델·촬영 데이터·로그·테스트 임시 자료는 제외했습니다.

검증 환경: Python 3.13.15, OpenCV 5.0.0, NumPy 2.5.4, Pillow 13.0.0, Tk 8.6, PyTorch 2.15.0+cpu. 이 환경의 XPU/CUDA는 모두 사용 불가입니다. 기존 Intel GPU 어댑터를 유지했으며 이번 검증을 Intel GPU 실장비 시험으로 표현하지 않습니다.

## 여러 차량 검증의 의미

나 주차장 16칸을 하나의 합성 이미지에 등록하고, 칸마다 다른 번호(10~24 및 100)와 흰색·초록·파랑 스티커를 배치했습니다. OCR 결과를 모의 입력으로 주어 다음 흐름을 검사했습니다.

1. 카메라 A가 주차장 B를 보는 경우에도 주차장과 카메라 ID가 섞이지 않음.
2. 16개 칸의 번호 후보가 원본 좌표 및 칸 이름에 연결됨.
3. 자동 분석만으로 점유·스티커 색을 정답으로 확정하지 않음.
4. 각 스티커 내부 영역을 지정하고 사람이 승인하면 16개 번호·색·차량 종류가 보존됨.
5. `.frames.jsonl` 한 행에 같은 원본의 16개 칸 주석이 함께 저장됨.

이는 **여러 칸의 데이터 처리·라벨 연결 검증**입니다. 실제 사진에서 EasyOCR이 16개 번호를 정확하게 읽었다는 실험 결과는 아닙니다.

## 남아 있는 한계와 현장 확인

- 스티커 자동 검출기가 없습니다. 색은 사진별로 지정한 스티커 내부에서 측정합니다. 바닥색과 스티커색을 자동으로 완전히 구분하는 기능이 완성된 것은 아닙니다.
- 차량 점유 검출 모델이 없습니다. 숫자 미인식은 빈칸이 아닙니다. 바닥 칸 번호나 차체 장식 숫자도 OCR 후보가 될 수 있으므로 사람이 확인해야 합니다.
- 한 원본 안의 등록 ROI를 차례로 분석합니다. 칸을 모두 병렬 추론하는 구조나 두 카메라의 하드웨어 동기 촬영은 아닙니다.
- 실제 D435 설정·지원 범위, Intel Arc B390에서의 현재 패키지 조합, 실제 OCR/색상 정확도, 장시간 USB 재연결은 이번 자동 시험으로 확인하지 못했습니다.
- 설정 후 새 영상 읽기를 기다리지만 센서 버퍼의 모든 프레임에 새 설정이 적용됐는지나 자동 노출이 안정됐는지까지 보증하지 않습니다. 화면이 안정된 뒤 먼 칸 스티커를 원본 1:1로 확인하세요.
- 이미 시작된 SDK 설정은 창을 닫아도 되돌릴 수 없습니다. 불일치/실패 안내가 나오면 실제값 조회부터 다시 하세요.
- 내보내기 묶음 전체가 하나의 파일시스템 트랜잭션은 아닙니다. 강제 종료나 파일 삭제 실패 시 잔여 파일이 남을 수 있습니다. 성공 메시지와 주 JSONL·frames JSONL·report JSON이 함께 있는 결과를 사용하세요.
- 같은 데이터셋을 여러 앱에서 동시에 편집하는 동작은 지원하지 않습니다. 기존 검수 수정 충돌 검사만으로 여러 프로세스 간 모든 경합을 막지는 못합니다.

## 자료 호환성

제품 버전은 V16입니다. `contract_revision=1103-sticker-100-v2`, `frame_revision=multi-slot-v1`은 유지합니다. `stream_epoch`는 촬영 상태 추적용 선택 메타데이터이며 라벨 의미를 바꾸지 않습니다. 기존 정상 승인 자료는 다시 승인할 필요가 없습니다. 손상되거나 모순된 자동 분석 파일은 OCR 실행 시 다시 분석합니다.

공통 JSONL은 Geti 전용 형식이 아닙니다. ROI는 주차칸 범위이며 차량 바운딩 박스가 아닙니다. `all_objects_in_image_annotated=false`를 유지합니다. 실행·이전 자료 연결 방법은 README.md에 있습니다.
