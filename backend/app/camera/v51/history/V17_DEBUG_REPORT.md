# V16 → V17 최종 심층 검수

작성일: 2026-11-03. V16 원본과 ZIP을 보존한 별도 수정본입니다.

## 결론

검수 승인, 원본 사진 연결, 가져오기, 결과 안내, 실행 경로를 보완했습니다. 사용자 PC의 기존 설치 환경에서 **130개 테스트가 모두 통과**했습니다. 실제 Intel GPU로 기존 사진 2장을 처리하고 수동 기준 라벨의 승인·내보내기까지 확인했습니다.

이 결과는 데이터 수집·검수 처리의 검증입니다. **작은 스티커 번호 미검출은 남아 있으며 모든 칸·번호·색의 자동 인식 완료를 의미하지 않습니다.** 이번 작업은 카메라를 열거나 카메라 설정을 변경하지 않았습니다.

## 재현한 문제와 수정

| 문제 | 수정 | 관련 파일 |
|---|---|---|
| 점유 `unknown`인 칸도 승인 버튼으로 저장·내보내기 가능 | 승인에는 `occupied`/`vacant` 확인을 요구. 미확인은 초안 저장 가능 | `review.py`, `widgets.py` |
| 기존 자료에 이미 들어간 점유 미확인 승인 | 검수 화면에서 초안으로 열고 안내. 내보내기는 해당 칸만 제외하고 사유 기록, 같은 사진의 정상 승인 칸은 유지 | `review.py`, `widgets.py` |
| 번호 후보가 나오면 검수 필요 수에서 빠짐 | 번호 미확인 수와 사람의 확인 대상 수를 분리. 화면에서 자동 결과 확인 대상이며 검수 진행률이 아님을 명시 | `multi_vehicle.py`, `main.py` |
| 원본 사진이 같은 해상도의 다른 사진으로 교체되어도 기존 라벨과 연결 가능 | 새 저장본에 `raw_sha256` 추가. 분석·검수·승인 내보내기가 읽은 동일 바이트의 해시를 검사 | `pipeline.py`, `records.py`, `review.py` |
| 사진 가져오기에서 ROI 편집 중 외부 프로그램이 파일을 변경하면 사진과 출처 해시가 서로 달라짐 | 최초 읽은 바이트로 사진 디코딩과 출처 해시 계산을 함께 수행 | `main.py` |
| 폭 또는 높이가 매우 작은 이미지의 미리보기 크기가 0이 되어 오류 | 미리보기 가로·세로를 최소 1픽셀로 제한 | `widgets.py` |
| 새 버전에 `.venv`가 없을 때 실행 배치가 다른 시스템 Python을 사용 | 명시적 환경 경로 → 현재 버전 `.venv` → 기존 D: V10 환경 순서로 선택. 환경이 없으면 설치 안내, 실행 인자와 종료 코드 전달 | `run_windows.bat` |

촬영·OCR·색 판정 알고리즘을 새 모델로 교체하거나 임의의 카메라 최적값을 적용한 작업은 아닙니다. 카메라 수신·설정 코드와 Intel OCR 어댑터는 V16과 동일합니다.

## 검증 방법과 실제 결과

| 검사 | 결과 | 한계 |
|---|---|---|
| 수정 전 V16에 신규 회귀 사례 적용 | 18개 중 성공 3, 실패 14, 오류 1 | 같은 문제를 저장·GUI·내보내기에서 각각 검사하며, 새 검증 기능 부재도 포함하므로 독립 버그 15개라는 의미가 아님 |
| 수정 후 전체 테스트 | 기존 112 + 신규 18 = **130 통과**, 실패·오류·건너뜀 0 | 카메라는 가짜 장치, OCR은 주로 모의 결과, GUI는 실제 Tk 창으로 검사 |
| 16칸 통합 시험 | 번호 후보 → 수동 스티커 다각형 색 측정 → 검수 승인 → 사진 단위 내보내기 통과 | 합성 이미지와 모의 OCR을 사용한 연결·저장 검증 |
| 실제 Intel GPU 통합 | EasyOCR 1.7.2, PyTorch 2.15.0+xpu, Arc B390. 검출기·인식기 모두 `xpu:0`, CPU 대체 실행 없음 | 기존 사진 2장만 사용, 현재 카메라 각도의 평가 아님 |
| 실행 배치 | V10 설치 환경 선택 후 `--check` 정상 종료 | `--check`는 설정 검사이며 카메라나 모델을 열지 않음 |
| Python 구문 | 28개 파일 검사 | 실행 시 모든 경로의 무결점을 보증하는 것은 아님 |
| 이전 버전 보존 | V16 배포 파일 56개 SHA-256 대조 | 원본 코드와 기존 V16 ZIP 보존 |

기존 테스트 중 5개의 입력에서 승인할 점유 상태를 명시했습니다. 색·가상 번호판·출력 실패를 검사하려던 사례가 점유 미확인 상태로 승인하고 있었기 때문입니다. 해당 검사의 원래 검증 항목은 유지했습니다. 테스트 수를 줄이거나 실패 검사를 삭제하지 않았습니다.

## 실제 사진 결과

| 기존 사진 | 실제 번호 | V17 자동 번호 | 수동 영역의 색 | 판단 |
|---|---|---|---|---|
| `dfd270a355464f9ab3cceda79e02a62c` | 49 | 49 | blue | 이 사례 번호 일치 |
| `09b2a2d07f3940f58087d3708a7f9de2` | 49 | 미검출 (`no_text`) | blue | **작은 스티커 번호 인식 문제 지속** |

두 사진의 선택 번호 결과는 V16과 같았습니다. 색은 사람이 지정한 스티커 내부 다각형을 사용했습니다. 두 번째 사진에 `49`를 직접 입력해 내보낸 것은 수동 정답 라벨의 처리 검사이며 OCR 성공으로 세지 않았습니다. 작은 표본을 전체 인식률로 환산하지 않습니다.

콘솔의 최초 `Using CPU` 메시지는 EasyOCR 모델을 CPU에서 초기화할 때 나옵니다. 이번 시험에서는 이후 두 모델의 실제 장치가 `xpu:0`임을 확인했습니다.

## 기존 데이터와의 호환

1. `contract_revision=1103-sticker-100-v2`, `frame_revision=multi-slot-v1`을 유지합니다.
2. 새 촬영 manifest에는 선택 필드 `raw_sha256`을 기록합니다. 승인 내보내기와 사진 단위 내보내기에도 해당 값이 있으면 전달합니다. 검증은 파일 변조 방지 서명이 아니라 실수로 사진을 교체·손상한 상황을 검출하기 위한 것입니다.
3. 해시가 없는 기존 자료도 읽습니다. 과거 사진의 동일 해상도 교체 여부까지 소급해서 검증할 수는 없습니다. 기존 파일에 현재 해시를 임의로 붙여 원본이 보장된다고 주장하지 않습니다.
4. 기존 점유 미확인 승인만 초안으로 취급합니다. 정상 승인 자료를 일괄 해제하지 않습니다. 기존 파일을 자동 덮어쓰지 않으며, 사용자가 저장하면 새 검수 기록을 남깁니다.
5. 점유는 확인했지만 번호나 색을 읽을 수 없는 자료는 해당 값을 미확인으로 남기는 부분 라벨이 가능합니다. 승인이 곧 모든 라벨 완성을 뜻하지는 않습니다. 모든 번호·색이 필요한 학습에는 값이 완성된 자료를 사용하세요.
6. `frame_summary`의 검수 대상 수 계산을 바로잡고 `missing_number_spaces`를 추가했습니다. 구형 요약이 있는 분석 결과는 OCR 실행 시 재분석됩니다. 기존 원본과 사람이 승인한 정답은 보존합니다. 팀 소비 코드가 요약 필드를 사용한다면 의미 변경을 확인하세요.
7. 기존 데이터 경로는 `config.json`의 `dataset_directory`로 연결합니다. 동시에 여러 버전에서 같은 데이터셋에 저장하지 마세요.

## 오늘 마무리 판단

V17은 확인된 데이터 처리 오류를 수정했고, 해당 회귀 시험과 실제 GPU 실행 경로를 통과했습니다. 현장 사용은 **한 장 수집 → ROI·번호·점유·색 확인 → 승인 → 내보내기**로 시작하세요. 작은 스티커 해상도·반사·각도에 따른 OCR 실패, 여러 실제 차량의 한 장 전체 일치율, 장시간 연속 수집 및 USB 장애 복구는 별도 현장 평가가 남아 있습니다.

사진의 번호를 읽지 못하면 빈칸으로 확정하지 말고 초안 또는 미확인 라벨로 남기세요. 색 판정은 스티커 내부 수동 영역 기준이며, 자동 차량/스티커 검출 모델과 Intel Geti 전용 데이터 변환은 포함하지 않습니다.

검증 파일: `TEST_RESULTS_V17.json`, `V16_REPRODUCTION.json`, `XPU_INTEGRATION_V17.json`, `VALIDATION.json`. 재실행은 `tests/test_v17.py` 및 전체 `tests/`를 사용합니다.
