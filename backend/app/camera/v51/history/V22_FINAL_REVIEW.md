# V22 최종 종합 분석·코드·수집·저장 검수 보고서

검수일: 2026-11-04 / 기준: 배포 V21 → 수정 V22 / 대상: 카메라 한 대로 A 직사각형 12칸과 B 사선형 16칸을 수집하는 통합 프로그램.

## 1. 검수 결론과 판정 범위

**V21에서 재현한 저장·내보내기·자동 등록 상태 오류를 V22에서 수정했고, 최종 회귀시험 182개와 별도 저장 중단 시험 28개를 통과했습니다.** 카메라 입력에서 칸 등록, 인식, 표시사진·한글 JSON, 파일 집계, 검수, 복구, 내보내기로 이어지는 경로를 검토했습니다. 설정 검사와 Windows 통합 UI 육안 확인도 진행했습니다.

이 결과는 시험한 소프트웨어 경로가 요구한 동작을 한다는 근거입니다. 모든 환경에서 오류가 전혀 없거나 실제 촬영 정답률이 100%라는 뜻은 아닙니다. 현행 D-39 실물 A·B 사진이 없으므로 실제 주차장 인식 정확도는 아직 측정할 수 없습니다. 학습된 점유 모델과 차량 외곽 모델도 포함하지 않습니다. 따라서 **소프트웨어 수집·저장 경로 검증 완료, 실제 현장 성능 검증 대기**로 판정합니다.

이번 수정은 번호·색 인식률을 새로 높였다고 주장하는 변경이 아닙니다. V21 인식 알고리즘과 계약은 유지하고, 저장된 결과의 최신성·완료 상태·복구·UI 작업 상태를 보완했습니다. 과거 OCR 시험과 이번 시험을 구분합니다.

## 2. 사용자의 요구를 해석한 기준

- 카메라는 한 대를 A·B 주차장으로 이동해 사용합니다. 다른 사람이 담당하는 두 번째 카메라 개발은 이번 범위에 포함하지 않습니다.
- A는 직사각형 12칸, B는 사선형 16칸입니다. 주차장 A/B와 주차칸 이름의 A/B 구역 문자는 서로 다른 식별자입니다.
- 색은 차량 차체색이 아니라 **흰색·초록·파랑 스티커 배경색**입니다. 번호도 현행 D-39 모형 차량 스티커의 24개 번호를 기준으로 합니다.
- 원본 한 장에서 전체 칸의 위치·이름·점유·번호·색을 연결하고, 화면과 칸별 자료에서 결과를 확인합니다.
- 매 프레임마다 위치 확인·OCR·저장을 수동 클릭하지 않도록 자동 흐름을 제공합니다. 물리적 카메라 설치, 주차장/저장 경로 선택, 최초 환경 준비는 필요합니다.
- 표시가 있는 사진과 한글·수치 JSON을 같은 칸명 아래 저장하고, 무표시 원본도 보존합니다. 데이터 정확성 평가와 자동 후보 수집은 구분합니다.
- 잘못된 주차 위치는 구현된 판단 근거의 범위를 보여줘야 하며, 차량 마스크가 없는 상태에서 확정 판정을 만들어서는 안 됩니다.
- 이전 문서·분석·버전은 이력으로 보존하고, 실제 수정본은 새 정수 버전과 ZIP으로 제공합니다.

## 4. 실제 재현한 V21 문제와 V22 수정

동일한 합성 장면·모의 입력으로 V21과 V22를 각각 실행했습니다. 원본 프로그램이나 이전 ZIP을 수정하지 않고 별도 시험 폴더에서 비교했습니다. 근거: `REPRODUCTION_V21.json`, `REPRODUCTION_V22.json`.

| 문제 상황 | V21 재현 | V22 결과 |
|---|---|---|
| 기존 장면의 예측 교체 직후 저장 중단 | 이전 표시사진 묶음 1장면이 계속 내보내짐 | 미완료로 표시, 해당 장면 내보내기 0 |
| 사람 정답 저장 직후 표시사진 생성 전 중단 | 새 정답과 다른 이전 사진 묶음 1장면 내보내짐 | 해당 장면 내보내기 0, 저장된 사람 정답은 유지 |
| manifest는 pending인데 이전 bundle은 complete | 해당 장면 1개 내보내짐 | 미완료 장면 제외, 0개 |
| 번호를 ` 23 `으로 입력해 승인 | 정답 표기는 23, 한글 JSON 숫자는 null | 정규화한 정답을 사용, 한글 JSON `차량번호: 23` |
| 자동 ROI 등록 중 새 촬영 묶음 선택 | 등록 결과가 폐기되고 calibrating 상태에 정체 | 등록 중 변경 차단, 등록 실패 후 정상 waiting 재시도 |

추가로 예측 파일이 유효한 다른 내용으로 바뀌거나 검수 파일이 삭제된 경우, 이전 표시사진이 최신 정답을 나타내는 것처럼 사용되지 않도록 입력 SHA256 지문을 대조합니다. 원본 파일이 존재한다는 이유만으로 파생 사진의 최신성을 인정하지 않습니다.

## 5. 수집 과정 검수

### 5.1 전칸 등록과 구도

자동 시작은 카메라 연결 → 프레임 대기 → 기존 구도 검사 또는 자동 칸 등록 → 점유/스티커/OCR → 저장의 순서입니다. 실제 칸 이름과 선의 닫힌 볼록 사각형을 연결하므로 직사각형과 사선 평행사변형을 처리할 수 있습니다. A12/B16 전체 이름과 경계가 맞지 않으면 수집을 진행하지 않고 진단 및 재탐색을 합니다.

열린 U자 선, 가려진 칸 이름, 끊긴 선, 매우 작거나 90도 회전한 이름까지 일반적으로 해결하는 주차선 학습 모델은 아닙니다. 이런 구도에서는 수동 ROI 네 모서리 등록이 필요할 수 있습니다. A/B 구도·해상도·시리얼·pose가 맞고 자동 등록 anchor가 검증되어야 재사용합니다. 자동 ROI의 매 분석 장면에서도 anchor를 대조하여 이동한 카메라에 이전 ROI를 그대로 적용하지 않도록 합니다. ORB 방식은 조명·가림·반복 무늬에 영향을 받으므로 현장 검증은 남습니다.

### 5.2 카메라 프레임과 비동기 결과

추가한 4개 카메라 모의시험에서 읽는 쪽의 이미지 수정이 카메라 캐시를 바꾸지 않는지, 설정 변경 시 연결 구간(epoch)이 바뀌고 새 프레임을 받는지, 종료 후 이전 캐시를 반환하지 않는지, 오래된 프레임을 반환하지 않는지 확인했습니다. 카메라 하드웨어 드라이버 자체를 시험한 결과는 아닙니다.

UI는 입력·주차장·구도 변경 때 이전 처리 결과가 새로운 화면을 되살리지 않도록 세대 번호와 문맥을 확인합니다. V22에서는 ROI 편집/빈 기준 등록/저장 폴더 선택 같은 대화상자를 열기 전에 실시간 처리를 멈춥니다. 저장 사진을 열 때도 자동 등록을 멈춥니다. 자동 등록 중 촬영 묶음을 바꾸는 동작은 차단합니다. 대기 중 묶음을 바꾸면 자동 상태와 체크박스를 함께 해제합니다.

### 5.3 번호·색·점유·위치

스티커를 찾아 투시 보정한 뒤 여러 처리 영상의 번호가 합의할 때 후보를 채택합니다. 번호 충돌, 근거 부족, 이웃 칸 영역, 동일 번호 중복은 보류합니다. OCR 장애가 색 검출 전체를 무효화하지 않도록 색 처리는 독립되어 있습니다. 배정표의 기대 색으로 실제 측정 색을 대체하지 않습니다.

검증된 점유 모델이 연결되면 해당 모델을 사용합니다. 모델이 없을 때 자동 흐름은 인쇄 흔적이 있는 스티커를 점유 후보 근거로 사용합니다. **스티커를 못 찾았다는 이유로 빈칸으로 확정하지 않습니다.** 수동 빈 기준 비교는 조명·손·그림자의 영향을 받는 후보 방식입니다.

잘못된 주차는 현재 전용칸 종류와 스티커 종류 불일치 의심, 빈 기준 변화 영역의 경계 걸침 후보까지 제공합니다. 차량 전체 외곽과 주차선의 침범을 학습 모델로 확정하는 기능은 아직 없습니다. 사용자 목표인 전칸의 정확한 빈칸/점유 및 위치 위반 확정을 달성하려면 현장 자료와 검증된 모델이 추가로 필요합니다.

## 6. 저장 과정 검수와 V22 완료 규칙

### 6.1 저장 순서

재저장은 원본 ID·시각·프레임·연결 구간·구도·픽셀이 같은지 먼저 검사합니다. 새로운 원본으로 기존 ID를 덮어쓰지 않습니다. 저장은 다음 순서로 진행합니다.

1. manifest에 `asset_status: pending`, `collection_status: pending`을 먼저 기록합니다. 예측을 쓸 때는 예측도 pending입니다.
2. 표시사진 bundle도 pending으로 기록합니다. 이전 complete bundle이 있더라도 완료 자료로 사용되지 않습니다.
3. 무표시 칸/스티커 크롭, 예측 및 변경 이력을 기록합니다.
4. 최신 검수 정답을 검증하고 표시사진·한글 JSON·전체 장면 자료를 생성합니다.
5. 예측/검수 입력 파일의 SHA256 지문과 각 산출물의 SHA256을 bundle에 기록합니다. 생성 중 입력이 바뀌면 partial입니다.
6. 자산 완료 기록을 쓴 뒤 **마지막으로 manifest 완료 상태**를 반영합니다. 중간 실패는 부분 실패/미완료로 남습니다.

각 파일은 임시 파일에 쓰고 flush/fsync 후 교체합니다. 여러 파일 전체가 하나의 파일시스템 트랜잭션이 되는 구조는 아니므로, 중간 중단은 pending 표식과 지문으로 감지하고 복구합니다. 실제 정전, 장치 고장, OneDrive 충돌을 모두 재현한 것은 아닙니다. 새 원본 직후 manifest 이전에 중단하면 기록에 연결되지 않은 파일이 남을 수 있으며 유효 자료 수에서 제외합니다. 사용자 원본을 임의로 지우는 자동 정리 기능은 추가하지 않았습니다.

### 6.2 사람 정답 저장

검수 입력을 검증하고 이전 검수 revision이 맞는지 확인한 후, 먼저 표시자료를 pending으로 전환합니다. 이전 검수 이력을 남기고 새 정답을 저장한 뒤 사진과 JSON을 갱신합니다. 사진 생성이 실패해도 이미 저장된 사람 정답을 취소하지 않습니다. 대신 해당 묶음을 미완료로 표시하고 내보내기에서 제외합니다. 재복구는 최신 승인 정답을 사용합니다.

공백이 붙은 번호는 저장 전에 정규화합니다. 한글 JSON의 숫자 값은 승인된 `display_number`를 사용합니다. 확인하지 못한 값은 null/미확인으로 유지합니다. 승인한 색에는 해당 스티커 영역이 필요하며, 이웃 칸 영역이나 한 장면의 동일 실물 번호 중복 승인은 거부합니다.

### 6.3 데이터 복구

**선택 장면 저장 복구**는 저장 목록에서 고른 장면의 원본 해시, manifest, 예측, 검수 정답을 검사한 뒤 파생 자료를 다시 생성합니다. 카메라 연결이나 새로운 OCR은 필요하지 않습니다. ID·촬영 시각·세션·배치·출처·원본 픽셀은 유지합니다. 반복 복구해도 논리적 원본/칸별 짝 개수가 늘지 않습니다.

원본이 손상되었거나 필요한 예측 파일이 없어졌거나 검수 파일이 잘못된 경우 복구를 거부합니다. 복구는 유실된 정답을 추측하는 기능이 아닙니다. 원본만으로 다시 인식해야 하는 상황과, 이미 저장된 증거로 파생 사진을 다시 만드는 상황을 구분합니다.

## 7. 표시사진·한글 JSON·경로 검수

원본은 `raw/<주차장>/<사진ID>.png`, 칸별 표시자료는 `collected/<주차장>/<칸명>/<칸명>__<UTC>__<사진ID>.png/.json`에 저장합니다. A주차장 A-01과 B주차장 A-01은 다른 폴더입니다. 전체 표시사진·전체 결과는 `scenes`에, 기계용 manifest/예측/검수/완료 기록은 각각 별도 폴더에 둡니다.

표시사진에는 칸 경계·스티커 영역·번호 영역·칸명·번호·한글 색·라벨 출처를 표시합니다. 표시는 원본 복사본에 그리므로 무표시 원본·학습 크롭을 오염시키지 않습니다. 발표·검토용 표시사진을 학습 원본으로 사용하지 않습니다.

한글 JSON에는 정수 번호, 원본 픽셀 좌표, 수치 점수·화질, 촬영 시각, 구도·칸 이름, 미확인 여부, 사람 승인 여부, 라벨 출처, 원본·표시사진 경로와 해시가 들어갑니다. 좌표는 표시사진의 설명 여백이 아닌 **변경하지 않은 전체 원본의 좌상단 기준**입니다. 승인 정답이 적용되어도 자동 측정값·과거 예측 근거는 정답과 구분하여 남습니다. `자동정보완성`은 값의 존재 여부이며 정확도 100% 또는 사람 승인이라는 뜻은 아닙니다.

자동 라벨 출처와 사람 승인 상태를 명시하므로 자동으로 수집한 후보를 검수 정답으로 오인하지 않게 했습니다. 현재 키 이름 중 `자동정보완성`은 사람 승인 값이 반영된 사진에서도 정보 완성 여부를 계산하는 기존 이름입니다. 정답 여부는 `사람검수완료`/`라벨출처`로 판단합니다.

## 8. 파일 집계·내보내기 검수

집계는 디스크 manifest 및 원본/자산/사진·JSON의 해시를 검사하고, 현재 주차장/세션/전체 범위를 적용합니다. 손상 기록은 오류로 표시합니다. 원본 수, 칸 크롭 수, 표시사진 수, 한글 JSON 수, 정상 짝, 승인 수, 학습 가능 수는 의미가 다르므로 따로 표시합니다.

자동 내보내기는 완료된 묶음과 원본을 복사합니다. manifest pending/partial, 구규격 bundle, 입력 지문 불일치, 사진/JSON 누락·해시 불일치, 원본 오류는 제외 사유를 남깁니다. 파일을 읽어 준비한 뒤 입력 지문을 다시 확인합니다. 복사 중 실패한 묶음은 성공 수량으로 보고하지 않습니다. 새 내보내기가 진행/실패하는 동안 과거 성공 수량을 현재 성공으로 보여주지 않도록 상태를 갱신했습니다. 중복 클릭과 내보내기 중 저장 루트 변경도 막습니다.

| 완성 장면 | 칸 사진·JSON 짝 | 이미지 수 | 데이터 JSON 수 | 별도 결과 JSON |
|---|---:|---:|---:|---:|
| A 한 장면 | 12 | 14 | 13 | 1 |
| B 한 장면 | 16 | 18 | 17 | 1 |
| A+B를 한 번에 내보냄 | 28 | 32 | 30 | 1 |

이미지 수에는 원본과 전체 표시사진이 포함됩니다. 한 번의 A+B 내보내기 폴더에서 확장자만 세면 JSON은 결과 기록을 포함해 31개입니다. UI 데이터 JSON은 30개입니다. 복사이므로 원래 데이터는 삭제하지 않습니다.

승인 학습 내보내기는 사람이 승인한 정답과 무표시 크롭을 사용하며 자동 후보 내보내기와 별도입니다. 번호 정답만 있고 번호 영역 박스가 없으면 번호 학습 크롭을 생성하지 않습니다. 관련 자료의 학습/검증 분리 그룹을 유지합니다. 실제 Geti 프로젝트로 가져오기 및 학습은 이번 시험 범위가 아닙니다.

중단 시험은 각 저장 지점에서 중단한 뒤 원본 해시 불변, 내보내기가 허용된 경우 현재 예측·정답과 일치, 복구 후 한 원본/정상 사진·JSON 짝 유지, 반복 생성에 따른 중복 집계 없음 등을 확인했습니다. 의도한 예외를 검사하는 회귀시험은 로그에 오류 메시지가 있어도 최종 unittest 결과가 통과일 수 있습니다. 최종 실패/오류 개수는 시험 보고서 기준입니다.

UI는 현재 PC에서 합성 저장 자료를 넣은 실제 Tk 창을 확인했습니다. 긴 칸 라벨을 두 줄로 배치했고, 작은 창에서도 저장 현황·오류 안내·칸 목록에 공간을 먼저 배정하도록 수정했습니다. 기본 크기, 1060×780의 기본 보기, 최대화 보기를 확인했습니다. 고급 보기 역시 확인했으나 마지막 레이아웃 변경 후 모든 창 크기의 고급 보기를 재검증한 것은 아닙니다. 모든 해상도·DPI 조합을 보증하지 않습니다. 시험창은 실제 카메라와 서버를 연결하지 않았습니다.

### V21에서 수행했고 이번에는 재실행하지 않은 인식 시험

인식 코드가 V21과 동일한지 배포 검사에서 확인합니다. `history/OCR_VALIDATION_V21.json`, `history/AUTO_REAL_OCR.json`, `history/COLLECTION_REAL_OCR.json`은 과거 실행 증거입니다.

- 실제 로컬 EasyOCR CPU, 합성 D39 24대: 번호 20개 일치·4개 보류, 스티커색 24개 일치. 이 시험에서 채택한 번호 오답은 없었지만 실제 현장 일반 정확도를 뜻하지 않습니다.
- 합성 A12/B16의 자동 칸 등록과 사진·JSON 28쌍, 이미지 32/데이터 JSON 30 내보내기.
- 과거 원형 파랑 49 실물 사진: 파랑 후보를 검출하되 현행 D39 번호로 인정하지 않음.

V22의 182개 회귀 및 UI 시험에서는 OCR 대역을 사용했습니다. 이번 작업에서 실제 CPU OCR을 다시 수행한 결과인 것처럼 과거 기록을 합산하지 않습니다. 실물 A/B 현재 번호 데이터는 여전히 없습니다.

## 10. 버전·데이터 호환

제품 버전은 V22, 폴더는 `smart_parking_v22`, 배포는 `smart-parking-v22.zip`입니다. V21 소스 116개와 이전 ZIP의 변경 여부는 시작 시 저장한 SHA256과 비교합니다. 환경·모델·촬영 데이터·로그·임시 테스트 폴더·캐시는 ZIP에 넣지 않습니다.

| 항목 | V22 값 | 이유 |
|---|---|---|
| D39 계약 | 20261104-d39-v3 | 번호/색 계약을 바꾸지 않음 |
| 예측 규격 | prediction-v21-1 | 인식 근거 구조 유지 |
| 자동 ROI | roi-registration-v2 | 등록 방식·설치 pose 유지 |
| 표시사진 bundle | **korean-collection-v2** | 예측/검수 입력 지문과 완료 확인의 의미 추가 |
| 한글 칸/장면 JSON | 주차칸-한글-v1 / 주차장면-한글-v1 | 사용자 라벨 구조 유지 |
| 자동 내보내기 | automatic-export-v1 | 기존 복사 결과 형식 유지 |

V21 자료 루트를 V22에 연결할 수 있습니다. 다만 V21의 `korean-collection-v1` 묶음에는 최신성 지문이 없으므로 V22는 그대로 자동 내보내지 않습니다. 목록에서 해당 장면을 선택해 **선택 장면 저장 복구**를 실행하면 검증된 기존 증거로 v2 표시자료를 만듭니다. 사진 전체를 일괄 변환하는 기능은 추가하지 않았습니다. 변환 전에는 구자료가 미완료/주의로 표시될 수 있으며 원본 유실을 뜻하지 않습니다.

같은 데이터 루트를 여러 프로그램/버전이 동시에 수정하는 다중 쓰기 잠금은 없습니다. 한 프로그램에서만 수정해야 합니다. V22에서 갱신한 bundle은 V21로 다시 편집하지 않습니다. 프로그램 폴더를 바꾸면서 기본 datasets를 새로 사용하는 경우 기존 촬영 자료가 자동 이동하지 않으므로, 이어 쓸 때는 기존 저장 폴더를 명시적으로 선택합니다.

## 11. 아직 확인하지 못했거나 목표에 남은 부분

- 현재 D39 실제 A/B 영상의 번호·색·점유 정답률, 반사·그림자·원거리·가림·사선 각도별 성능.
- RealSense 실기기 연결과 설정 변화, 실제 GPU/XPU, 장시간 실행·디스크 사용량·실제 처리 속도.
- 학습된 점유 모델을 통한 정확한 빈칸 판단, 차량 마스크 기반 경계 침범 확정.
- 실제 Geti 가져오기·학습 결과, 실제 서버 계약 및 전송 성공. 이번 HTTP 시험은 모의입니다.
- 실제 정전·장치 고장·OneDrive 동기화 충돌·동일 데이터 루트의 여러 프로그램 동시 수정.
- 모든 창 크기/DPI, 다수 장면의 장기 집계 성능, 자동 유사·중복 사진 제거, 과거 자료 일괄 변환.

품질 지표를 통과해도 인식 정답을 보장할 수 없습니다. 미확인 자료는 실패 원인 분석을 위해 보존합니다. 장기간 품질 좋은 자료만 선정하려면 현장 정답 대조와 수집 커버리지, 중복률, 촬영 조건별 표본을 함께 확인해야 합니다.

## 12. 현장 최종 확인 절차

1. 카메라 하나로 A12/B16 전체 이름과 선이 보이도록 설치하고 자동 등록 결과를 실제 칸과 대조합니다. 이동 후 이전 ROI가 재사용되지 않고 재검증되는지 봅니다.
2. 실제 D39 24개 번호·세 가지 스티커색을 여러 칸과 거리·조명에서 촬영해 승인 정답을 작성합니다. 맞힌 비율과 보류 비율을 함께 확인합니다.
3. 빈칸·차량 있음·스티커 가림·중복 번호·경계 걸침을 각각 시험합니다. 점유 모델이 없다면 스티커 없는 칸이 관측 보류라는 점을 확인합니다.
4. A/B 장면을 저장하고 원본/표시사진/한글 JSON에서 칸명·좌표·번호·색이 동일 장면을 가리키는지 봅니다. 내보낸 수량은 12/16쌍과 실제 파일을 비교합니다.
5. 미완료 자료는 복구 후 내보내고, 실패는 UI의 사유와 기록으로 확인합니다. 실제 USB·디스크·동기화 환경에서 종료/재시작을 시험합니다.
6. 현재 범위 품질·정답 대조 보고서의 평가 표본 수·일치·보류·커버리지로 현장 사용 가능 여부를 결정합니다. 정답이 없으면 정확도를 채우지 않습니다.

이 절차는 앞으로 필요한 실물 검증 목록입니다. 이번에 모두 수행했다고 기록하지 않습니다.
