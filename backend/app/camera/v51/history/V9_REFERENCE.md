# V9 주차장 통합 데이터 수집 프로그램



**실행 파일은 `main.py` 하나입니다.** 카메라·ROI·번호/색상 분석·사진 불러오기·검수·내보내기를 같은 프로그램에서 사용합니다. 내부 코드는 디버깅을 위해 역할별 모듈로 나눴습니다.





## 이후 수정본의 버전 규칙



V8을 보존하고 전체 디버깅 수정본 **V9**를 별도로 만들었습니다. 다음 실제 수정본은 **V10**으로 올립니다. 버전별 변경 이유·수정 내용·검증 결과는 CHANGELOG.md (`CHANGELOG.md`, 별도 보관 이력)에 기록합니다. 이전 버전 폴더와 ZIP은 보존합니다.



## 발표용 버전 구분



이번 배포는 **V8의 저장·ROI 검증·검수·내보내기 오류를 수정한 V9**입니다. 폴더는 `smart_parking_v9`, 배포 파일은 `smart-parking-v9.zip`, 실행 파일은 `main.py`입니다. V8의 통합 기능을 유지하면서 잘못된 자료 연결과 오류 시 중단을 줄였습니다. 상세 내용은 [DEBUG_REPORT.md](DEBUG_REPORT.md)를 확인하세요.



**V9에서 달라진 점:** 카메라/ROI 불일치 저장 차단, 오류 파일을 제외한 CSV 내보내기, OCR 오류 재시도, 다른 칸 스티커 연결·중복 차량 승인 차단, 검수 중복 창/덮어쓰기와 종료 시 미저장 처리 개선입니다.



| 구분 | V7: 1차 원본 수집 | V8: 통합 데이터 수집 |

|---|---|---|

| 목적 | 카메라로 학습용 원본 확보 | 원본·주차칸 위치·번호·스티커색을 연결해 검수 자료 확보 |

| 입력 | A/B 카메라 | A/B 카메라 + 휴대폰·가상 이미지 |

| 주차칸 | 기본 수집 과정에 ROI 등록 없음 | 가나다라 도면 계약에 맞춘 칸별 ROI 수동 등록 |

| 번호·색상 | 기본 수집 과정에서 분석하지 않음 | EasyOCR 번호 후보 + 사진별 스티커 영역 지정 후 내부 배경색 측정 |

| 자료 관리 | 원본과 촬영 기록 | 원본·ROI 사본·자동 후보·사람 검수 결과 |

| 검수·내보내기 | 별도 후속 작업 필요 | 수정·승인 화면, 후보 CSV, 승인 자료 JSONL |

| 자동 점유 판정 | 없음 | 없음 — 미인식은 빈칸으로 판단하지 않음 |



**발표 설명 예시:** “V7에서는 일정 간격으로 원본 사진을 모았습니다. V8에서는 고정 카메라의 주차칸 ROI와 번호·스티커 배경색 분석을 통합하고, 사람이 확인한 결과까지 같은 사진에 연결해 저장하도록 확장했습니다. V9에서는 잘못된 ROI 연결과 검수·저장 오류를 재현해 수정하고 회귀 테스트를 추가했습니다.”



흰색=일반, 초록=전기차, 파랑=장애인이라는 팀 규칙을 적용합니다. 자동 인식 결과는 후보이며 실제 장비에서 인식 정확도를 검증하는 단계입니다.



이전에 만든 `collection_v8_geti`는 화질·수집 조건을 바꿨던 별도 실험본입니다. 이번 발표의 **V8은 이 `smart_parking_v8` 통합 프로그램**을 가리킵니다. 기존 자료는 비교·이력용으로 보존합니다.



## 반영한 팀 계약



| 주차장 | lot_id | 종류 | 칸 수 | space_id | 전기차 칸 | 장애인 칸 |

|---|---|---|---:|---|---|---|

| 가 | A | 실물·기본형 | 12 | A-01~06, B-01~06 | A-05, A-06 | B-06 |

| 나 | B | 실물·사선형 | 16 | A-01~08, B-01~08 | A-07, A-08 | B-07, B-08 |

| 다 | C | 가상·일방순환형 | 12 | A-01~06, B-01~06 | A-05, A-06 | B-06 |

| 라 | D | 가상·L자 | 10 | A-01~05, B-01~05 | A-04, A-05 | B-05 |



- 칸의 식별자는 `(lot_id, space_id)`입니다. 가 주차장 A-01과 나 주차장 A-01은 다른 칸입니다.

- `camera_id`는 촬영 장치 식별자입니다. 카메라 A가 반드시 가 주차장을 보는 것은 아닙니다. 화면의 주차장 선택에서 실제 설치를 확인합니다.

- 카메라 기본 매핑은 A→가, B→나로 준비했으며 화면에서 바꿀 수 있습니다.

- `space_type`: `general`, `electric`, `accessible`. `disabled`를 사용하지 않습니다.

- 스티커 **배경색**: 흰색 `white`→일반 `general`, 초록 `green`→전기차 `electric`, 파랑 `blue`→장애인 `accessible`.

- 색상은 해당 사진에서 사람이 지정한 스티커 네 모서리 내부만 측정합니다. 글자 주변, 주차칸 바닥, 차량 몸체는 표본에 넣지 않습니다. 스티커 영역이 없으면 색상/차량 유형은 미확인입니다.

- 일반차는 전기차·장애인 전용 칸에 허용되지 않습니다. 전용 칸의 종류가 일치하는지 검수 자료에서 계산합니다. 일반 칸은 세 유형 모두 허용하도록 구성했습니다.

- 실물 가/나는 `01`~`24`의 정확한 두 자리만 유효합니다. `1`, `001`, `00`, `25`는 미확인 처리하며 `1→01` 자동 보정은 하지 않습니다.

- 가상 다/라는 `17가1724` 원문과 표시 번호 `1724`를 구분합니다. 가상 표시 번호를 실물 스티커 ID로 변환하지 않습니다.

- 검수 자료의 실물 `car_id`에는 확인된 두 자리 번호를 그대로 기록하고, 가상 자료의 `car_id`는 null로 둡니다. 가상 번호판의 최종 API 필드명/ID 연결은 확정 문서 확인 후 적용합니다. 이벤트 전송/DB 연결은 포함하지 않습니다.



계약은 사용자가 제공한 표와 11/03 팀 공지 중 수집 담당 확정 항목을 기준으로 구현했습니다. GitHub 문서 본문 접근이 되지 않아 DECISIONS.md의 13건 전체나 PR 병합 상태는 확인하지 못했습니다. 24대 번호별 색상 배정표, 정식 주차장 이름, 미확정 API 필드명, 요금/결제/세션 규격은 추정하지 않습니다. 현재 occupancy 값은 검수용 내부 값이며 서버의 칸 상태 4가지에 매핑하거나 전송하지 않습니다.



## 설치와 실행



별도 가상환경을 권장합니다. Windows Python 설치에 tkinter가 포함되어 있어야 합니다.



```powershell

python -m venv .venv

.\.venv\Scripts\python.exe -m pip install -r requirements.txt

.\.venv\Scripts\python.exe main.py --check

.\.venv\Scripts\python.exe main.py

```



이 버전의 화면은 Tkinter/Pillow이므로 OpenCV HighGUI를 사용하지 않습니다. `opencv-python-headless` 하나를 사용합니다. 기존 환경에 다른 OpenCV 변형이 섞여 있으면 새 가상환경을 사용하세요.



설치 후 `run_windows.bat`를 더블클릭해도 됩니다. `.venv`가 있으면 그 Python을 사용합니다.



RTX 3050에서 실행하려면 해당 PC/드라이버에 맞는 CUDA용 PyTorch가 필요합니다. 공식 설치 선택기: https://pytorch.org/get-started/locally/

`config.json`의 `device=auto`는 CUDA 사용 가능 여부를 확인해 CUDA 또는 CPU를 선택합니다. `cuda`를 명시했는데 불가능하면 OCR 시작 오류로 알립니다. 실제 사용 장치·GPU 이름·EasyOCR/PyTorch 버전은 분석 JSON에 남습니다.



[OCR 시작]은 모델 로딩을 별도 스레드에서 수행합니다. 기본 `ocr_languages`는 `ko`, `en`입니다. 실물은 숫자 allowlist와 두 자리 검증을 적용하고, 가상 이미지는 한국어 번호판 원문도 후보로 받을 수 있습니다. 첫 실행은 `models/`로 사전학습 모델을 다운로드할 수 있습니다. `download_models=false`는 이미 모델을 준비한 오프라인 환경용입니다.



## 첫 촬영



1. `main.py` 실행 → **카메라 연결**. `cameras.json`의 A/B 시리얼을 실제 장치와 맞춥니다.

2. 각 카메라 패널의 **보는 주차장**을 확인합니다. A=가, B=나입니다.

3. **ROI 등록** → 칸 번호를 선택 → 네 모서리를 테두리 순서로 클릭 → **현재 칸 등록**.

4. 보이는 칸을 등록하고 **완료**. 가 12칸, 나 16칸 전체를 등록할 수 있으며 부분 시야도 지원합니다. 미등록 칸은 빈칸으로 취급하지 않습니다.

5. 실시간 화면과 ROI 선이 맞는지 확인한 뒤 **위치 확인**.

6. **한 장 저장**으로 원본과 ROI 동시 저장을 먼저 확인합니다.

7. **OCR 시작** → 분석 완료 후 **최근 분석 검수** 또는 저장 자료 탭에서 해당 사진을 엽니다.

8. 문제가 없으면 각 카메라의 **자동 수집**을 누릅니다. V7처럼 3초 준비 후, 저장 완료 후 최소 2초 간격입니다. 움직임/밝기/OCR 성공으로 저장을 막지 않습니다.

9. 장면을 바꾸면 **전체 일시정지**, 독립 장면이면 **새 배치**. 카메라를 옮겼다면 ROI를 다시 등록합니다.



ROI 좌표는 원본 해상도로 저장합니다. 카메라 시리얼·해상도·주차장·설치 구분값이 달라지면 이전 좌표를 자동 사용하지 않습니다. 단, 물리적인 카메라 움직임 자체는 자동 감지하지 않습니다. 재실행/연결 끊김 뒤에는 위치를 재확인합니다.



카메라 옵션은 V7 값을 유지했습니다: 1920×1080/30fps 요청, 자동 노출·화이트밸런스, 60Hz 옵션, 샤프니스 70 요청. 적용 결과는 logs/camera_A_options.json 및 B 파일에서 확인합니다. 설치 메모는 형광등 높이 184cm, 그 아래 10~30cm이며 거리·조도 실측은 아닙니다.



## 사진 불러오기



카메라 없이도 사용할 수 있습니다.



1. 주차장 A/B/C/D와 출처 `phone`, `virtual`, `other_image`를 선택합니다.

2. **사진 열기 → ROI 지정 → 저장**을 누릅니다.

3. 해당 사진의 주차칸을 지정합니다. 카메라 ROI를 휴대폰 사진에 자동 재사용하지 않습니다.

4. 원본 내용은 EXIF 방향을 반영한 PNG로 보관하며, 입력 파일명과 SHA-256을 함께 기록합니다.

5. 카메라와 동일한 OCR/검수 흐름을 사용합니다.



사진의 기록 시각은 가져온 시각이며 원래 카메라 촬영 시각이라고 표시하지 않습니다. 한 장의 사진에는 하나의 주차장을 지정합니다. ROI 좌표가 없는 번호판 단독 클로즈업은 이 버전에서 임의의 주차칸에 연결하지 마세요.



## 검수와 데이터셋



**저장 자료 · 검수 · 내보내기** 탭에서 사진을 선택합니다.



- 칸별 자동 번호 후보를 확인합니다. 자동 글자 박스는 자홍색입니다. OCR 글자 박스는 스티커 경계를 입증하지 않으므로 색상 표본으로 사용하지 않습니다.

- **자동 후보를 입력란에 복사**할 수 있지만 승인 상태로 바뀌지는 않습니다.

- **스티커 내부 네 모서리 지정 + 색 측정**을 눌러 바닥이 들어가지 않게 스티커 테두리 안쪽 네 점을 찍습니다. 주황색 영역 내부만 HSV로 계산하고 글자/그림자처럼 어두운 픽셀은 제외합니다.

- 직사각형으로 확장하지 않으므로 비스듬한 스티커의 바깥 모서리 쪽 바닥도 제외합니다. 영역 삭제 시 색상을 미확인으로 되돌립니다.

- 점유 상태 `unknown/occupied/vacant`, 번호, 스티커 배경색을 사람이 확인합니다. 측정 오류는 사람이 수정할 수 있으며 실제 측정 결과와 수동 선택은 함께 보관합니다. 색상을 선택하려면 사진별 스티커 영역이 있어야 합니다.

- 번호/색상/점유를 수정하면 승인 체크가 해제됩니다. 다시 확인한 뒤 승인하세요.

- 학습용 번호판 전체 박스가 필요하면 **번호판 전체 박스 지정**으로 왼쪽 위·오른쪽 아래를 찍습니다. 수동 전체 박스는 청록색입니다.

- 승인할 스티커/번호판 영역은 선택한 주차칸에 75% 이상 들어가고 다른 칸과의 겹침은 각각 20% 미만이어야 합니다. 경계를 걸치면 ROI를 확인하거나 승인을 보류하세요. 같은 실물 차량 번호를 두 칸에 중복 승인할 수 없습니다. 잘못 읽은 번호는 미승인 초안으로 보관할 수 있습니다.

- 검수자 이름을 입력하고 해당 칸의 **직접 확인·승인**을 체크한 뒤 **검수 저장**.

- 기존 검수 파일을 수정하면 history에 이전 내용을 보존합니다. 같은 사진은 하나의 검수 창으로 열며, 다른 작업에서 파일이 먼저 바뀌었으면 오래된 창의 덮어쓰기를 차단합니다. 종료 시 수정 사항의 저장/버리기/취소를 선택합니다.

- 손상된 촬영/분석 JSON은 다른 사진의 내보내기를 막지 않습니다. 원본 기록이 정상인 경우 분석 오류도 CSV 행으로 남기고 `candidates.report.json`에 제외/오류 이유를 기록합니다.

- **후보 CSV 저장**은 분석 대기/오류 사진도 포함한 등록 칸 목록입니다. 색상은 검수에서만 영역을 지정하므로 자동 후보 CSV의 색상은 미확인입니다. 확인된 색상/유형은 승인 JSONL에 포함됩니다.

- **승인 자료 내보내기**는 승인한 칸만 팀 공통 JSONL로 내보냅니다. 사진 경로, lot_id, space_id, space_type, 주차칸 다각형, 수동 번호판 박스, 스티커 내부 다각형과 측정 근거, 표시 번호, 배경색, 차량 유형, 점유 및 전용 칸 규칙을 함께 제공합니다.



이 JSONL은 Geti 전용 가져오기 형식이 아닙니다. 일부 칸만 승인한 사진을 전체 라벨 완료 사진으로 오해하지 않도록 `all_objects_in_image_annotated=false`를 기록합니다. 원본은 Geti 업로드에 활용할 수 있으며 전용 라벨 변환은 별도 검증이 필요합니다.

## 현재 자동 분석의 범위



- 각 주차칸 내부를 마스킹하고 EasyOCR의 회전/확대 기능으로 숫자·번호판을 읽습니다.

- 낮은 점수, 다중 텍스트, 6/9 방향 모호성, 이미지 경계에서 잘린 문자, 칸 사이 중복 번호는 보류합니다.

- 글자 박스를 확장해 주변 색을 읽는 이전 방식을 제거했습니다. 검증된 자동 스티커 검출/분할 모델이 없으므로 현재는 사진별 수동 네 점 영역이 필요합니다. 이후 검출 모델을 붙이더라도 색상 함수에는 검증된 스티커 내부 마스크만 전달해야 합니다.

- 색 측정은 지정한 영역 내부로 제한되지만 사용자가 바닥을 포함해 잘못 그리거나 조명/반사가 심하면 오차가 생길 수 있습니다. 표본 수·픽셀 비율·마스크를 기록하며, 픽셀이 부족하거나 모호하면 unknown입니다.

- 차량 탐지기는 아직 없습니다. 주차칸 바닥 숫자를 차량 번호로 오인할 수도 있습니다. **번호 미인식은 빈칸이 아니며 자동 점유는 항상 unknown**입니다.

- 미등록 칸의 상태는 기록하지 않습니다. 등록 칸 수와 미등록 목록을 촬영 기록에 남깁니다.

- OCR은 별도 작업입니다. 원본+ROI 저장이 먼저 완료되며, 미처리 항목은 pending 상태로 남아 다음 OCR 시작 때 이어집니다.

- 모델 로딩/현재 OCR 호출이 끝나기 전에는 종료 완료가 지연될 수 있습니다. 진행 중 원본 저장과 현재 분석을 마친 뒤 종료합니다.

- 승인 전 차량 유형 후보로 실제 단속이나 DB 상태를 변경하지 않습니다.



## V8에서 V9로 옮기기와 미결 사항



V9는 별도 폴더에서 실행합니다. 배포 ZIP에는 가상환경·모델·촬영 데이터·로그가 들어 있지 않습니다. `cameras.json`, `camera_quality.json`, `configs/parking_*.json`의 현재 값은 V8 기준을 복사했으며 실제 좌표를 새로 만들지 않았습니다. 별도 사용 중인 V8 설정/등록 ROI가 있으면 백업한 뒤 해당 설정을 V9에 옮기고, 실시간 화면에서 위치를 다시 확인하세요.



기존 사진을 이어서 검수하려면 **V8의 datasets를 V9의 datasets로 복사**하거나, V9 `config.json`의 `dataset_directory`를 기존 datasets 절대 경로로 지정할 수 있습니다. Windows JSON 경로는 `<local-path>`처럼 슬래시를 쓰면 편합니다. 공유 경로 방식은 기존 검수 파일도 갱신하므로 먼저 백업하고 V8/V9를 동시에 실행하지 마세요. 기존 `models`도 필요하면 복사할 수 있습니다.



제품 버전은 V9지만 자료 규칙 `1103-sticker-v1`은 유지합니다. 이 규칙에 맞는 V8 분석·검수는 사용할 수 있습니다. 분석 파일이 없거나 손상된 경우 재분석하며, 새 검증에서 잘못된 연결이 발견된 검수는 승인 내보내기에서 제외하고 사유를 남깁니다.



- 촬영 원본과 과거 검수 기록은 삭제하지 않습니다. 이전 규격의 OCR 결과는 OCR 시작 또는 `--analyze-only`에서 재분석합니다.

- 이전 규격 검수는 화면에서 pending으로 열며, 스티커 영역 없는 과거 색상은 미확인으로 표시합니다. 원본 검수 파일은 재저장 전까지 유지됩니다.

- 이전 승인 자료는 그대로 내보내지 않습니다. 재검수 후 승인해야 하며, 제외된 파일과 이유는 내보낸 JSONL 옆 `.report.json`에서 확인합니다.

- 이번 내부 규칙 버전은 `1103-sticker-v1`입니다. config의 `sticker_assignment_status=pending_team_table`은 번호별 색 배정표가 아직 미정임을 뜻합니다. 번호만 보고 색이나 유형을 부여하지 않습니다.

- `space_type`, `vehicle_type`, `car_id`는 현재 수집 자료의 내부 필드입니다. 백엔드의 최종 필드명 공지가 오면 별도 API 변환 계층에서 맞춥니다. 챗봇·프론트·billing 코드는 이번 범위에 포함하지 않습니다.
