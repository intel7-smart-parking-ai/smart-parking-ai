# V30 최종 코드·데이터 품질 심층 검수



2026-11-05 · V29 → V30. 사용자가 지정한 마지막 수정본입니다. V29 소스/ZIP/수집 자료를 보존하고 별도 V30 폴더에서 번호 영역 품질 누락을 보완했습니다. 아래는 현재 판정이며, 문서 뒤에는 이전 전체 분석을 삭제 없이 이어 붙입니다.



## 1. 최종 판단



코드 수준에서 재현한 품질 누락을 수정했고, 수집·검수·저장·복구·파일 대조·통과 선별·학습 내보내기의 자동 검증을 완료했습니다. 하지만 **완벽한 품질이나 모든 각도의 실제 인식률을 증명한 것은 아닙니다.** 현재 제공된 실물 자료는 차량이 없는 A/B 보드 사진2장입니다. 실제 천장/D39 차량 정답 자료, 장비, 새 학습 모델이 없는 범위에서 확인 가능한 코드 검증을 마무리합니다.



고정 기능 수용 기준은 **19/20=95% 유지**입니다. 회귀 통과율과 기능 충족률, 실제 인식률은 서로 다릅니다. R18 차량 외곽 검출에 의한 선침범·다중칸 점유의 실제 정답 대조는 아직 충족하지 않았습니다. 이 버전 번호만으로 기존 기능 점수를 높이지 않았습니다.



## 2. V29에서 확인한 누락과 V30 수정



| 항목 | V29 결과 | V30 결과 |

|---|---|---|

| 번호 부분만 흐리거나 정보가 없는 경우 | 주차칸/스티커 주변이 선명하고 박스가 크면 통과 가능 | 실제 번호 크롭 안의 선명도·어두운 비율·밝은 비율을 별도로 측정하여 보류 |

| 반사로 번호 부분만 하얗게 된 경우 | 주변 스티커 품질에 가려질 수 있음 | 번호 영역 과도하게 밝음 사유로 보류 |

| 번호 부분만 어두운 경우 | 주변 스티커 품질에 가려질 수 있음 | 번호 영역 과도하게 어두움 사유로 보류 |

| 번호 박스와 스티커가 같은 칸 안의 다른 곳을 가리키는 경우 | 수동 정답의 두 영역이 각각 같은 칸에 속하면 품질 통과 가능 | 번호 박스 면적 중 스티커와 겹치는 비율60% 미만이면 보류 |

| 과거 통과를 새 기준 통과로 읽는 문제 | 검사 규칙 개정을 구분하는 필드가 없음 | 새 판정에 `검사개정=number-pixels-v1` 기록. 과거 통과는 현재 집계에서 미판정/재검사 필요, 통과 전용 전달 제외 |



주변의 선명한 주차선·바닥 무늬가 흐린 숫자를 대신 통과시키지 않도록, 번호 크롭을 원본에서 정수 좌표로 자른 뒤 그 안에서만 측정합니다. 크롭 바깥의 픽셀을 쓰지 않고, 라플라시안 경계 영향을 줄이기 위해 크롭 가장자리1픽셀을 측정에서 제외합니다. 0/1픽셀 크롭도 예외나 NaN을 만들지 않고 작은 영역/선명도 부족으로 처리합니다.



스티커와 번호의 겹침60% 기준은 기존 자동 예측 검증에서 사용하던 기준을 품질 선별에도 적용한 것입니다. 사선 스티커에도 다각형과 번호 박스의 실제 겹침 면적을 계산합니다. 번호가 들어갈 자리를 억지로 고정하지 않으며, 경계값60%와 그 미만을 별도 회귀로 확인했습니다.



두 품질 누락과 과거 판정 구분 조건은 V29 비교 시험에서 기대 조건을 충족하지 못하는 것으로 확인했습니다. `V29_REPRODUCTION.json`은3개 비교 사례를 기록합니다. 별도 `NUMBER_QUALITY_V30.json`에는 선명한 대조군/번호 평탄화/번호 흐림/암부/반사/분리된 영역의6개 동일 입력 비교가 있습니다. V29는6개 모두 통과, V30은 선명한 대조군1개 통과·나머지5개 보류였습니다. 이 입력들은 합성 시험이며 OCR 정확도 측정 자료가 아닙니다.

## 4. 품질 기준과 보장 범위



| 기준 | 기본값/의미 |

|---|---|

| 주차칸 짧은변 | 32px 이상 |

| 스티커 짧은변 | 16px 이상 |

| 실제 정수 번호 크롭 짧은변 | 16px 이상 |

| 주차칸·스티커·번호 선명도 | 저장된 정책의 min_sharpness, 기본 라플라시안 분산60 이상 |

| 어두운/밝은 픽셀 | 회색값40 미만/245 초과 비율이 저장 정책의 최대값 이하, 기본0.98 |

| 번호와 스티커 | 번호 박스의60% 이상이 스티커 다각형과 겹침 |

| 정보 완성 | A12/B16 전칸 등록, 점유 확인, 점유 칸의 현행 D39 번호·흰/초록/파랑 스티커색·영역 확인, 번호 중복/색 일관성 검사 |

| 학습 정답 전달 | 위 조건의 현재 기준 통과 + 사람 승인 + 작업별 영역 조건 |



이 값들은 초기 필터 규칙입니다. JPEG 잡음이 많은 이미지도 선명도 수치가 높을 수 있고, 다른 글자·잘못된 번호·미묘한 반사/가림은 모든 경우를 걸러낸다고 보장할 수 없습니다. 사람이 잘못 승인한 정답 역시 자동으로 참이 되지 않습니다. 실제 천장 자료의 정답 대조와 눈으로 읽을 수 있는지 확인한 표본 검수가 필요합니다.



화질 보류 자료도 원본과 사유를 저장합니다. 보류를 줄이려고 임계값만 낮추면 정답 품질이 높아지는 것이 아닙니다. 각도를 더 모으는 작업은 자료 다양성을 늘리는 것이며, 실제 모델 학습·연결·독립 시험을 거쳐야 각도별 인식 성능을 확인할 수 있습니다.



## 5. 파일·데이터 계약과 과거 자료



원본은 `raw/<카메라ID>/<시점>/`, 칸명 표시사진과 한글 JSON은 `collected/<주차장>/<시점>/<칸명>/`, 전체 장면은 `scenes/<주차장>/<시점>/`에 연결됩니다. 시점 없는 과거 자료는 기존 경로와 미지정 상태를 유지합니다. 사진에는 칸명·실제 경계/가상 입구·값·보류를 표시하며, 무표시 원본과 학습 크롭은 따로 보존합니다.



새 한국어 품질 JSON은 번호 영역의 `너비_px`, `높이_px`, `짧은변_px`, `유효픽셀수`, `선명도`, `어두운픽셀비율`, `밝은픽셀비율`, `스티커겹침비율`과 사유를 기록합니다. `검사개정`은 제품 V30이라는 이름 대신 실제 검사 의미를 나타내는 `number-pixels-v1`입니다. D39 contract_revision과 collection/prediction/journal schema, 기본 설치 pose는 제품 번호만으로 바꾸지 않았습니다.



기존 품질 정책 키/촬영 설정을 임의로 바꾸지 않습니다. 과거 통과 판정에 새 검사 개정이 없으면 현재 UI에서 **미판정 및 이전 기준 재검사**로 표시하고 학습 가능 수에 넣지 않습니다. 과거 보류는 계속 보류입니다. 과거 자료를 읽거나 전체 후보를 복사하는 것은 가능하지만, 최신 품질 통과 전용으로 전달하려면 **선택 장면 저장 복구**를 실행해야 합니다.



복구는 저장된 원본·ROI·예측·사람 정답과 촬영 당시 정책을 이용해 품질/표시사진/JSON을 다시 만듭니다. 원본 픽셀·촬영 시각·시점·배치·정답을 바꾸지 않습니다. 재검사 결과에 따라 통과 또는 보류가 됩니다. 미완료/해시 불일치/필수 예측 유실 자료는 먼저 근거를 복원해야 하며 없는 값을 생성하지 않습니다.



통과 사진·JSON과 통과·승인 학습 내보내기 모두 같은 `require_current_selection` 검사를 사용합니다. UI 집계도 같은 개정을 확인하므로, 사진 전달은 새 기준인데 학습 수량만 과거 기준을 쓰는 차이가 생기지 않도록 했습니다. 내보내기는 복사이며 원본을 삭제하지 않습니다. 폴더 전체와 `EXPORT_STATUS.json`을 함께 전달해야 상대경로와 파일 해시를 확인할 수 있습니다.



## 6. 실제 실행한 최종 검증



- **회귀 369/369, 실패/오류/건너뜀0.** V30 신규19개. 실제 프로세스 강제 종료/잠금, 숨긴 Tk UI 흐름 시험을 포함합니다. 보존된 history/tests는 현재 회귀 수에 합치지 않았습니다.

- **A/B×다섯 시점 전체 흐름:** 합성 입력10장, 총140칸의 표시사진/JSON 짝, 내보내기 이미지160개·데이터 JSON150개, 학습 크롭160개. 같은 배치의 시점별 자료가 한 분할에 유지됨을 확인했습니다. 촬영 각도를 실제로 바꾸어 인식한 시험은 아닙니다.

- **제공된 실물 빈 보드 사진:** A12/B16의 ㄷ자28칸, 내보낸 사진/JSON28쌍, 다른 폴더로 복사한 뒤 상대경로·해시 확인. 두 사진은 정보 부족으로 보류2장/통과0장입니다.

- **OCR 실행 구분:** 기존 V23의 동일 픽셀/옵션 CPU 관측35회 재사용, 신규 OCR0회. 실제 차량 번호·색 정답률은 산출하지 않았습니다.

- **보존:** 이전 데이터 1373파일, V29 배포 소스 244파일과 ZIP 해시 일치. 기존 전체 통합 분석 원문 보존.

- **배포:** Python 64파일 구문 검사, JSON 읽기, 설정 검사, ZIP CRC/파일별 SHA256 검증. 카메라·모델·가상환경·촬영 데이터·임시 로그는 배포 소스에 포함하지 않습니다.



기록 파일은 `TEST_RESULTS_V30.json`, `NUMBER_QUALITY_V30.json`, `V29_REPRODUCTION.json`, `FAULT_MATRIX_V30.json`, `INITIAL_EXPORT_FAULTS_V30.json`, `SELECTED_EXPORT_FAULTS_V30.json`, `SELECTED_TRAINING_FAULTS_V30.json`, `PHYSICAL_BOARD_REPLAY_V30.json`, `PREVIOUS_DATA_REUSE_V30.json`, `VALIDATION.json`입니다. 실제 변경 소스는 `CODE_CHANGES_V29_TO_V30.diff`에 있습니다.



## 7. 이번 단계의 완료와 남은 실측



이번 V30 코드 수정·자료 흐름 검수·배포 검증은 마무리합니다. 사용자는 새 폴더에서 `run_windows.bat`를 실행하고 실제 주차장과 현재 촬영 시점을 선택하면 됩니다. 기본은 천장이며, 다른 방향이면 오른쪽·왼쪽·위쪽·아래쪽으로 변경합니다. 위/아래는 평면 방향이며 천장과 다릅니다.



다음 실측은 천장 장비에서 모든 칸과 번호를 읽을 수 있는 구도 확보 → 현행 D39 차량 배치의 다양한 장면 수집 → 정답 검수 → 실제 모델 학습/연결 → 학습에 쓰지 않은 별도 배치의 천장/시점별 평가입니다. 조건별 일치 수·보류 수·전체 정답 수를 함께 확인해야 합니다.



실제 물리 카메라/천장 설치, 차량 인식률, 차량 외곽 위반 모델, GPU/Geti/실서버, 장시간 촬영, 물리 정전, OneDrive/외부 작성자 경쟁, 실제 화면/DPI 육안 검수는 미완료입니다. OS 잠금은 이를 따르는 작성자끼리만 보호합니다. 이 구분을 유지한 최종 상태는 **기능 기준95%, 이번 자동 검증 통과, 현장 품질·정확도 미측정**입니다.





## 8. 추가 요청: ArUco 적합성



카메라 이동 후 주차칸 재등록 효율을 높이는 보조 수단으로 적용을 권장합니다. 현재 OpenCV에서 검출·평면 좌표 복원 합성 시험을 수행했으며, 실제 인쇄 마커와 UI 연결은 아직 적용하지 않았습니다. 자세한 코드 연결/현장 조건/공식 출처는 ARUCO_APPLICABILITY.md, 시험 수치는 ARUCO_FEASIBILITY_V30.json에 있습니다. 이 적합성 시험은369개 회귀 수에 합산하지 않았습니다.
