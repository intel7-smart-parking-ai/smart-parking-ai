# 주차장 데이터셋 수집 프로그램 — 전체 칸 인식·주차 이상·저장 현황 통합 UI 요구사항

> **문서 작업 · 2026-11-04.** 이번 사용자 요청을 [기존 통합 업무계획](PARKING_VISION_MASTER_PLAN_SINGLE_CAMERA_2026-11-04.md)에 추가하는 상세 요구사항이다. 프로그램 제작·카메라 시험·모델 성능 검증은 다음 작업에서 수행한다.
>
> **사용자가 원하는 결과:** 현재 카메라 화면 안의 모든 주차칸에 대해 **차가 있는지 → 몇 번 차량인지 → 스티커색이 무엇인지 → 주차 위치에 문제가 있는지**를 한 UI에서 확인하고, **어떤 파일에 데이터가 얼마나 저장됐는지**까지 함께 확인한다.
>
> **추가 확인:** 사용자가 말한 자동차 색깔은 **기존의 스티커 배경색**이다. 흰색=일반, 초록=전기차, 파랑=장애인 차량으로 구분한다.

## 1. 이번 요구를 어떻게 이해했는가

사진을 저장한 뒤 여러 창과 폴더를 찾아다니는 방식에서, **촬영 장면·전체 칸 인식 결과·이상 상태·검수·저장 결과를 한 화면에서 연결하는 수집 프로그램**으로 목표를 구체화한다. 자동 인식 결과가 먼저 표시되고, 사용자는 같은 화면에서 근거 이미지를 확인하며 잘못된 결과를 수정·승인한다.

예를 들어 가 주차장을 촬영하면 12칸이 모두 표시되고, A-05에는 23번·초록 스티커·전기차, A-06에는 10번·흰색 스티커·일반 차량이 있다는 결과가 보인다. A-06이 전기차 전용 칸이면 ‘차량 종류 불일치 의심’과 그 이유를 즉시 표시한다. 이때 번호·색이 잘 읽히지 않은 칸도 목록에서 사라지지 않고 ‘차량 있음 / 번호 미확인’ 등으로 남는다.

‘한번에 파악’은 여러 차량 결과를 **같은 분석 장면에 묶어 전체 칸에 표시**한다는 의미다. 모델 내부를 반드시 동시에 실행해야 한다는 요구로 한정하지 않는다. 서로 다른 시각의 차량·번호를 합쳐 현재 한 장면의 완전한 결과처럼 보여서는 안 된다.

### 1.1 적용 범위

| 항목 | 이번 기준 |
|---|---|
| 카메라 | 우지원 담당 카메라 1대 |
| 촬영 대상 | 가(A) 12칸·나(B) 16칸을 순차 촬영 |
| 기본 화면 | 현재 선택한 한 주차장의 전체 칸을 표시 |
| B카메라 | 다른 담당자 범위. 연결을 기다리지 않고 작동 |
| 색 정보 | 스티커 배경색 white/green/blue, 차량 종류와 연결 |
| 실물 번호 | D-39의 현행 24개, API 범위 10~99와 구분 |
| 데이터 품질 | 원본·좌표·작업별 정답·검수·중복/분할·인수 기준은 기존 계획 유지 |
| 이번 결과물 | 마크다운 요구사항·기존 계획 갱신 |

한 대로 가를 촬영하는 동안 나를 실시간 관측하는 것은 아니다. 화면 상단에는 **현재 촬영 주차장**을 표시하고, 저장 현황에서는 가·나 누적 자료를 모두 볼 수 있게 한다. 다른 주차장의 과거 결과를 보고 있다면 ‘저장 장면’과 촬영 시각을 표시한다.

## 2. 전체 주차칸을 인식한다는 의미

### 2.1 칸 위치와 차량 인식을 구분

고정 카메라에서는 먼저 도면과 실제 영상의 주차칸 영역(ROI)을 연결한다. 기본 설계는 사용자가 초기 칸 좌표를 등록·검수한 뒤, 프로그램이 그 영역별 차량 유무·번호·색을 계속 분석하는 방식이다. ‘모든 칸 인식’이 주차선과 바닥 칸 번호를 매번 자동 검출해야 한다는 뜻은 아니다.

| 단계 | 화면에 보여줄 결과 | 실패 시 동작 |
|---|---|---|
| 도면 선택 | 가 12칸 또는 나 16칸의 기대 목록 | 선택되지 않으면 분석 준비 안내 |
| ROI 등록·검수 | 기대 칸 수 / 등록 수 / 현재 유효 수 | 누락·중복·화면 밖 좌표를 구체적으로 표시 |
| 구도 확인 | 모든 대상 칸이 원본 안에 포함되는지 | 보이지 않는 칸을 빈칸으로 계산하지 않음 |
| 점유 분석 | 모든 칸에 점유/빈칸/관측 보류/처리 대기 | 번호 검출 칸만 목록에 올리지 않음 |
| 번호·색 분석 | 점유 칸별 번호·스티커색·미확인 이유 | 미인식이 있어도 점유와 해당 행 유지 |
| 위치 이상 검사 | 종류 불일치·경계 침범 등 근거별 상태 | 검사할 근거가 없으면 정상 대신 미검사/확인 필요 |

현재 카메라 구도로 모든 칸이 충분히 보이지 않으면 설치 높이·방향·촬영 조건을 다시 조정한다. ‘칸이 화면에 들어옴’과 ‘먼 칸의 번호까지 읽을 화질이 확보됨’은 별도 검사다. 전체 장면을 담느라 숫자가 너무 작아지는 경우, 원본 확대 확인과 판독 시험으로 촬영·스티커 조건을 개선한다.

### 2.2 완료 상태를 구체적으로 표시

상태 표시 예시는 다음과 같다. 숫자는 화면 설계 설명용이며 실제 측정값이 아니다.

```text
가 주차장 | 대상 12칸 | ROI 유효 12/12 | 분석 응답 12/12
점유 7칸 · 빈칸 4칸 · 관측 보류 1칸
현재 장면 번호 확인 5/7 · 스티커색 확인 6/7
주차 이상 후보 2건 · 위치 검사 불가 1칸
```

‘분석 응답 12/12’는 모든 칸의 처리가 반환됐다는 의미이며 12칸 모두 정답이라는 의미가 아니다. 번호·색의 자동 인식 성공 여부는 검수 정답과 대조해야 알 수 있다. 화면에는 ‘자동 판독됨’과 ‘사람 검수 완료’를 구별한다.

점유 7칸은 차량 7대를 확정했다는 뜻도 아니다. 한 차량이 두 칸에 걸치거나 한 칸에 여러 후보가 있을 수 있다. 차량 수를 따로 표시하려면 중복·다중 객체를 해결할 근거가 있어야 하며, 그렇지 않으면 ‘점유칸 수’로 표시한다.

## 3. 하나의 UI에 담을 화면 구조

### 3.1 화면 배치 제안

```text
┌──────────────────────────────────────────────────────────────┐
│ 주차장 [가/나]  카메라 상태  [실시간 분석/저장 장면 검수]      │
│ 분석 시각 · 현재 모드 · 모델 상태 · 전체 칸/점유/미확인 요약  │
├──────────────────────────────────────┬───────────────────────┤
│                                      │ 선택 칸 확대          │
│ 카메라 분석 장면                     │ 원본 칸 + 스티커      │
│ 전체 ROI · 칸 ID · 점유 · 번호 · 색   │ AI 결과 / 검수 정답   │
│ 이상 위치·이유·확인 필요 표시        │ 수정 · 승인 · 보류    │
│                                      │ 이상 근거·최근 상태   │
├──────────────────────────────────────┴───────────────────────┤
│ 전체 12/16칸 카드 또는 표: 점유·번호·색·이상·검수·저장 상태   │
├──────────────────────────────────────┬───────────────────────┤
│ 저장 경로·가/나·세션별 누적 수량     │ 최근 저장 목록        │
│ 원본/칸/스티커/라벨/승인/내보내기   │ 파일명·건수·완료/실패 │
│ [촬영 저장] [승인 저장] [내보내기]   │ [파일 열기][폴더 열기]│
└──────────────────────────────────────┴───────────────────────┘
```

한 메인 창 안에서 기본 작업을 끝내도록 한다. 번호·색을 보려고 별도 결과창을 열거나 저장 성공을 확인하려고 파일 탐색기를 필수로 열게 하지 않는다. 파일/폴더 열기는 상세 확인을 돕는 보조 기능이다.

실제 노트북 화면 크기를 확인한 뒤 기본 배치를 검증한다. 12칸·16칸 각각의 요약 카드와 전체 상태는 한눈에 보이게 하고, 긴 파일 이력이나 상세 로그만 내부 스크롤로 처리한다. 창 축소·DPI 변경으로 핵심 버튼·오류 안내가 가려지지 않게 한다.

### 3.2 화면 영역별 요구사항

| 영역 | 필수 표시 | 사용자 동작 |
|---|---|---|
| 상단 상태 | 현재 주차장, 실제 카메라, 연결/촬영/분석/저장 상태, 분석 장면 시각 | 주차장·모드 변경, 연결·중지 |
| 분석 영상 | 전체 칸 다각형·칸 ID·점유·번호·스티커색·이상 근거 | 칸 클릭, 확대·축소, 표시 항목 전환 |
| 전체 칸 카드/표 | 모든 12/16칸의 결과, 미확인·검수·저장 상태 | 선택, 이상/미검수 강조·정렬 |
| 선택 칸 상세 | 칸 원본·스티커 확대, 자동 결과와 정답, 품질 사유 | 번호·색·점유·영역 수정, 승인/보류 |
| 주차 이상 | 유형·해당 칸·차량 후보·근거·확인 상태 | 해당 칸/장면으로 이동, 근거 확인 |
| 저장 현황 | 현재 실제 저장 경로, 세션/전체 범위, 파일 종류별 수량·용량·실패 | 필터·새로고침·폴더 열기 |
| 최근 저장 | 촬영 시각·원본명·세션·주차장·저장 구성·라벨 상태 | 해당 저장 장면으로 이동, 파일 열기 |
| 알림/진행 | 모델 미준비·카메라 끊김·검수 충돌·쓰기 실패·저장 중 | 재시도·문제 위치 확인 |

단축키나 표시 전환이 있어도 핵심 기능은 화면 버튼으로 사용할 수 있게 한다. ‘전체 요약’은 필터를 적용해도 유지하고, 필터로 일부 행을 감추면 ‘표시 3/12’처럼 범위를 명시한다.

## 4. 칸별 표시 규칙과 결과 최신성

### 4.1 칸 카드/행의 필드

| 필드 | 표시 예시 | 규칙 |
|---|---|---|
| 주차장·칸 | 가 / A-05 | lot_id와 space_id 함께 식별 |
| 칸 종류 | 전기차 전용 | 도면 설정에서 가져옴 |
| 점유 | 차 있음 / 빈칸 / 관측 보류 / 처리 중 | 빈칸과 미확인을 구분 |
| 번호 | 23 / 미확인 / 복수 후보 | 유효한 직접 판독이 없으면 이전 번호를 현재 값으로 사용하지 않음 |
| 스티커색 | 초록 / 흰색 / 파랑 / 미확인 | 작은 색상 칩 + 글자. 상태색과 구분 |
| 차량 종류 | 전기차 / 일반 / 장애인 차량 / 미확인 | 확인한 스티커색에서 변환 |
| 위치/규칙 검사 | 이상 없음 / 종류 불일치 의심 / 경계 침범 의심 / 확인 필요 | 검사를 하지 않은 상태와 정상 구분 |
| 시간 | 분석 장면 시각, 번호 마지막 확인 시각 | 과거 이력은 현재 관측과 분리 |
| 검수 | 미검수 / 작업별 승인 / 보류 | 자동 결과를 자동 승인으로 바꾸지 않음 |
| 저장 | 미저장 / 저장 중 / 완료 / 일부 실패 | 디스크에 완료된 결과를 기준으로 표시 |

번호 미인식 칸은 `?`만 보여주지 말고 ‘번호 미확인: 스티커 작음/가림/모델 미준비/판독 실패’처럼 확인 가능한 원인을 표시한다. 원인을 모르면 ‘원인 미확인’으로 남긴다. 분석 confidence를 검증 없이 ‘정확도 98%’로 표시하지 않는다.

### 4.2 영상과 모든 결과는 같은 장면에 연결

실시간 분석 화면의 큰 영상은 **지금 표시하는 결과에 대응하는 원본 프레임**이다. 더 최신의 카메라 원본 위에 늦게 끝난 과거 번호·박스를 덧그리지 않는다. 필요하면 별도 작은 수신 미리보기나 ‘수신 중 / 분석 장면은 몇 초 전’ 표시를 둔다.

전체 장면 결과는 capture/frame ID, 주차장, 설치/ROI 개정, 촬영 시각에 묶는다. 점유만 먼저 반환되면 해당 칸에 점유를 표시하고 번호·색은 처리 중/미확인으로 둔다. 다른 프레임에서 나온 번호가 새 장면의 번호처럼 섞이지 않게 한다.

전체 장면 검수에서는 한 장면을 고정한다. 검수 도중 실시간 프레임이 바뀌어 선택한 번호·칸이 다른 차량에 적용되지 않아야 한다. 사용자가 검수에서 실시간으로 돌아오면 저장하지 않은 수정 여부를 알려준다.

동작 효율을 위해 과거 번호를 참고 표시할 경우 ‘이전 확인 23 / 15:32:10’처럼 **이력**으로 표시한다. 현재 번호 완성률에는 포함하지 않는다. 주차장 전환·ROI 변경·재연결·차량 교체 시 결과와 캐시의 연결을 다시 검증한다.

### 4.3 색·도형·문자 표시

점유/이상 상태의 테두리와 스티커색 칩을 별도로 표현한다. 예를 들어 붉은 테두리는 이상 후보, 회색 점선은 미확인 상태로 쓰되, 스티커가 파랑인 차량의 ‘파랑’은 칩과 글자로 표시한다. 색만으로 상태를 구분하지 않고 `정상`, `의심`, `미확인` 문구·아이콘을 함께 둔다.

이상 검사가 가능한 범위도 표시한다. ‘전용칸 종류 일치’만 확인하고 주차선 침범을 검사하지 않았다면 전체 상태를 무조건 ‘정상 주차’라고 표시하지 않는다.

## 5. 잘못된 주차 위치를 어떻게 보여줄 것인가

### 5.1 이상 유형을 구분

| 유형 | 예시 | 필요한 근거 | UI 표시 |
|---|---|---|---|
| 전용 칸 종류 불일치 | 일반 차량이 전기차/장애인 전용 칸에 있음 | 확인된 점유·칸 규칙·스티커색/차량 종류 | 종류 불일치 의심 + 칸 종류·차량 종류 |
| 주차선/칸 경계 침범 | 차량이 옆 칸이나 통로로 걸침 | 차량 실제 영역과 칸 경계의 공간 관계 | 경계 침범 의심 + 근거 영역 |
| 두 칸 걸침 | 한 차량이 이웃 두 칸을 사용 | 두 칸의 물체가 같은 차량이라는 근거 | 관련 두 칸을 함께 강조, 차량 수 중복 방지 |
| 지정 칸 밖 차량 | 통로·ROI 밖에 차량이 있음 | 칸 밖 관측 영역과 차량 존재 근거 | 칸 밖 차량 의심, 위치 표시 |
| 번호 귀속 혼동 | 이웃 칸에 같은 번호, 한 칸 복수 후보 | 스티커 위치·원본·칸 귀속 검사 | 번호 연결 확인 필요 |
| 관측 불가 | 가림·모델 없음·구도 이탈 | 품질/처리 상태 | 위치 검사 불가, 정상 판정하지 않음 |

번호 귀속 혼동은 실제 주차 위반과 다른 종류의 **인식 이상**이다. UI에서 ‘주차 이상’과 ‘인식 확인 필요’의 사유를 구분해 사람이 상황을 이해할 수 있게 한다.

### 5.2 전용 칸 규칙

흰색=일반, 초록=전기차, 파랑=장애인 차량이라는 기존 기준을 사용한다. 전용 칸 규칙은 프로젝트의 승인된 규칙표를 입력받아 적용한다. 일반 칸에 전기차/장애인 차량이 있는 경우 등 세부 허용 여부를 임의로 위반 처리하지 않는다.

스티커색을 못 읽었으면 번호 배정표에서 색을 채워 ‘색 인식 성공’이나 ‘확정 위반’으로 만들지 않는다. `점유 있음 / 차량 종류 미확인 / 전용칸 적합 여부 확인 필요`로 표시한다.

로컬 수집 UI는 설명 가능한 규칙 비교 결과를 즉시 표시한다. 운영 API가 연결된 경우 서버가 확정한 위반/상태를 **서버 결과**로 구분해 같은 UI에 표시한다. 서버 응답이 없거나 해당 API가 지원되지 않으면 ‘서버 미확인’으로 남긴다. 수집용 경고 표시만으로 서버의 입출차·요금·위반 기록을 직접 변경하지 않는다.

### 5.3 경계 침범·칸 밖 주차는 추가 근거가 필요

기존 D-32의 칸 점유 분류는 차 있음/없음의 근거를 제공한다. 그 결과와 스티커 위치만으로 차량 전체가 칸 안에 들어왔는지 확정할 수는 없다. **이번 ‘잘못된 위치까지 통합 확인’ 요구에 따라 기하학적 위치 검사 방법을 다음 프로그램 설계에 추가**한다.

| 검토 방법 | 필요한 자료/검증 | 한계와 결정 |
|---|---|---|
| 고정 빈 기준 대비 전경 영역 | 현재 설치의 빈 사진, 그림자·손·차량 구분 시험 | 변화 영역을 차량 전체로 바로 확정하지 않음 |
| 칸 주변의 차량 영역 추정 | 차체 윤곽/마스크 등 추가 정답과 독립 시험 | 점유 2분류와 다른 작업. 모델팀 역할·성능 검토 |
| 칸 밖 관심 영역 검사 | 통로·외곽 관측 영역, 차량/비차량 구분 자료 | 칸 ROI만 자르면 확인할 수 없는 구역을 보완 |
| 사람 확인 | 고정 원본에서 경계/차량을 직접 검수 | 데이터 정답 작성에 활용하되 자동 검출 성과로 세지 않음 |

기존 ‘전체 화면 차량 탐지 모델을 필수로 만들지 않는다’는 방침을 유지하면서 적용 가능한 보조 방식을 먼저 평가한다. 칸 밖·걸침 자동 판별을 위해 별도 차량 검출/분할 모델이 필요하다고 확인되면 D-32 범위·담당을 팀과 조정한다. 필요한 근거가 없는 상태에서 단순히 문구만 띄워 기능 완료로 보고하지 않는다.

위치 이상 검사는 사용자 요구 범위에 포함한다. 구현 준비 단계에서 근거가 부족한 유형은 ‘수동 확인/자동 미지원’으로 표시하고, 해당 자동 기능은 미완료로 남긴다. 카메라 원근·차량 높이·그림자의 영향이 있으므로 몇 픽셀 또는 ROI 겹침 비율 하나를 현장 시험 없이 보편적 위반 기준으로 확정하지 않는다.

## 6. 자동 인식과 사람 검수의 관계

사용자가 원하는 **전체 장면 자동 인식 결과 확인**과 **정확한 학습 정답 확보**를 둘 다 지원한다. 자동 모델이 아직 없을 때 수동 라벨을 넣어 화면을 채울 수는 있지만, 이를 자동 인식이 성공한 화면으로 표시하지 않는다.

| 데이터 | 화면 구분 | 저장·평가 원칙 |
|---|---|---|
| 모델 자동 결과 | AI 예측: 점유·번호·색·영역·모델 정보 | 원래 결과와 실패 상태를 보존 |
| 사람 수정 정답 | 검수 정답: 실제 값·검수자·사유 | 예측을 덮어 없애지 않고 별도 개정 |
| 로컬 이상 후보 | 규칙/위치 검사: 유형·근거·판단 가능 여부 | 자동/사람 확인의 출처 구분 |
| 서버 운영 상태 | 서버 확인: 상태·신원·확인 시각 | 로컬 결과와 다르면 차이를 표시 |
| 저장 결과 | 원본·예측·정답·미리보기의 완료 상태 | 화면 상태와 실제 디스크 상태 대조 |

번호·색을 한 칸씩 수정하더라도 전체 카드·선택 칸 상세·표시 사진은 같은 정답 개정을 사용한다. 다른 칸이나 다른 프레임에 수정이 전달되지 않아야 한다. 작업별 승인 기준은 기존 계획을 적용하고, ‘모두 승인’은 실제로 검수한 행의 필수 조건이 통과할 때만 수행한다.

점유만 확인된 사진은 점유용으로 승인할 수 있고, 번호·색은 보류할 수 있다. 번호를 못 읽는 사진을 임의 번호로 채우거나, 빈칸에 스티커 정답을 만들지 않는다. 이상 주차·가림·반사 자료는 원인을 표시해 학습 보강 또는 별도 평가에 사용하며, 정상 사진만 남겨 실제 어려움을 숨기지 않는다.

## 7. 촬영부터 결과 확인까지의 사용자 흐름

1. **연결·주차장 선택:** 카메라 한 대를 연결하고 현재 가/나를 선택한다. 저장 루트·세션·카메라 상태를 상단과 하단에서 확인한다.
2. **전체 칸 준비 확인:** 가 12칸/나 16칸의 등록·유효 수를 확인한다. 빠진 칸이나 구도 이탈은 화면에 표시하고 해당 부분의 정상 인식을 주장하지 않는다.
3. **자동 분석:** 현재 분석 장면에 점유·번호·스티커색과 주차 이상 후보를 표시한다. 모델 미준비·미인식·처리 중은 별도 상태로 보인다.
4. **장면 저장:** 버튼을 누른 장면의 원본과 결과를 같은 ID로 고정한다. 아직 끝나지 않은 작업은 같은 장면에 연결해 대기/실패 상태를 기록한다.
5. **한 화면 검수:** 저장 장면을 고정해 전체 결과를 보고, 이상/미확인 칸을 클릭해 원본·스티커 확대와 비교한다.
6. **정답 수정·승인:** 점유·번호·색·위치 이상을 검수하고 작업별로 승인한다. 자동 결과와 수정 이력을 보존한다.
7. **저장 확인:** 최근 저장 행에서 원본명·칸 사진 수·라벨 행 수·승인 수·저장 상태를 확인한다. 필요한 파일을 바로 열 수 있다.
8. **누적/내보내기 확인:** 현재 세션·가/나·전체 범위에서 파일과 유효 학습 자료 수를 확인하고, 승인 자료를 내보낸다.
9. **나로 전환:** 가 작업을 정리한 뒤 나 프로필·구도·ROI·기준 사진을 확인한다. 가의 기록은 유지되고 나의 현재 상태와 섞이지 않는다.

운영 서버 전송은 로컬 데이터 저장과 독립 상태로 표시한다. 사진 저장이 성공해도 API가 실패할 수 있고, API 접수가 성공해도 사진 저장이 실패할 수 있다. 두 결과를 같은 ‘성공’ 표시로 합치지 않는다.

## 8. 데이터가 어느 파일에 몇 개 쌓였는지 표시

### 8.1 항상 보이는 저장 요약

| 항목 | 표시 규칙 |
|---|---|
| 데이터 저장 위치 | 사용자가 선택한 **실제 절대경로**. 긴 경로는 복사/전체 보기 지원 |
| 현재 주차장·세션 | lot_id·session_id와 세션 시작 시각 |
| 집계 범위 | 현재 세션 / 선택 주차장 / 전체 데이터 / 선택 내보내기 묶음 |
| 원본 사진 | 저장 완료한 서로 다른 capture ID 수와 실제 원본 파일 수 |
| 칸 사진 | 실제로 저장 완료한 칸 크롭 파일 수. 생성 예정 수와 구분 |
| 스티커 사진 | 실제 스티커 크롭 파일 수. 빈칸에 가짜 파일을 만들지 않음 |
| 라벨 | 라벨 파일 수와 칸별 정답 레코드 수를 구분 |
| 작업별 승인 | 점유·스티커 검출·번호·색 각각 검수 완료한 유효 레코드 수 |
| 미검수·보류 | 처리할 자료 수와 주요 사유 |
| 내보내기 | 묶음별 성공/실패, 실제 포함 원본·학습 샘플·라벨 수 |
| 용량·실패 | 실제 파일 용량, 남은 공간, 쓰기 실패·유실·손상 확인 건수 |

한 번의 촬영에서 원본 1장·칸 사진 12장이 생겼다면 ‘13개의 독립 촬영 자료’로 세지 않는다. 원본·칸·스티커·정답·표시 미리보기·내보내기 복사본은 각각의 종류로 표시한다.

파일 수와 모델 학습 샘플 수는 다르다. 한 JSON 파일에 12칸의 정답이 있으면 ‘라벨 파일 1개 / 칸 레코드 12개’다. 번호 정답이 5칸만 승인됐다면 번호용 승인 수는 5개다. 화면에 ‘데이터 12개’ 하나만 보여주지 않는다.

### 8.2 최근 저장 목록

| 칼럼 | 사용자에게 알려주는 내용 |
|---|---|
| 촬영 시각·ID | 어떤 장면인지 |
| 주차장·세션 | 가/나 중 어디에서 찍었는지 |
| 전체 원본 파일명·경로 | 실제 사진이 어느 파일인지 |
| 칸/스티커 파일 수 | 그 장면에서 무엇이 생성됐는지 |
| 자동 결과 상태 | 점유·번호·색·위치 검사의 완료/미확인/미지원 |
| 검수 상태 | 작업별 승인·보류와 수정 개정 |
| 저장 구성 | 원본/메타데이터/예측/라벨/미리보기 각각 완료 여부 |
| 오류 사유 | 저장 실패 또는 참조 누락의 실제 원인 |
| 동작 | 장면 열기, 선택 파일 열기, 폴더 열기, 경로 복사 |

사용자가 파일을 선택하면 해당 사진의 전체 칸 결과와 라벨이 같은 UI에 다시 열린다. 저장 장면을 열었을 때 실시간 결과가 그 위에 섞이지 않는다. 최근 목록은 앱 재시작 후에도 저장된 기록을 기반으로 복원한다.

### 8.3 예시 수량과 해석

다음은 **UI 설명용 가상 수량**이며 현재 쌓인 데이터의 실측값이 아니다.

| 가 주차장 한 세션의 항목 | 표시 예시 | 해석 |
|---|---:|---|
| 전체 원본 | 10장 | 10개 capture ID |
| 칸 사진 | 120장 | 모든 12칸을 매번 저장한 경우 |
| 스티커 사진 | 42장 | 스티커 영역이 확보돼 저장한 것만 |
| 라벨 파일 | 10개 | 원본 장면당 1개라는 제안 구조일 때 |
| 현재 칸 레코드 | 120개 | 수정 이력을 중복 합산하지 않은 현재 레코드 |
| 점유 승인 | 95개 | 점유 작업에 쓸 수 있는 정답 수 |
| 번호 승인 | 30개 | 번호 작업의 승인 정답 수 |
| 색 승인 | 36개 | 색 작업의 승인 정답 수 |

이 세션의 독립 장면 수는 연속 촬영 여부에 따라 10개보다 적을 수도 있다. 120개 크롭이 120개의 독립 장면은 아니다. 같은 자료를 두 번 내보낸다고 학습 원본이 늘어나지 않는다.

### 8.4 정확한 집계 규칙

- 파일 쓰기 완료와 필요한 연결 정보 검증 후 성공 수량을 올린다. 버튼 클릭·작업 요청·파일명 할당만으로 올리지 않는다.
- 저장 중인 장면은 별도 진행 수량으로 표시한다. 원본은 성공했지만 크롭 2개가 실패한 경우 ‘원본 1 완료 / 칸 10 완료·2 실패’처럼 구성별로 보인다.
- 촬영 묶음의 전체 완료 여부와 개별 파일 저장 성공을 분리한다. 일부 실패한 묶음을 전체 성공으로 표시하지 않는다.
- 같은 capture ID의 재시도·재분석·정답 수정은 새 촬영으로 세지 않는다. 물리 파일이 여러 개면 실제 파일 수와 현재 유효 자료 수를 따로 표시한다.
- 승인 라벨을 바꿔 재검수가 필요하면 현재 승인 수를 다시 계산한다. 승인 이력 횟수를 현재 승인 자료 수로 쓰지 않는다.
- 프로그램 시작/새로고침 때 인덱스와 실제 파일을 대조한다. 파일 유실·외부 수정·해시 불일치가 있으면 불일치를 표시하고 유효 자료 집계에서 처리 원칙을 적용한다.
- 사진·라벨·미리보기의 복사본과 내보내기 파일은 원본 합계에서 중복 제외한다. 내용 중복 촬영은 품질 보고서에 별도 표시한다.
- 주차장·세션 필터를 바꾸면 모든 수량의 범위를 같이 바꾸고, 현재 보고 있는 범위를 헤더에 남긴다.

폴더 안 파일 수만 세거나 UI 메모리 변수만 누적해 영구 수량을 만들지 않는다. 저장 기록과 실제 파일의 일치를 기준으로 하며, 대조 작업이 진행 중이면 ‘확인 중’ 상태를 보여준다.

## 9. 파일 구조와 화면 결과의 연결

아래는 후속 구현을 위한 **저장 구조 제안**이다. 현재 V18 구조가 이렇게 바뀌었다는 의미는 아니다.

```text
<선택한 데이터셋 절대경로>/
  sessions/
    session_A_001/
      session.json
      frames/
        capture_000001.png            # 표시선 없는 원본
      captures/
        capture_000001.json           # 시각·카메라·설치·ROI·저장 상태
      spaces/
        A/A-05/capture_000001.png      # 칸 원본 크롭
      stickers/
        capture_000001_A-05_01.png     # 스티커 크롭, 필요 시
      predictions/
        capture_000001.json           # 자동 결과·모델·처리 상태
      annotations/
        capture_000001.json           # 작업별 검수 정답·개정
      review_previews/
        capture_000001_marked.png     # 검수/발표용 표시 사진
    session_B_001/
      ...
  exports/
    dataset_revision_001/
      manifest.json
      split_manifest.json
      label_map.json
      quality_report.json
      ...
```

### 9.1 각 저장 장면에 필요한 연결

| 범주 | 필요한 정보 |
|---|---|
| 원본 | capture/frame ID, 촬영 시각, camera_id·시리얼, lot_id·session_id, 파일경로·해시 |
| 촬영/좌표 | 해상도·실제 설정·설치 개정·ROI 개정·칸 목록·크롭 변환 |
| 자동 예측 | 각 칸의 점유·번호·색·근거 좌표·모듈 상태·모델 개정·완료 시각 |
| 이상 검사 | 유형·근거 영역·적용 규칙·판단 가능 여부·자동/수동·서버 확인 여부 |
| 검수 | 예측과 별개의 정답, 작업별 승인, 검수자·시각·수정 사유·개정 |
| 저장 결과 | 구성 파일별 완료/실패, 경로·크기, 묶음 완료 상태 |
| 품질/분할 | 장면 그룹·중복 그룹·판독 가능성·제외 이유·train/validation/test |

원본을 불러오면 이 연결로 같은 결과를 재구성할 수 있어야 한다. 표시 미리보기는 당시 화면을 이해하는 보조 자료이며 학습 원본을 대체하지 않는다. 미리보기에는 자동 예측인지 사람 검수 정답인지, 장면 시각과 미확인 상태를 표시한다.

칸 경계 침범용 차량 영역 정답을 추가할 때에는 기존 스티커 박스·색 내부 영역과 별도 필드로 정의한다. API의 `bbox_xyxy` 의미를 임의로 바꾸지 않는다. 데이터 형식의 실제 의미 변화가 있으면 별도 개정·이전 방법을 마련하고 기존 원본과 라벨을 보존한다.

## 10. 통합 결과를 확인하는 기준

### 10.1 사용자가 확인할 다섯 단계

| 단계 | 확인할 질문 | UI의 증거 |
|---|---|---|
| 전체 칸 | 현재 주차장의 모든 칸이 표시되는가? | 기대/등록/유효 칸 수, 누락 위치 |
| 인식 | 각 칸에 어떤 번호·스티커색 차량이 있는가? | 같은 장면의 전체 카드·원본·스티커 확대 |
| 이상 | 왜 잘못된 위치 또는 확인 필요로 판단했는가? | 규칙·차량 종류·경계·관측 불가 등 근거 |
| 저장 | 어떤 장면이 어떤 파일에 저장됐는가? | 최근 저장 행·파일 경로·구성별 완료 |
| 학습 자료 | 검수 후 실제 사용 가능한 자료가 몇 개인가? | 작업별 승인 수·내보내기 manifest·품질 보고 |

### 10.2 자동 결과와 정답 비교

검수된 장면은 점유·번호·색의 **예측값과 정답값**을 대조한다. 전체 칸 인식의 성공 사례뿐 아니라 미인식·오인식·관측 보류를 포함한다. 전체 장면에서 대상 칸을 모두 맞혔는지와 개별 칸 성적을 구분한다.

번호 정확도 분모는 ‘번호를 출력한 칸’만으로 제한하지 않는다. 평가 대상 점유 칸과 판독 가능성 기준을 기록하고, 출력하지 못한 칸도 포함한 완료율·정답률을 제공한다. 자동 결과에서 틀린 것을 사람이 고쳤다고 원래 자동 성적을 성공으로 바꾸지 않는다.

위치 이상은 종류별 오탐·누락·판정 불가를 따로 집계한다. 전용 칸 종류 불일치가 잘 동작해도 경계 침범 기능까지 성공했다고 계산하지 않는다. ‘위치 검사 미지원’도 미완료 범위로 보고한다.

화면·저장 예측·검수 파일·내보내기 결과가 같은 capture ID와 라벨 개정을 가리키는지 대조한다. 서버 연결이 있으면 event ID와 서버 조회까지 연결해 차이를 보여준다. 서버 202 접수와 실제 상태 반영은 구분한다.

## 11. 후속 프로그램 제작 순서와 역할

### 11.1 구현 순서

| 단계 | 구현 | 완료 증거 |
|---|---|---|
| U1 | 한 카메라·가/나 프로필·한 메인 UI·전체 칸 카드 | B카메라 없이 가 12/나 16 목록과 구도 상태 표시 |
| U2 | 동일 장면 점유·번호·색 결과 연결 | 자동 결과·미확인·모델 미준비가 구분되고 이미지와 일치 |
| U3 | 전체 칸/선택 칸 연동 검수 | 카드 클릭→확대→정답 수정→승인이 같은 칸·장면에 적용 |
| U4 | 주차 이상 통합 표시 | 종류 불일치 후보와 인식 이상, 위치 검사 근거/미완료 상태 표시 |
| U5 | 경계 침범·칸 밖 자동 판별 보강 | 방법·필요 정답·담당 합의 후 독립 영상으로 오탐/누락 검증 |
| U6 | 저장 구성·최근 파일·누적/승인 수량 | 성공/부분 실패·재시도·재시작 후 실제 파일과 일치 |
| U7 | 내보내기·장면 재열기·결과 대조 | 원본/예측/정답/미리보기/학습 묶음의 동일 출처 확인 |
| U8 | 실제 가/나 현장 시험·부하·서버 연결 | 12칸·16칸 전체 결과, 품질·주기·실패·복구 기록 |

단계 번호는 개발 순서를 설명하며 제품 버전 번호가 아니다. 모델 미준비 상태에서 수동·모의 입력으로 UI 연결은 시험할 수 있지만, **최종 자동 인식 완료에는 실제 모델과 실제 영상 시험이 필요**하다.

기존 11/06 A안 점유 시연에서는 번호 인식이 필수는 아니었다. 이번 최종 요구에는 **전체 칸 번호·스티커색 자동 판독과 통합 확인이 포함**된다. 점유만 동작하는 중간 시연을 최종 프로그램 완료로 보고하지 않는다.

| 담당 | 이번 요구와 연결되는 작업 |

| 김한별·박해준 | 점유 결과·유효성·점수, A/B안 연결, 필요한 차량 영역 보조 방법 협의 |

모델 출력에 번호·색뿐 아니라 `미확인/처리 실패/입력 무효`의 의미와 원래 프레임 문맥이 필요하다. UI가 임의 추정값으로 빈칸을 채우지 않도록 어댑터에서 계약을 명확히 한다. 파일 소유 경계는 기존 공동 작업 계획에 맞춰 정한다.

| 선 침범·두 칸 걸침·칸 밖 차량 | 구현한 검사 범위에서 근거 영역·관련 칸 표시, 오탐/누락 평가. 미구현이면 최종 요구 미완료 |
| 같은 번호가 이웃 칸에 중복 | 중복 후보/귀속 확인 필요, 차량 수 이중 확정 금지 |
| 점유 지속 중 차량 교체 | 이전 번호가 현재 차량처럼 유지되지 않고 재판독/미확인 표시 |
| 비동기 결과 지연 | 오래된 결과가 최신 영상/다른 주차장 위에 표시되지 않음 |
| 카드 선택·정답 수정 | 선택 영상·표·정답·저장 라벨이 같은 장면/칸에 연결 |
| 원본 1장·12칸 저장 | 실제 저장 구성과 화면 수량 일치. 원본 수와 크롭 수 구분 |
| 쓰기 실패·남은 공간 부족 | 부분 실패 위치·사유 표시, 미완료 묶음의 전체 성공 표시 금지 |
| 동일 장면 재시도·라벨 수정 | 촬영 원본 수가 중복 증가하지 않고 현재 승인 수 재계산 |
| 종료·재시작·파일 외부 유실 | 저장 기록 복원, 실제 파일과 수량 대조, 유실/불일치 안내 |
| 원본·예측·검수·내보내기 재열기 | 출처·개정·좌표·라벨이 일치하고 표시선 없는 학습 원본 보존 |
| 화면 크기·DPI·분석 부하 | 전체 칸 요약과 주요 상태를 확인할 수 있고 입력·저장 오류가 숨지 않음 |
| 서버 연결/끊김 | 로컬 수집 상태·API 상태를 각각 표시. 접수와 운영 확정 구분 |

전체 완료는 **UI가 채워진 상태**, **자동 인식이 검증된 상태**, **검수 정답과 저장 파일이 맞는 상태**를 함께 만족해야 한다. 슬롯별·장면별 인식률과 지연의 최종 수치 목표는 실제 영상·장비와 팀 기준으로 정하며, 정확도 100%를 사전 보장하지 않는다.

## 13. 기존 계획에 추가하는 핵심 요구사항 목록

| ID | 요구 | 완료 판단의 핵심 |

## 14. 교수님·팀원께 설명할 문안

> 수집 프로그램은 카메라 화면 안의 모든 주차칸을 한 UI에 표시하고, 각 칸에 차가 있는지, 차량 번호와 스티커색이 무엇인지 함께 보여주는 방향으로 만들겠습니다. 인식하지 못한 칸도 빠뜨리지 않고 미확인 상태와 원인을 표시하겠습니다.
>
> 전용 칸에 맞지 않는 차량이나 경계 침범 같은 주차 이상도 같은 화면에서 확인하도록 하겠습니다. 전용 칸 규칙과 차량 종류를 비교하는 기능, 차량 영역을 확인해야 하는 위치 검사 기능을 구분해 근거가 있는 결과를 보여주겠습니다.
>
> 사용자는 전체 영상에서 칸을 선택해 스티커를 확대하고, 자동 인식 결과와 실제 정답을 비교해 수정·승인할 수 있습니다. 저장할 때는 어떤 원본과 칸 사진·라벨이 만들어졌는지, 저장 경로와 누적 개수가 얼마인지 바로 확인할 수 있게 하겠습니다.
>
> 카메라는 한 대로 가·나 주차장을 차례로 촬영합니다. 각 주차장의 전체 칸 인식과 데이터 품질을 검증하고, 화면 결과·검수 정답·실제 저장 파일이 일치하는지를 완료 기준으로 삼겠습니다.
