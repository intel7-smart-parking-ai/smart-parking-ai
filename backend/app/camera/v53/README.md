# V53 36차 · 두 카메라 실시간 주차 관제

> **시연은 이 폴더(`backend/app/camera/v53`)만 사용한다.** `backend/app/camera/v51`은 수집 코드 원형 보관용이며 실행하지 않는다. 원격의 옛 브랜치 `feature/KAN-52-geti-unified`(서버 수정·"차량 화재" 표기 포함 첫 업로드)는 PR·병합 대상이 아니다.

Intel D435 두 대로 개발원 A 12칸과 부산역 B 16칸을 읽는다. 차량의 스티커에서 번호와 차종을 판독하고, 차량 지붕의 붉은 LED 위치를 도면에 대응시킨다. 일반칸은 세 종류 모두 정상이고 전기차·장애인 전용칸은 해당 종류만 정상이다. 번호가 불분명하면 빈 값으로 보낸다. 가림이나 연결 단절로 바닥을 확인할 수 없으면 빈칸 전송을 멈춘다.

## 카메라 PC 설치 5줄 (시연 PC 재설치용)

`backend/app/camera/v53` 폴더에서 PowerShell로 실행한다. 모델·도면·빈 바닥 기준은 팀 드라이브 `데이터셋/camera_v53_assets_<날짜>` 묶음(최신 `20261110`)에서 복원해 `assets.local.json`에 경로를 적는다(Git에 없음). 묶음 안 `RESTORE.md`에 복원 위치, `SHA256SUMS.txt`에 해시가 있고, 세 모델 해시는 [모델 명세](MODEL_MANIFEST_V53.json)와 같아야 한다. 드라이브 링크는 저장소에 적지 않는다.

```powershell
py -3.13 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-v53.txt
Copy-Item assets.example.json assets.local.json   # 이 PC의 모델·도면 경로로 수정
$env:API_BASE_URL = "http://<시연 서버 IP>"; $env:VISION_TOKEN = "<팀에서 받은 토큰>"
.\run_windows.bat --start-camera
```

전송 전 `Test-NetConnection <시연 서버 IP> -Port 80`으로 연결을 확인한다. 토큰은 파일에 저장하지 않고 실행 창에서만 설정한다.

**화면을 닫으면 외부 전송이 꺼진다(기본값).** 카메라 화면(8011)의 상태 조회가 30초 넘게 없으면 외부 주소로의 전송을 끄고 화면에 사유·시각을 표시한다. 시연 PC에서 카메라 화면을 닫아도 시연 서버 전송을 유지하려면 실행 창에서 `$env:V53_UNATTENDED_SEND = "1"`을 추가로 설정한다. 이 설정은 이미 승인·전송을 켠 주소에만 적용되며, 끊긴 동안의 관측을 나중에 보내지 않는다.

## 시연 당일 순서와 점검

| 순서 | 할 일 | 확인 |
| --- | --- | --- |
| 1 | 카메라 PC를 **서버와 같은 망**에 연결 | `Test-NetConnection <서버 IP> -Port <포트>`가 True. 봇 테스트 서버·시연 PC 주소는 팀 공지에서 확인(저장소에 적지 않음). 랜 포트 없는 노트북은 USB 랜 어댑터 또는 팀 Tailscale 참여 후 시연 PC의 Tailscale 주소 사용. 휴대폰 핫스팟만으로는 내부망에 닿지 않는다. 외부망에서는 `API_BASE_URL=https://<공개 도메인>`(HTTPS·토큰 필수)만 바꾸면 되지만, 11/10 현재 공개 도메인 앞단에서 카메라 수신 경로가 404로 막혀 있어 PM·서버 담당 확인 후 사용한다. **시연 사이트로는 도메인이 아니라 사이트 PC의 내부 IP와 `web` 컨테이너 포트**(공개용 중계 포트 아님)로 보낸다 — 도메인 경유는 지연이 커서 2초 기준을 넘기 쉽다. `Test-NetConnection` True, `http://<IP>:<포트>/api/v1/health` 200을 먼저 확인(연결 실패=방화벽·포트, 401·403=토큰, 404=주소 경로, 422=시계). 새 포트·터널은 PM 승인 없이 열지 않는다 |
| 2 | 시간 확인 | 서버는 2초 넘게 미래인 관측을 거부하고, 송신 시각(`X-Vision-Dispatched-At`)이 서버 시계보다 0.5초 넘게 앞서거나 2초 넘게 뒤져도 422로 거부한다. **PC 시계를 서버와 같거나 조금(0~1초) 늦게** 둔다. `w32tm /query /status`로 동기화 원본 확인. 어긋나면 관리자 PowerShell에서 `w32tm /resync` 또는 Windows 설정 > 시간 및 언어 > 날짜 및 시간 > 지금 동기화. 원본이 `Local CMOS Clock`이라 동기화가 안 되는 공용 PC(11/10 교육장)는 관리자 PowerShell `Set-Date -Adjust 00:00:0X.X`(늦추기는 `-00:00:0X.X`)로 맞춘다. 서버 시계 자체가 표준시와 다를 수 있으니(11/10 봇 서버 약 0.9초 늦음) 표준시가 아니라 **서버 시간차**를 기준으로 본다 |
| 3 | 실행 창에서 `API_BASE_URL`·`VISION_TOKEN`(DM으로 받은 값)·필요 시 `V53_UNATTENDED_SEND=1` 설정 후 `run_windows.bat --start-camera` | 토큰은 파일·채널·커밋에 남기지 않는다 |
| 4 | `http://127.0.0.1:8011`에서 두 도면의 칸 이름이 실제 칸과 맞는지 보고 승인 → **전송 켜기** | 화면 상단 "인식 중 · 관측 전송 켜짐". 조명·카메라·판을 만진 뒤에는 승인이 풀릴 수 있다(판 위치가 바뀌면 의도된 해제) → 칸 이름을 다시 대조하고 '칸 위치 맞음' |
| 5 | 사이트 지도 A 12칸·B 16칸, 관리자 입차 세션 번호, 차 한 대 빼기 → 빈칸 | 칸이 노란 점선(uncertain)으로 깜빡이지 않는지 1~2분 관찰. 서버 시험·리허설 전에 **남아 있는 시험 입차 세션이 없는지** 관리자 화면에서 확인(11/10 시험 세션 6건이 실제 번호와 409 충돌) |
| 6 | LED 하나씩 켜기 (**모의 화재 장면에서만**) | 관리자 안전 현황 "[모의 화재] … (실제 화재 아님)" 경보, 사용자 화면 대피 배너. LED가 켜져 있는 동안 카메라는 1초마다 모의 화재를 보내므로 경보가 계속 살아 있고 그 주차장의 결제 차단·대피 안내·챗봇 경보 응답이 이어진다(관리자 "경보 해제"를 해도 다시 생김). **결제·요금 장면 전에는 LED를 끄고**, 끈 뒤 경보 해제를 확인한다 |
| 7 | 시연장 조명에서 확신도 확인 | 서버 점유 기준은 0.80. `/live/state?images=false`의 칸별 `confidence`가 0.85~0.88인 칸(11/10 교육장 7칸)은 조명이 어두워지면 0.8 아래로 내려가 그 칸이 깜빡일 수 있다 → 조명 각도·밝기를 맞춘 뒤 다시 승인 |

카메라 높이·각도는 도면 기준(`runtime/board_landmarks/`)을 만든 위치 그대로 둔다. 카메라를 옮기면 첫 도면 정합이 늦거나 실패할 수 있다(A 도면은 시작 때 저장되는 고정점에 의존). 문제가 생기면 Esc로 정지 → F5로 다시 시작 → 4번부터 반복한다.

**차를 옮기거나 맞바꿀 때(운영 규칙)**: 차를 **완전히 빼서 그 칸이 빈칸으로 3초 이상 보인 뒤** 다른 차를 넣는다. 손이나 차로 가려진 동안 카메라는 빈칸을 보내지 않으므로(가림 = 빈칸 금지) 빈칸 없이 바로 바꿔 넣으면 서버에는 출차 없이 번호만 바뀐 것으로 보이고, 활성 입차 세션 번호와 달라 그 칸의 관측이 409로 거부된다. 409로 빠진 관측만큼 그 칸의 접수 간격이 벌어져(11/10 최대 3.3초) 지도에서 노란 점선으로 남는다. 이미 바꿔 넣었다면 차를 세션 위치로 되돌리거나 서버 담당에게 세션 정리를 요청한다. **카메라에서 번호를 빼고(null) 보내는 방식으로 우회하지 않는다**(세션 문제는 그대로이고 번호·세션 연결만 잃는다).

**칸이 늦게 바뀌거나 깜빡일 때**: 실행 창에 1분마다 `frame perf camera=… fps=… total_ms median=… p95=…`, `heartbeat max gap …s at <칸>`, `delivery last 60s {...} reasons {...}`가 찍히고 `runtime/logs/v53.log`(5MB×6개 순환, 토큰 없음)에도 남는다(`/live/state?images=false`의 `frame_perf`에도 있음, round38 이전에는 로그 설정이 없어 INFO 줄이 출력되지 않았다). 두 카메라는 한 스레드에서 번갈아 판독하므로 한쪽 `total_ms`가 길면 다른 쪽도 늦어진다. 수신 서버는 칸마다 2초 넘게 관측이 끊기면 그 칸을 uncertain(노란 점선)으로 바꾸므로, 하트비트 간격이 1.5초를 넘으면 WARNING이 찍힌다. 11/10 노트북 만차 기준 1.0~1.2fps(B 판독 약 480ms)에서 한 칸이 한 프레임만 판독 보류돼도 그 칸 간격이 약 2.6초가 됐다(#99 하트비트로 보완). 11/10 교육장 PC(Core Ultra 7)는 1.55fps·판독 중앙 274~375ms였다. 봇 테스트 서버가 받은 관측(16:45~16:55, 15,837건)의 칸별 접수 간격은 **22칸 p95 1.34~1.40초, 개발원 6칸(A-01·A-02·A-03·A-05·B-02·B-05) p95 2.28~2.37초, 차를 맞바꾼 칸 3.1초**였다. 같은 칸 하트비트가 1초 타이머라 1.55fps에서 두 프레임마다(1.29초) 보내졌고, 한 번만 건너뛰어도 1.94초+전송 지연으로 2초를 넘었다 → round38부터 같은 상태도 **매 프레임(0.6초 주기)** 보낸다(요청 약 28→43건/초). 2초를 넘는 칸이 몇 개뿐이면 그 칸의 409부터 본다. 칸별 결과는 `http://127.0.0.1:8011/live/delivery-trace`(최근 2,048건, 칸·결과·사유, 토큰 없음)에서 확인한다.

**LED가 경보에 안 뜰 때**: 빨간 차체를 LED로 오인하지 않도록 칸의 12% 이상을 덮으면서 점수 0.88 미만인 붉은 발광 후보는 제외한다(11/10 실험실 조명 기준). 제외된 상자는 `http://127.0.0.1:8011/live/state?images=false`의 결과마다 `filtered_lights`(칸·이유·점수·칸 면적 비율·상자)에 남고, 실행 창 로그에도 `LED candidate excluded camera=… bay=… reason=…`가 칸·이유별 1분에 한 번 찍힌다. 진짜 LED가 여기에 보이면 시연 조명에서 기준을 다시 잡아야 한다. 여기에도 없으면 LED 발광 모델이 그 위치를 못 잡는 것이다(11/10 부산역 A-06 42번 사례).

**LED 장착 차 명단(`mock_fire_cars`, round39)**: `assets.local.json`에 `"mock_fire_cars": ["11", "23", "42"]`처럼 LED를 단 차 번호를 적으면, **번호가 읽힌 다른 차 위의 붉은 빛은 어느 칸에서든 모의 화재로 확정하지 않는다**(`filtered_lights` 이유 `not_led_car`). 11/10 기록(`collection.db` 5만 프레임)에서 가짜 확정 1,300구간은 모두 번호가 읽힌 LED 없는 차(33·21·22·88·30 등) 위였고, 같은 자리에서 100~300프레임 연속·0.85~0.97점이라 점수나 반복만으로는 가를 수 없었다. 명단의 차는 '빨간 차체(12%↑·0.88↓)' 추정에서 빠진다(42번 지붕 LED가 칸 면적 12.1%·0.87까지 측정). 번호가 안 읽힌 칸·통로는 기존 광학 규칙을 쓰고, 0.88 미만의 약한 붉은 빛은 3프레임 연속일 때만 확정한다. 명단을 비우면(기본) 예전 동작이다. 확정 전 후보는 화면에 "LED 확인 중"으로 그린다(서버로는 확정만 보낸다).

**LED가 잠깐 안 보일 때(round39)**: 확정된 LED가 1~3프레임 안 잡혀도 같은 자리에 다시 보이면 바로 확정으로 잇는다(`LED_MISSED_FRAMES=3`). 안 보이는 동안 모의 화재를 대신 보내지는 않는다. 11/10 부산역 A-02 23번: 보일 때 0.93~0.95인데 1~3프레임씩 빠져 모의 화재가 2~6초 끊김(10분에 2초 초과 51회) → 수정 후 2분 동안 2초 초과 0회·최대 1.64초.

**LED 차 자리(11/11 D-75 해제, round40)**: 11/10에는 부산역 A-04~A-06에 LED 차를 두지 않았으나(42번 스티커 미확인, 11번 LED 포화로 미확정), round40 이후 A-04(42)·A-05(11)는 흰 차 분홍 발광 규칙으로, A-06(23)은 기존 규칙으로 확정된다(A4 가림 조명 실측 각 174/174, 끄면 즉시 0, 빨간 차 5분 오인 0). 앱 재시작 직후에는 42번 LED를 끈 채 번호를 한 번 읽힌 뒤 켠다. 조명·카메라를 바꾸면 재승인 후 다시 확인한다.

**차를 옮긴 칸의 번호(round39)**: 칸별 번호 고정(#84)은 빈칸이 확인될 때까지 다른 번호를 null로 보낸다. 빈칸 없이 바꿔 넣으면 계속 null이었다 → 고정된 차가 **지금 다른 칸(다른 카메라 포함, 승인된 화면)에서 읽히면** 그 칸의 고정을 새 번호로 바꾼다(맞바꾸기·순환 이동 즉시 반영). 고정된 차가 어디에서도 안 보여도(판 밖으로 치웠거나 옮긴 자리에서 번호 미판독), 새 번호가 같은 칸에서 **8프레임(약 5초) 연속** 읽히면 새 번호로 바꾼다(11/10: 11·23번이 부산역 A-04·A-06에서 안 읽혀 개발원 A-02·B-01이 10분간 null이던 사례). 번호가 잠깐 null인 프레임에서는 그 칸의 고정 번호로 LED 차 명단을 판단한다(`not_led_car_pinned`, 11/10 21번 3프레임 사례).

**흰 차의 LED(round40, 부산역 A-04·A-05)**: 42·11번은 흰 차라 차체가 LED와 같이 255로 포화되어, '밝은 중심 + 붉은 고리' 검출이 후보조차 못 만든다(42: 작은 상자 0.97 미만·약한 특징, 11: 후보 없음). 대신 LED 빛이 흰 지붕을 분홍으로 물들인다. **LED 명단 차가 있는 칸에서만** 분홍 화소(R-max(G,B)>25, R>150)가 칸 면적의 1~15%이면 3프레임 연속일 때 확정한다(`detail: led_car_glow`, 이벤트는 기존 `mock_fire_led_observed`). 11/11 A4 가림 조명 실측(960px): 42번 켬 466~499 / 끔 0~1화소(칸 7,322), 11번 켬 306~344 / 끔 0(칸 7,495), 빨간 차 24·30은 2,000화소 이상(약 28%)이라 15% 상한에 걸린다. LED가 켜지면 42번 스티커가 가려지므로(165/165프레임 미검출) 칸 고정(#84)처럼 **그 칸에서 직접 읽은 LED 차 번호를 빈칸이 보이거나 다른 번호가 읽힐 때까지 유지**한다. 앱 재시작 직후에는 LED를 끈 상태에서 번호를 한 번 읽어야 한다. 번호 없는 칸·명단 밖 차는 기존 규칙 그대로다.

**칸 경계의 붉은 빛(round41)**: 칸과 85% 미만으로 겹친 빛은 `boundary`가 되어 칸 단위 LED 명단 판단을 건너뛰고, 확정되면 칸 없는(주차장 단위) 모의 화재로 나갔다. 11/11 시연 사이트: 부산역 A-02(빨간 21번)에 82.7% 걸친 0.91 빛. 이제 경계 빛이 닿은 칸(`touching`)이 **모두 번호가 읽힌 LED 명단 밖 차**이면 `not_led_car_boundary`로 제외한다. 닿은 칸 중 하나라도 LED 차·번호 미판독·빈칸이면 기존 규칙, 통로 빛은 그대로다.

**운영자 실행 자동화(round43)**: 11/11 운영자가 직접 재시작하자 두 화면 승인·전송이 꺼진 채 남아 40분간 관측 0건이었고, 흰 LED 차(42·11)도 판정되지 않았다. 또 PC 시계가 시연 서버보다 0.5~0.7초 빨라 422 위험이 있었다.
- `V53_AUTO_APPROVE=1`: 앱 시작 때 마지막으로 **사람이 승인한** 판 위치(`runtime/board_landmarks/start-view-*.npz`)를 재검증 대기에 올린다. 두 프레임 연속 정확히 같으면 자동 승인(실측 시작 5초), 카메라·판이 움직였으면 기존처럼 '칸 위치 맞음'.
- `V53_AUTO_SEND=1`: 첫 승인이 되면 전송을 자동으로 켠다(운영자가 직접 끈 경우는 제외).
- 시계 보정: `V53_CLOCK_OFFSET_SECONDS`(서버−PC 초)와 `API_BASE_URL`의 `/api/v1/health` 시각으로 2분마다 다시 재서, 관측·송신 시각을 서버 시계에 맞춘다(±5초 안만, 그 밖이면 무시·경고). Windows 시간 동기화가 근본 해결이다.
- 시계 보정 방식(round44): 시연 서버(Windows의 Docker)의 시계가 약 3% 느리게 가다가 10~30초마다 되돌아가는 톱니(폭 약 1.1초)였다. 2분마다 한 번 재서 그대로 쓰면 꼭대기나 바닥을 잡아 관측이 1.35초 과거로 보였다(리뷰 15:12~15:15). 이제 10초마다 재고(응답 0.25초 넘는 측정은 버림) **최근 3분 측정의 중앙값**을 쓴다. `V53_CLOCK_SYNC=0`이면 주기 보정을 끈다.
- 세 값 모두 기본은 꺼짐이며, 교육장 실행기(`start_demo_send.ps1`)가 켠다. 11/11 실측: 운영자가 직접 실행 → 5초 뒤 자동 승인·전송, LED 차 3대 100% 확정, 2,048건 모두 수락.

**도면 승인 자동 복구(round42)**: 11/11 장애 시험에서 USB를 다시 꽂으면 두 화면 승인이 풀려 사람이 '칸 위치 맞음'을 눌러야 했다. 이제 재연결(새 스트림) 뒤에도 승인된 판 위치를 `APPROVAL_RECHECK_SECONDS`(90초) 동안 보관하고, **새 스트림의 연속 두 프레임이 승인 위치와 정확히 일치**하면 자동 복구한다(실측: 재연결 후 1.2초). 번호·빈 기준은 이어받지 않는다. 고정 기준 영상은 승인 중 노출에 맞춰 갱신되므로, 승인 당시 영상(`approved_views`)도 함께 보관해 조명이 돌아온 뒤에도 검증할 수 있게 했다. 전체 재탐색이 몇 픽셀 어긋난 결과는 재검증을 취소하지 않고 90초 뒤 만료된다. 카메라·판이 실제로 움직이면(11/11 시험 5~38px) 검증되지 않아 기존처럼 재승인이 필요하다. 복구 실패 사유는 1초에 한 번 `approval recheck failed: reference_not_matched|moved|frame_quality` 로그로 남는다.

**차를 여러 번 옮길 때(round45)**: 11/11 15:47 차를 옮기다 부산역 판이 3.7px 밀리자 전체 재탐색이 모서리에서 15px 넘게 어긋나 승인이 풀렸고, 픽셀 단위 재검증이 맞지 않아 9분간 부산역 전송 0(흰 LED 차 판정도 꺼짐). 이제 승인이 풀린 동안 같은 판이 승인 위치에서 화면 크기의 1.6%(약 31px) 안에서 5프레임 연속 같은 자리로 찾히면 그 새 위치를 승인으로 쓰고 저장한다(실측 15:55 3.7px 자동 복구). 칸 폭이 약 100px라 칸 배정이 바뀌지 않으며, 더 크게 움직이면 기존처럼 '칸 위치 맞음'이 필요하다.
또 LED를 켠 채 옮긴 LED 차는 새 칸에서 번호를 한 번도 못 읽어(불빛이 스티커를 가림) LED 차인지 알 수 없었다(부산역 B-01 11번). 번호를 못 읽은 점유 칸이 LED 범위 분홍빛(1~15%)을 보이고 LED 명단 차 중 최근 10초 동안 어디에서도 읽히지 않은 차가 있으면 LED 차로 본다(3프레임 확정). 읽힌 명단 밖 번호는 제외, 빨간 차체는 15% 상한, 모의 화재 이벤트에는 번호를 싣지 않는다.

**LED 탈락 진단(round40, 동작 변화 없음)**: 붉은 빛 후보가 왜 빠졌는지(`low_score`·`small_box`·`weak_features`·`orange_body`·`paint_reflection`)를 프레임 결과 `rejected_lights`에 남기고, 칸별 횟수·최고점을 1분에 한 번 로그로 쓴다. `V53_LED_DEBUG_BAYS=A-04,A-05`로 칸을 좁힐 수 있다.

**RGB 노출 고정(round40, 기본 꺼짐)**: `V53_EXPOSURE`·`V53_GAIN`·`V53_WHITE_BALANCE`·`V53_POWER_LINE`(50/60)을 지정한 경우에만 자동 노출·화이트밸런스를 끄고 값을 넣는다. 카메라별 `V53_CAMERA_1_EXPOSURE`가 우선한다. 지정하지 않으면 기존과 같고, 잘못된 값은 무시하고 경고만 남긴다. 11/11 시험에서는 쓰지 않았다(바꾸면 빈칸 기준 재등록·전체 재측정 필요).

## 카메라 PC에서 실행

소스 폴더는 ZIP 안의 `smart_parking_v53`, 팀 저장소에서는 `backend/app/camera/v53`이다. 그 폴더를 VS Code로 열고 PowerShell에서 실행한다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements-v53.txt
Copy-Item assets.example.json assets.local.json
```

최초 설정 때 팀 드라이브 `데이터셋/camera_v53_assets_<날짜>` 묶음에서 Geti IR의 XML·BIN 쌍, 점유·번호 분류 모델, 도면, 인쇄번호 표본, LED 특징 모델과 빈 바닥 기준을 복원한다. `assets.local.json`에 이 PC의 자료 경로를 지정한다. 기존 설정 파일은 계속 사용할 수 있다. 모델 종류와 해시는 [모델 명세](MODEL_MANIFEST_V53.json)에 있다. 선택 OCR 작업자는 [전용 의존성](requirements-ocr.txt)과 `ocr_python`, `ocr_models` 설정을 사용한다.

```powershell
.\run_windows.bat --start-camera
```

[카메라 화면](http://127.0.0.1:8011/)에서 각 도면의 실제 칸 위치를 확인한다. F5로 시작, Esc로 정지, Space로 현재 결과를 저장한다. 로컬 수집 기록은 프로그램 폴더의 `runtime/collection.db`에 저장된다. 저장 사진 분석은 카메라 송신과 분리된다.

## 수신 서버와 관제

팀 저장소 루트에서 서버 가상환경에 `backend/requirements.txt`를 설치한다. 시험용 토큰을 서버와 카메라 프로세스의 `VISION_TOKEN`에 동일하게 설정하고, 카메라의 `API_BASE_URL`에 수신기의 기본 주소를 지정한다. 아래 예시는 같은 PC에 별도 시험 DB를 만든다.

```powershell
$env:PARKING_MODE = "real"
$env:SMART_PARKING_DB_PATH = Join-Path $PWD "camtest.db"
.\.venv\Scripts\python.exe -m uvicorn backend.app.main:app --host 127.0.0.1 --port 8000
```

카메라에서 관측 전송을 켠 뒤 팀 관리자 화면과 `GET /api/v1/parking-lots/{A,B}/spaces`에서 칸 상태를 확인한다. 교육장 Docker 연결에는 승인된 웹 포트가 필요하다.

## 보내는 이벤트 (팀 API 계약 그대로)

| event_type | 언제 |
| --- | --- |
| `vehicle_observed` | 칸 점유 확인. `car_id`는 D-54 번호 또는 `null` |
| `space_empty_observed` | 검수한 빈 바닥이 현재 프레임에서 확인된 칸만 |
| `mock_fire_led_observed` | 빨간 LED 점등(절대 규칙 6, **모의 화재**). 차량 지붕 위면 `space_id`·`car_id`·`vehicle_type`을 채우고, 통로·칸 경계면 `space_id`·`car_id`가 `null` |

본문 필드는 `event_id, event_type, source, lot_id, camera_id, space_id, car_id, vehicle_type, confidence, bbox_xyxy, observed_at, frame_id`뿐이다. 카메라 내부 표시(`_`로 시작하는 키)는 전송 직전에 제거한다. 화면 표기는 **(모의 화재)** 이며 LED 소등은 표시하지 않는다.

**칸별 번호 고정(36차)**: 점유 중인 칸에서 처음 확정한 번호를 그 칸에 고정한다. 같은 칸이 점유된 채 다른 번호가 읽히면 새 번호 대신 `car_id: null`을 보내 활성 세션의 번호가 바뀌는 409를 막는다. 빈칸이 확인되거나 카메라를 다시 시작하면 고정을 푼다. 번호를 못 읽은 프레임에 고정 번호를 대신 채우지 않는다. 나중의 번호 연결·칸 이동은 서버(박해준) 담당이다.

## 34차에서 수정한 부분

최초 위치 승인 때 사용자가 검토한 프레임의 빈 바닥과 발광 근거를 한 번의 관측으로 보존한다. 이후 다른 프레임의 같은 지점에서 다시 확인해야 전송할 수 있다. 재승인·연결 단절·오래된 프레임·도면 변경에서는 근거를 폐기한다. 동일한 칸과 프레임의 점유와 모의 화재를 전송할 때는 모의 화재 요청이 먼저 도착할 기회를 최대 100ms 주어 화면의 순간적인 소등을 줄였다. 차량 이동·제거와 다른 칸은 이 대기를 적용받지 않는다.

현재 배치의 검사 수치와 미검증 항목은 [검증 결과](VALIDATION.json)에 있다. 재시작 후 28칸이 모이는 시간, 차량을 손으로 움직인 순간부터의 시간, 요금 세션의 최종 입출차는 서로 다른 측정 항목이다.
